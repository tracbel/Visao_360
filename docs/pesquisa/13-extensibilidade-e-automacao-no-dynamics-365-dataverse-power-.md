# Extensibilidade e automação no Dynamics 365 / Dataverse (Power Platform) — pipeline de eventos, plug-ins, automação declarativa, Power Fx, integração e ALM — com receita de replicação em .NET 8 puro

> Pesquisa automatizada - workflow `crm-tracbel-pesquisa-profunda`, 30/08/2026.

## Resumo

O Dataverse resolve extensibilidade com UM conceito central: toda operação de dados é uma *mensagem* nomeada (Create/Update/Delete/Retrieve/RetrieveMultiple/Associate/Assign/SetState...) que atravessa um pipeline de 4 estágios (PreValidation, PreOperation, MainOperation=30, PostOperation=40). Extensões (plug-ins) se registram como *steps* em (mensagem + tabela + estágio + modo), com ordem de execução, filtering attributes e snapshots pré/pós (entity images). O contrato de código é minúsculo — `IPlugin.Execute(IServiceProvider)` — e todo o resto é configuração em tabela (`SdkMessageProcessingStep`), o que permite ligar/desligar lógica sem release. Isso é o que a Tracbel deve copiar. O que NÃO copiar é o entorno: sandbox de 2 minutos, isolamento por processo, assembly .NET Framework 4.6.2 de até 16 MB assinado, registro via ferramenta externa (Plug-in Registration Tool), depth 8 de anti-loop, camadas managed/unmanaged de solutions e a proliferação de 6 mecanismos concorrentes de automação (business rules, real-time workflows, BPF, cloud flows, Power Fx low-code plug-ins, plug-ins) que a própria Microsoft hoje desaconselha em parte ("There are better ways to create modern automations" na doc de real-time workflows). Em .NET 8 o pipeline inteiro cabe em ~200 linhas: um `IRequestHandler` por mensagem + uma lista ordenada de `IStageHandler` resolvida por DI, tudo dentro de uma transação EF Core, com registro em tabela e cache. Números que definem o desenho: 2 min hard limit / 2 s recomendado por plug-in, 6.000 requests/300s e 52 concorrentes por usuário (service protection), 5.000 linhas por página FetchXML, 50.000 registros em agregação, 256 KB (webhook) / 192 KB (Service Bus) de payload de evento, 116,85 MB de mensagem máxima, 500 ações por cloud flow, 150 business rules por tabela.

## Entidades / objetos mapeados

### `SdkMessage / SdkMessageFilter`

**Funcao:** Catálogo de todas as mensagens (operações) do Dataverse e de quais combinações mensagem+tabela aceitam extensão. Flags iscustomprocessingstepallowed e isvisible determinam elegibilidade.

**Campos-chave:** name, isprivate, primaryobjecttypecode, iscustomprocessingstepallowed, isvisible

**Relacoes:** SdkMessage 1:N SdkMessageFilter; SdkMessageFilter é referenciado por SdkMessageProcessingStep

### `SdkMessageProcessingStep`

**Funcao:** A tabela central da extensibilidade: cada linha é um registro de handler no pipeline. É o que a Tracbel deve replicar como crm_pipeline_step.

**Campos-chave:** Message, PrimaryEntity, SecondaryEntity, FilteringAttributes, EventHandler(PluginType), Stage, Mode(sync/async), Rank(Execution Order), ImpersonatingUserId, Configuration(unsecure), SecureConfiguration, StateCode(enable/disable)

**Relacoes:** N:1 SdkMessage, N:1 PluginType; 1:N SdkMessageProcessingStepImage

### `SdkMessageProcessingStepImage`

**Funcao:** Define os snapshots pré/pós operação (entity images) com alias e lista de colunas. Acessados no código via context.PreEntityImages[alias] / PostEntityImages[alias].

**Campos-chave:** EntityAlias, ImageType (PreImage/PostImage), Attributes

**Relacoes:** N:1 SdkMessageProcessingStep

### `PluginAssembly / PluginType / PluginPackage`

**Funcao:** Armazenamento do código. PluginAssembly guarda o binário em base64 na coluna Content (máx 16 MB, .NET Framework 4.6.2, assinado). PluginPackage guarda um NuGet com dependências (conteúdo em file storage, não no SQL) e dispensa assinatura.

**Campos-chave:** PluginAssembly: Content, Version(major.minor.build.revision), IsolationMode(Sandbox), SourceType(Database). PluginType: Name, FriendlyName, WorkflowActivityGroupName

**Relacoes:** PluginPackage 1:N PluginAssembly 1:N PluginType 1:N SdkMessageProcessingStep

### `CustomAPI / CustomAPIRequestParameter / CustomAPIResponseProperty`

**Funcao:** Definição de mensagem própria (nova API). Governa quanto de extensão terceiros podem aplicar sobre aquela operação.

**Campos-chave:** UniqueName, AllowedCustomProcessingStepType (None/AsyncOnly/SyncAndAsync), BindingType (Global/Entity/EntityCollection), IsFunction, IsPrivate, ExecutePrivilegeName, PluginTypeId, WorkflowSdkStepEnabled, IsCustomizable

**Relacoes:** CustomAPI 1:N CustomAPIRequestParameter, 1:N CustomAPIResponseProperty; N:1 PluginType

### `ServiceEndpoint`

**Funcao:** Registro de destino externo: webhook HTTP, Azure Service Bus (Queue/Topic/OneWay/TwoWay/REST/PersistentQueue) ou Event Hubs. Invocável de plug-in via IServiceEndpointNotificationService.

**Campos-chave:** ContractType, AuthType (HttpHeader/WebhookKey/HttpQueryString para webhook; SAS para Service Bus), Url, MessageFormat (binário .NET/XML/JSON), NamespaceFormat

**Relacoes:** Referenciado por SdkMessageProcessingStep (o step aponta para o endpoint em vez de para um PluginType)

### `Workflow`

**Funcao:** Armazena processos declarativos: background workflows, real-time workflows, business process flows, business rules (compiladas em XAML) e actions. Todos compartilham a mesma tabela — o Category distingue.

**Campos-chave:** Category (Workflow/Dialog/BusinessRule/Action/BusinessProcessFlow), Mode (0=async, 1=sync), Scope, StateCode (Draft/Activated), XAML, TriggerOnUpdateAttributeList

**Relacoes:** N:1 tabela primária; BPF gera uma tabela própria por processo para as instâncias

### `Organization`

**Funcao:** Configurações globais do ambiente que afetam integração e automação.

**Campos-chave:** ExpireChangeTrackingInDays (default 7 dias — janela do delta token), Allowconnectorsonpowerfxactions (liga/desliga conectores em low-code plug-ins)

**Relacoes:** 1 por ambiente

### `PluginTypeStatistic`

**Funcao:** Telemetria de execução de plug-ins e workflow extensions, populada 30 min a 1 h após a execução. ATENÇÃO: a doc oficial marca esse recurso como 'no longer operational or supported. Don't use it.'

**Campos-chave:** ExecuteCount, AverageExecuteTimeInMilliseconds, FailureCount, CrashCount

**Relacoes:** N:1 PluginType

### `Solution / SolutionComponent`

**Funcao:** Unidade de empacotamento e distribuição (managed/unmanaged). Define camadas, publisher, prefixo e dependências. Limite de 95 MB por solution.

**Campos-chave:** UniqueName, IsManaged, Version, PublisherId (prefixo imutável após criação de componentes), ComponentType

**Relacoes:** Solution 1:N SolutionComponent; SolutionComponent aponta para qualquer componente customizável (incluindo PluginAssembly e SdkMessageProcessingStep, que precisam ser adicionados SEPARADAMENTE)

## Achados

### 1. O pipeline de execução tem 4 estágios e o estágio é um NÚMERO no contexto

Toda mensagem é processada em 4 estágios: **PreValidation**, **PreOperation**, **MainOperation** e **PostOperation**. Os valores numéricos 30 (MainOperation) e 40 (PostOperation) estão CONFIRMADOS em documentação oficial: o exemplo de código de Custom API usa `context.Stage.Equals(30)` para detectar a main operation, e o payload JSON de webhook publicado pela Microsoft mostra `"Stage": 40` no contexto do PostOperation e `"Stage": 30` no ParentContext. Os valores 10 (PreValidation) e 20 (PreOperation) são universalmente citados pela comunidade mas NÃO aparecem numericamente na doc oficial que li. Semântica de cada estágio: PreValidation roda ANTES da transação de banco E ANTES das checagens de segurança (é o único lugar barato para cancelar); PreOperation roda DENTRO da transação e é onde se alteram valores do registro; MainOperation é "for internal use only" exceto para Custom API e provedores de virtual table; PostOperation roda dentro da transação, é onde se modificam os OutputParameters, e é o ÚNICO estágio que aceita registro assíncrono.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework (tabela 'Event execution pipeline'); https://learn.microsoft.com/en-us/power-apps/developer/data-platform/custom-api (código `context.Stage.Equals(30)`); https://learn.microsoft.com/en-us/power-apps/developer/data-platform/use-webhooks (JSON com "Stage": 40)

**Licao para a Tracbel:** COPIAR o conceito, SIMPLIFICAR para 3 estágios. A Tracbel deve ter `BeforeValidation` (fora da transação, cancela cedo e barato), `BeforeSave` (dentro da transação, muta a entidade) e `AfterSave` (dentro da transação, lê resultado). O 4º estágio do Dataverse (MainOperation) só existe porque a Microsoft precisou de um gancho para Custom API e virtual tables — em .NET 8 isso é simplesmente 'o handler principal', não um estágio registrável. NÃO usar números mágicos como valor do estágio: usar `enum PipelineStage { BeforeValidation, BeforeSave, AfterSave }`. Os números do Dataverse são um acidente histórico de serialização e hoje vazam para o código de todo mundo (`Stage.Equals(30)` é feio e não se documenta sozinho).

### 2. O ponto de extensão é uma linha de tabela, não uma linha de código — SdkMessageProcessingStep

O registro de uma extensão é UMA LINHA na tabela `SdkMessageProcessingStep`, com os campos: Message, Primary Entity, Secondary Entity, Filtering Attributes, Event Handler (classe), Step Name, Run in User's Context (impersonação), Execution Order (rank), Description, estágio e modo. Tabelas relacionadas: `SdkMessage` e `SdkMessageFilter` (catálogo de mensagens válidas, com as flags `iscustomprocessingstepallowed` e `isvisible` que dizem se aquela combinação mensagem+tabela aceita extensão), `SdkMessageProcessingStepImage` (as entity images), `PluginAssembly` (o binário em base64 na coluna `Content`), `PluginType` (as classes) e `PluginPackage` (o pacote NuGet com dependências). Um step pode ser ativado/desativado (Enable/Disable, ou Turn on/Turn off no Power Apps) sem recompilar nada.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in (seção 'General Configuration Information Fields' e 'Unregister components'); https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework (query Web API sobre sdkmessages)

**Licao para a Tracbel:** COPIAR, e é o achado mais importante do tópico inteiro para o requisito 'extensibilidade sem release'. A Tracbel deve ter uma tabela `crm_pipeline_step` com (Id, Mensagem, Entidade, Estagio, Modo, Ordem, HandlerKey, FiltroCampos, Ativo, ExecutarComoUsuarioId, ConfigJson). Um `IHandlerRegistry` lê essa tabela no boot (com cache invalidado por versão) e resolve `HandlerKey` -> tipo via DI keyed services do .NET 8 (`services.AddKeyedScoped<IStageHandler>("AprovacaoDesconto", ...)`). Desligar uma regra vira UPDATE numa linha; reordenar vira UPDATE na coluna Ordem. Sem deploy. Isso entrega 'extensibilidade sem release' sem precisar de plugin dinâmico, DLL carregada em runtime ou motor de script — que são as três armadilhas caras.

### 3. Filtering attributes: a otimização que decide a performance de todo o sistema

Ao registrar um step em `Update`, você declara quais colunas disparam o handler. A doc é explícita: se você NÃO setar filtering attributes, o plug-in executa em TODA operação de update daquela tabela. Duas armadilhas documentadas: (1) 'Only include columns with changed values in update operations. If a request contains a filtering attribute, the plug-in will be triggered regardless of whether the attribute's value is changed or not' — ou seja, o filtro é sobre PRESENÇA no payload, não sobre mudança real de valor; (2) 'Don't include the primary key of the entity in the filtering attributes. The primary key is always included in update operations, so doing this negates all other filtered attributes'. Incluir a PK anula silenciosamente todo o filtro. Existe uma regra de best practice dedicada só a isso: 'Include filtering attributes with plug-in registration'.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in (campo Filtering Attributes); https://learn.microsoft.com/en-us/power-apps/developer/data-platform/best-practices/business-logic/

**Licao para a Tracbel:** COPIAR o conceito, MELHORAR a semântica. A Tracbel deve filtrar por MUDANÇA REAL DE VALOR, não por presença no payload — com EF Core isso é trivial e gratuito: `ChangeTracker.Entries<T>().Single().Properties.Where(p => p.IsModified && !Equals(p.OriginalValue, p.CurrentValue))`. O Dataverse não consegue fazer isso porque o payload chega de um web service sem estado; a Tracbel tem o ChangeTracker na mão. Isso elimina de saída a classe inteira de bugs 'meu plugin disparou mas nada mudou'. E nunca deixar o filtro vazio significar 'dispara sempre': fazer filtro vazio = erro de configuração recusado na gravação do step.

### 4. Entity Images (PreEntityImages / PostEntityImages): snapshot declarativo em vez de Retrieve

Em vez de o código fazer um `Retrieve` para saber o valor anterior de um campo, você declara na configuração do step um 'pre image' e/ou 'post image' com um ALIAS e a lista de colunas desejadas. No código, acessa-se por `context.PreEntityImages["a"]["name"]`. A Microsoft é enfática: 'Using these images provides much better performance than including code in a plug-in to retrieve a table just to compare the attribute values' e 'The default behavior when creating an entity image is to select all columns. **Don't use this default behavior.** Returning all columns negatively impact performance'. Regras de disponibilidade: não existe Pre Image em `Create` (o registro não existe); não existe Post Image em `Delete`; Post Image só existe em steps de PostOperation; em `Update` no PostOperation dá para ter ambos. Só estas mensagens suportam images: `Assign`, `Create`, `Delete`, `DeliverIncoming`, `DeliverPromote`, `Merge`, `Route`, `Send`, `SetState`, `Update`. Custom workflow activities NÃO podem configurar images (usam as chaves fixas `PreBusinessEntity` / `PostBusinessEntity`).

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in (seção 'Define entity images'); https://learn.microsoft.com/en-us/power-apps/developer/data-platform/workflow/workflow-extensions (seção 'Entity images for workflow extensions')

**Licao para a Tracbel:** DESCARTAR o mecanismo, MANTER o resultado. Entity images existem porque o plug-in do Dataverse roda num sandbox isolado sem acesso ao estado do banco — é uma prótese. A Tracbel roda em processo, com EF Core: `entry.OriginalValues` e `entry.CurrentValues` entregam pre e post image de graça, tipados, sem configuração, sem alias mágico string-based, sem a pegadinha de 'selecionei todas as colunas e derrubei a performance'. Passe ao handler um `ChangeSet<T> { T Before, T After, IReadOnlySet<string> ChangedFields }`. Essa é uma simplificação enorme e é a prova de que copiar o Dataverse literalmente seria um erro.

### 5. SharedVariables: o canal de comunicação entre estágios (e a pegadinha do ParentContext)

`IExecutionContext.SharedVariables` é um `ParameterCollection` que um handler de PreOperation usa para passar dado a um handler de PostOperation na mesma operação. Requisito: 'You must add serializable data to the shared variables collection. Otherwise, the server doesn't know how to serialize the data and plug-in execution fails.' Pegadinha documentada e não óbvia: para ler SharedVariables gravadas no estágio **PreValidation** a partir de PreOperation/PostOperation em Create/Update/Delete, é preciso acessar `context.ParentContext.SharedVariables`, não `context.SharedVariables`. Também existe a keyword `tag` (Web API e SDK) que permite ao CHAMADOR injetar uma string no SharedVariables — e uma vez setada não pode ser alterada.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/understand-the-data-context (seção 'Shared variables' e a Note sobre ParentContext)

**Licao para a Tracbel:** COPIAR o conceito, SIMPLIFICAR radicalmente. A Tracbel precisa de um `PipelineContext` scoped por requisição com um `IDictionary<string,object> Items` (ou melhor: um bag tipado com chaves fortemente tipadas, estilo `HttpContext.Features`). Como tudo roda no mesmo processo e no mesmo escopo de DI, NÃO há requisito de serialização — pode passar objeto vivo. E NÃO replicar a bifurcação ParentContext/Context: essa é uma cicatriz de arquitetura distribuída que confunde todo desenvolvedor de Dynamics. Um único contexto plano por operação. O equivalente do `tag` (dado injetado pelo cliente que chega aos handlers) é útil e barato: reservar uma chave `caller.tag` no bag.

### 6. Modos síncrono e assíncrono: assíncrono SÓ existe no PostOperation

Dois modos: **Synchronous** ('Plug-ins execute immediately according to the stage of execution and execution order. The entire operation waits until they complete') e **Asynchronous** ('The execution context and the definition of the business logic to apply is moved to the system job queue, which will execute sometime after the main operation completes'). Restrição estrutural: 'Asynchronous plug-ins can only be registered for the PostOperation stage.' Steps assíncronos rodam FORA da transação de banco, via asynchronous service (system jobs). Caso obrigatório documentado: se o plug-in faz update e está registrado no Create da tabela `SystemUser`, ele DEVE ser assíncrono (porque `UserSettings` relacionado ainda não existe quando o SystemUser é criado).

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in (seções 'Execution Mode' e 'Event Pipeline Stage of execution'); https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework (seção 'Asynchronous plug-in steps')

**Licao para a Tracbel:** COPIAR, inclusive a restrição. É um bom design: assíncrono antes da gravação não faz sentido (você não sabe se vai commitar). A Tracbel deve implementar assíncrono como **outbox transacional**: o handler AfterSave não enfileira na hora — ele grava uma linha numa tabela `crm_outbox` DENTRO da mesma transação EF Core; um `BackgroundService` (ou Hangfire/Quartz) faz polling e executa. Isso garante 'se commitou, o job existe; se rolou back, o job sumiu' — propriedade que o Dataverse tem por construção e que quase todo sistema caseiro erra ao usar `Task.Run` ou publicar em fila antes do commit. Com 130 usuários e time de 2-3 pessoas, outbox + BackgroundService no mesmo processo é suficiente; não precisa de RabbitMQ/Service Bus no dia 1.

### 7. Cancelar operação: InvalidPluginExecutionException, e o custo de cancelar no lugar errado

Para cancelar uma operação e mostrar erro ao usuário, lança-se `InvalidPluginExecutionException` — existe uma best practice dedicada ('Use InvalidPluginExecutionException in plug-ins and workflow activities'). A orientação de ONDE cancelar é explícita e é sobre custo: 'If you want to cancel the operation, detect this condition in the **PreValidation** stage', porque no PreOperation 'Avoid cancelling an operation here. Canceling will trigger a rollback of the transaction and have significant performance impact'. E o aviso global: 'An exception thrown by your code at any synchronous stage within the database transaction causes the entire transaction to roll back.' Erro correlato muito comum, com código próprio: 'Error Code: -2146893812 — ISV code reduced the open transaction count. Custom plug-ins should not catch exceptions from OrganizationService calls and continue processing' e 'Error Code: -2147220911 — There is no active transaction'. Ou seja: engolir exceção de operação de dados dentro de um plug-in síncrono QUEBRA o sistema, porque a transação já morreu.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework (bloco Important); https://learn.microsoft.com/en-us/troubleshoot/power-platform/dataverse/plug-in-execution/dataverse-plug-ins-errors (seção 'Transaction errors')

**Licao para a Tracbel:** COPIAR a disciplina, com melhor ergonomia. Ter uma exceção própria `BusinessRuleException(string mensagemParaUsuario, string codigo)` que o middleware traduz em HTTP 422 com payload amigável, distinta de exceção técnica (500). Regra de time, escrita no CLAUDE.md/AGENTS.md do repo: **validações vão em BeforeValidation, nunca em BeforeSave**, exatamente pelo mesmo motivo de custo. E a lição do '-2146893812' é ouro: em .NET 8 com EF Core, `try/catch` que engole erro dentro de uma transação deixa a transação em estado zumbi. Proibir catch genérico dentro de handlers; deixar o middleware de transação ser o único dono do rollback.

### 8. Execution Order (rank): ordem explícita, e o perigo do valor default

'Multiple steps can be registered for the same stage and message. The number in this field determines the order in which the steps are applied within a stage from lowest to highest.' E o aviso crítico: 'It's not recommended to simply accept the default value. The actual execution order of plug-ins with the same Execution Order value (for the same stage, table and message) **isn't guaranteed and can be random**.' Ou seja: empate na ordem = não-determinismo. Além disso existe a best practice 'Don't duplicate plug-in step registration' — registro duplicado faz o plug-in disparar múltiplas vezes no mesmo evento.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in (campo Execution Order); https://learn.microsoft.com/en-us/power-apps/developer/data-platform/best-practices/business-logic/do-not-duplicate-plugin-step-registration

**Licao para a Tracbel:** COPIAR a ordem, EVITAR o não-determinismo. A Tracbel deve tornar `Ordem` obrigatória e criar **índice único em (Mensagem, Entidade, Estagio, Ordem)** — empate simplesmente não é gravável. Custo: zero. Benefício: nunca ter o bug 'funciona em homologação e falha em produção porque a ordem sorteou diferente', que é um clássico documentado do Dynamics. Convenção sugerida: usar múltiplos de 10 (10, 20, 30) para permitir inserir no meio depois sem renumerar tudo.

### 9. Sandbox / isolation mode e o limite duro de 2 minutos — com recomendação de 2 SEGUNDOS

Números oficiais: 'A Dataverse message operation must complete within **2 minutes**. This limit includes executing the intended message operation and all registered synchronous and asynchronous plug-ins.' Se estourar, lança `TimeoutException` e faz rollback de toda a operação. E a recomendação real, muito mais agressiva: '**Limit the time your plug-in takes to execute to no more than 2 seconds.** If your plug-in requires more than 2 seconds to execute, consider registering your plug-in for asynchronous rather than synchronous execution. In fact, always consider asynchronous execution first when possible.' Se a extensão estoura CPU, memória ou handles, 'Dataverse kills that process' — e quando o worker morre, ele leva junto plug-ins de OUTROS que estavam rodando no mesmo processo ('This includes plug-ins that you don't own or maintain'). O sandbox bloqueia acesso a file system, event log do sistema, registry e certos protocolos de rede; só HTTP/HTTPS saem, sem loopback e sem IP literal (exige nome DNS resolvível). Para online, isolation mode é sempre **Sandbox** e location **Database**. Existe ainda um limite de payload: 'Message size exceeded when sending context to Sandbox' quando a mensagem passa de **116,85 MB**.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/analyze-performance; https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in (Note sobre isolation mode); https://learn.microsoft.com/en-us/troubleshoot/power-platform/dataverse/plug-in-execution/dataverse-plug-ins-errors (erro -2147220970, 116.85 MB)

**Licao para a Tracbel:** DESCARTAR o sandbox, COPIAR o orçamento de tempo. Sandbox de processo separado existe porque o Dataverse é multi-tenant e roda código de terceiros desconhecidos. A Tracbel roda código do próprio time em servidor próprio — isolar por processo seria pagar um custo enorme (serialização de contexto, IPC, perda de EF Core, perda de debug) sem nenhum benefício. MAS o orçamento de 2 segundos é a melhor regra de engenharia do tópico inteiro: adotar como SLO explícito, instrumentar cada handler com `Stopwatch` + `ILogger`, e logar WARNING acima de 2s. Regra dura: chamada HTTP a sistema externo (TOTVS, JDE, John Deere) NUNCA em handler síncrono — vai para o outbox. Sempre setar `HttpClient.Timeout` explícito (o Dataverse tem best practice só para isso: 'Set Timeout when making external calls in a plug-in') e `ConnectionClose = true` ('Set KeepAlive to false when interacting with external hosts in a plug-in').

### 10. Depth: proteção anti-loop infinito com máximo de 8

`IExecutionContext.Depth` — 'Gets the current depth of execution in the call stack. Used by the platform for infinite loop prevention.' Mecânica oficial: 'Every time a running plug-in or Workflow issues a message request to the Web services that triggers another plug-in or Workflow to execute, the Depth property of the execution context is increased. If the depth property increments to its maximum value within the configured time limit, the platform considers this behavior an infinite loop and further plug-in or Workflow execution is aborted.' Valores: 'The maximum depth (**8**) and time limit (**one hour**) are configurable... using the PowerShell command Set-CrmSetting. The setting is WorkflowSettings.MaxDepth' (nota: Set-CrmSetting é mecanismo on-premises; no online não há como alterar). Aviso importantíssimo da Microsoft: '**Do not take any dependency on the IExecutionContext.Depth property in your code.** Depth is used solely to manage potential infinite loops... Any business logic that depends on a specific Depth value will break.' Na prática, metade dos desenvolvedores de Dynamics usa `if (context.Depth > 1) return;` como guarda anti-recursão — e a Microsoft diz explicitamente para não fazer isso.

**Evidencia:** https://learn.microsoft.com/en-us/dotnet/api/microsoft.xrm.sdk.iexecutioncontext.depth (seção Remarks)

**Licao para a Tracbel:** COPIAR o contador, DESCARTAR o padrão de uso. Ter `PipelineContext.Depth` incrementado a cada reentrada e abortar com exceção clara acima de um limite (8 é um número razoável e testado em campo). MAS o antipadrão a evitar é o real aprendizado: se desenvolvedores precisam de `if (Depth > 1) return`, é porque a plataforma não distingue 'update feito pelo usuário' de 'update feito por um handler'. A Tracbel deve resolver isso na origem, marcando a origem da operação no contexto (`context.Origin = Origin.User | Origin.Handler | Origin.Integration | Origin.Job`) e permitindo que o registro do step declare em quais origens ele dispara. Assim ninguém precisa adivinhar profundidade. Isso é uma melhoria genuína sobre o Dynamics e custa uma coluna.

### 11. O contrato de código é minúsculo: IPlugin.Execute(IServiceProvider) e um IServiceProvider como service locator

'Any classes in an assembly that you register on an event framework (pipeline) step must implement the `IPlugin` interface. This interface exposes a single method called `Execute`.' O acesso a tudo é via service locator: `serviceProvider.GetService(typeof(IPluginExecutionContext))`, `GetService(typeof(ITracingService))`, `GetService(typeof(IOrganizationServiceFactory))` -> `CreateOrganizationService(userId)` para obter `IOrganizationService`. Configuração por step chega pelo CONSTRUTOR: dois parâmetros string (unsecure config e secure config) — 'Secure Configuration data isn't included with the step registration when you export a solution'. Evolução das interfaces de contexto (retrocompatível por herança encadeada): `IPluginExecutionContext` -> `IPluginExecutionContext2` (detalhes de portals) -> `IPluginExecutionContext3` (adiciona `AuthenticatedUserId`, separando quem autenticou de quem está sendo representado) -> `IPluginExecutionContext4` (adiciona `PreEntityImagesCollection`/`PostEntityImagesCollection` para operações em lote) -> `IPluginExecutionContext5`. Propriedades principais do `IExecutionContext`: InputParameters, OutputParameters, SharedVariables, PreEntityImages, PostEntityImages, Depth, MessageName, PrimaryEntityName, PrimaryEntityId, UserId, InitiatingUserId, BusinessUnitId, OrganizationId, CorrelationId, Mode, Stage, IsExecutingOffline, IsInTransaction.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/plug-ins; https://learn.microsoft.com/en-us/power-apps/developer/data-platform/understand-the-data-context; https://learn.microsoft.com/en-us/dotnet/api/microsoft.xrm.sdk.ipluginexecutioncontext4

**Licao para a Tracbel:** COPIAR o tamanho do contrato (essa é a razão de 'qualquer dev do time consegue estender'), DESCARTAR o service locator. Interface alvo: `public interface IStageHandler<T> { Task HandleAsync(PipelineContext<T> ctx, CancellationToken ct); }` — com dependências injetadas por CONSTRUTOR via DI nativo do .NET 8, não `GetService(typeof(...))`. O service locator do Dataverse só existe porque o assembly é carregado por reflection num sandbox sem container de DI; a Tracbel não tem essa restrição. A lição de UserId vs InitiatingUserId vs AuthenticatedUserId é ótima e deve ser copiada: o contexto precisa carregar QUEM disparou, QUEM está sendo representado e QUEM autenticou — três coisas diferentes que importam para auditoria e LGPD. E o par unsecure/secure config vira uma coluna `ConfigJson` + integração com secrets (Azure Key Vault / User Secrets), nunca segredo em texto plano na linha do step.

### 12. Impersonação por step: 'Run in User's Context'

Cada step declara em nome de qual usuário as operações dele rodam. Default = 'Calling User'. 'If the calling user doesn't have privileges to perform operations in the step, you may need to set this field value to a user who has these privileges.' Requer role System Administrator/System Customizer ou o privilégio `prvSetImpersonatingUserIdOnSdkMessageProcessingStep`. Erro correlato documentado: se o usuário configurado for desativado, toda a operação falha com 'The user with SystemUserId=<...> is disabled. Disabled users cannot access the system.' — e a doc dá até a query Web API para achar todos os steps presos a um usuário desativado.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in (seção 'Set user impersonation for a step'); https://learn.microsoft.com/en-us/troubleshoot/power-platform/dataverse/plug-in-execution/dataverse-plug-ins-errors (seção 'Error when executing in the context of a disabled user')

**Licao para a Tracbel:** COPIAR com correção do defeito. O padrão é certo — automação frequentemente precisa de privilégio que o usuário não tem — e resolve diretamente o requisito 'níveis diversos de permissão'. Mas NÃO amarrar a uma pessoa física: usar uma **service account / principal de sistema** nomeada (ex.: `sistema.pipeline`), nunca o CPF de um colaborador que um dia sai da empresa. Esse é exatamente o bug que a Tracbel já viveu no Vórtice com hierarquia presa a usuário antigo (ver memória vortice-troca-usuario-hierarquia). Modelar como `ExecutarComo: CallingUser | SystemPrincipal | SpecificPrincipal` e proibir SpecificPrincipal apontando para usuário pessoal desativável.

### 13. Empacotamento: 16 MB por assembly, .NET Framework 4.6.2, assinatura, e plugin packages

Limites duros e exatos: 'Your assembly can include multiple plug-in classes or types and even custom workflow activities, but it **can't be larger than 16 MB**.' 'Plug-in and custom workflow activity assembly projects must target .NET Framework' — o exemplo oficial de csproj usa `<TargetFramework>net462</TargetFramework>`. Sem plugin package, o assembly PRECISA ser assinado (strong name). Com plugin package (NuGet armazenado na tabela `PluginPackage`, conteúdo em file storage e não no SQL), a assinatura não é necessária, mas: workflow extensions NÃO são suportadas em packages, on-premises não é suportado, código não gerenciado não é suportado, e 'You can't change the name and version of the plug-in package (on the server) once created'. Todos os projetos devem ser 'SDK style' (`<Project Sdk="Microsoft.NET.Sdk">`). Microsoft NÃO suporta ILMerge. Performance de import: 'Import times of 15 minutes for a thousand plug-in types have been observed'. Versionamento do assembly muda o comportamento de upgrade: mudar build/revision = in-place upgrade automático; mudar major/minor = a plataforma trata como assembly DIFERENTE e os steps continuam apontando para a versão antiga (você tem que reapontar manualmente).

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/build-and-package; https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in (seção 'Assembly versioning')

**Licao para a Tracbel:** DESCARTAR inteiramente. Isso é dívida técnica de plataforma que existe só porque o Dataverse precisa hospedar binários de terceiros. Em .NET 8 monolítico os handlers são CLASSES no mesmo assembly da aplicação — sem upload, sem assinatura, sem limite de 16 MB, sem NuGet intermediário, sem semântica maluca de versão. Se algum dia a Tracbel quiser plugin de terceiro de verdade, o caminho .NET 8 é `AssemblyLoadContext` colecionável — mas NÃO fazer isso no dia 1: 130 usuários e 2-3 devs não justificam. A lição que SOBREVIVE: manter TODOS os handlers no mesmo assembly/solution (o próprio Dataverse recomenda isso na best practice 'Optimize custom assembly development': consolidar em um assembly único desde que caiba). Um assembly, muitas classes, registro em tabela.

### 14. As 14 best practices oficiais de plug-in: a lista que a Tracbel deve virar code review checklist

Lista completa e nominal da doc oficial: (1) **Don't use batch request types in plug-ins and workflow activities** — não usar `ExecuteMultipleRequest`/`ExecuteTransactionRequest` dentro de plug-in; (2) **Develop IPlugin implementations as stateless** — membros de classe expõem a problemas de thread-safety, 'Dataverse caches custom workflow activity instances... multiple system threads can execute at the same time'; (3) **Don't duplicate plug-in step registration**; (4) **Don't use parallel execution within plug-ins and workflow activities** — 'Multi or parallel threading within plug-ins or custom workflow activities isn't supported'; (5) **Implement all types of queries when filtering results using PreOperation RetrieveMultiple**; (6) **Include filtering attributes with plug-in registration**; (7) **Limit the registration of plug-ins for Retrieve and RetrieveMultiple messages** — 'Adding synchronous plug-in logic to the Retrieve and RetrieveMultiple message events can cause slowness'; (8) **Manage plug-ins in single solution**; (9) **Optimize custom assembly development**; (10) **Set KeepAlive to false when interacting with external hosts**; (11) **Set Timeout when making external calls**; (12) **Use InvalidPluginExecutionException**; (13) **Use ITracingService in plug-ins**; (14) **Verify certification dependencies for plug-ins making outbound calls**; e **Write memory efficient code** (link para o erro de memory limit do worker).

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/best-practices/business-logic/ (tabela completa)

**Licao para a Tracbel:** COPIAR quase integralmente como checklist de code review — é uma lista destilada de ~15 anos de incidentes em produção. Traduções diretas para .NET 8: (2) handlers devem ser **stateless**, registrados como Scoped ou Singleton sem campo mutável — vira regra de analyzer; (4) nada de `Task.Run`/`Parallel.ForEach` dentro de handler (quebra o `DbContext`, que não é thread-safe — mesmo problema, causa diferente); (7) NUNCA colocar handler síncrono em leitura (Query/Read) — o custo multiplica por cada linha de cada grid; (13) `ILogger` com scope de CorrelationId em todo handler, obrigatório; (10)+(11) `IHttpClientFactory` com timeout e Polly configurados por named client. O item (1) — proibir batch dentro de handler — traduz para: proibir `SaveChanges()` dentro de handler; quem commita é o middleware de transação, uma vez só.

### 15. Custom Workflow Activities: a segunda via, hoje legado

Assemblies que herdam de `System.Activities.CodeActivity` (Windows Workflow Foundation) e implementam `Execute(CodeActivityContext)`. Parâmetros são propriedades tipadas `InArgument<T>` / `OutArgument<T>` / `InOutArgument<T>` decoradas com atributos .NET: `[Input("...")]`, `[Output("...")]`, `[RequiredArgument]`, `[Default("...")]`, `[ReferenceTarget("account")]`, `[AttributeTarget("account","industrycode")]`. Tipos suportados: bool, DateTime, Decimal, Double, EntityReference, int, Money, OptionSetValue, string. Diferenças-chave contra plug-in: NÃO se registra step (só o assembly); você NÃO controla se roda sync ou async (quem decide é o workflow que o usa); NÃO dá para configurar entity images. Mesma regra dos 2 segundos: 'workflow extensions should require no more than two seconds to complete when used synchronously'. A doc abre com: 'Whenever possible, first consider applying one of the several declarative options... Use workflow extensions when a declarative process doesn't meet your requirement.' Estágios em que rodam num real-time workflow: Create->PostOperation, Delete->PreOperation, Update->PreOperation ou PostOperation.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/workflow/workflow-extensions

**Licao para a Tracbel:** DESCARTAR o mecanismo, COPIAR a ideia de 'ação reutilizável parametrizada'. Custom workflow activities são plug-ins piorados: sem controle de estágio, sem controle de modo, sem images, presos a WWF (tecnologia que a própria Microsoft não evoluiu). A ideia boa e barata de aproveitar: **declarar os parâmetros da ação com metadados para que a UI monte o formulário sozinha**. Em .NET 8: uma classe `[AcaoCrm("AprovarDesconto")] public record AprovarDescontoParams { [Rotulo("Percentual")][Obrigatorio] public decimal Percentual {get;init;} }` e um endpoint que devolve o schema (ou JSON Schema puro) para o front React montar o form. Isso entrega 'fluxos interativos' e 'extensibilidade' sem inventar uma engine de workflow. NÃO adotar Windows Workflow Foundation nem nenhum sucessor: não existe versão viva disso em .NET 8.

### 16. Custom API: a forma moderna de criar uma mensagem própria (e o modelo de governança de extensão)

Custom API cria uma NOVA mensagem em Dataverse, chamável por Web API, SDK .NET e Power Automate. É a alternativa moderna às Custom Process Actions. Propriedades que definem o contrato (tabela `CustomAPI`): **AllowedCustomProcessingStepType** com 3 valores — `None` (ninguém pode registrar step: 'Use this option when the custom API provides some capability that shouldn't be customizable'), `Async Only` (terceiros só observam, não cancelam nem mudam — 'recommended if you're using the business events pattern'), `Sync and Async` (terceiros podem alterar e até cancelar); **BindingType** — `Global`, `Entity` (cria automaticamente um parâmetro `Target` do tipo EntityReference), `EntityCollection`; **IsFunction** (GET, deve retornar dado, limite de **32 KB / 32.768 caracteres** de URL) vs Action (POST, parâmetros no corpo — e a doc recomenda Action para evitar o inferno de escapar `/ < > * % & : \ ? +` na URL); **IsPrivate** (some do $metadata e dos geradores de código — e 'If you define your custom API as private, you can't use that message in a plug-in'); **ExecutePrivilegeName** (exige um privilégio para executar — mas 'there's currently no supported way for developers outside of Microsoft to create new privileges'; workaround: criar uma tabela custom só para ganhar o privilégio `prvCreatenew_myaction`); **PluginTypeId** (o plug-in que implementa a MainOperation — e não aceita secure/unsecure config); **WorkflowSdkStepEnabled** (habilita uso em workflow, mas então não pode ser Function e só aceita tipos Boolean, DateTime, Decimal, EntityReference, Float, Integer, Money, Picklist, String, Guid). Recomendação de ALM: 'When you ship or deploy your solution, use a managed solution and always set the **Is Customizable** managed property to false for these components.'

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/custom-api

**Licao para a Tracbel:** COPIAR o modelo de governança — é o achado mais subestimado do tópico. A ideia central: **quem publica uma operação declara EXPLICITAMENTE quanto de extensão ela aceita**. Traduzido para a Tracbel: cada comando/mensagem do CRM carrega um atributo `[Extensivel(Extensibilidade.Nenhuma | Extensibilidade.SomenteObservacao | Extensibilidade.Total)]`. Operações sensíveis (aprovação de desconto, fechamento de pedido, integração fiscal) = `Nenhuma` ou `SomenteObservacao`, e o registro de step nelas é RECUSADO pela validação. Isso resolve o requisito 'segurança alta' + 'extensibilidade' que normalmente brigam entre si. Também COPIAR: `IsPrivate` (mensagem interna que não vira API pública — versionar API pública é caro, então o default deve ser privado) e `ExecutePrivilegeName` (autorização a nível de mensagem, não só de tabela — em .NET 8 é uma policy do ASP.NET Core, trivial). DESCARTAR: a separação Function/Action com limite de 32 KB de URL; em .NET 8 padronize POST com corpo JSON para tudo que não seja consulta trivial.

### 17. Business Rules: a automação declarativa que roda no cliente E no servidor — com teto de 150 por tabela

Business rules aplicam lógica sem código. Escopo determina onde rodam: **Entity** = 'Model-driven app forms and server' (gera plug-in síncrono via XAML no servidor); **All Forms** = só forms; **form específico** = só aquele form. Ações disponíveis em qualquer escopo: definir valor de coluna, limpar valor, definir default, validar dados e mostrar mensagem de erro. Ações SÓ de escopo form: definir nível de obrigatoriedade, mostrar/ocultar colunas, habilitar/desabilitar colunas, recomendações de negócio. Limite numérico oficial e explícito: 'Power Platform today supports up to **150 business rules for a single table**. Beyond 150 business rules, performance degradation can be experienced. **This limit includes both client side (JavaScript) and server side (XAML generated as synchronous plugins) business rules.**' Não funcionam com colunas do tipo Choices (multi-select), File e Language. Não funcionam em subgrids editáveis. FAQ revelador: 'When I update a business rule, is it executed against all existing records? **No.** Business rules are run on clients... They aren't executed inside Dataverse.' — o que contradiz parcialmente o escopo 'Entity' e é fonte histórica de confusão. Atributos compostos (ex.: `fullname`) não são suportados em Unified Interface.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/maker/data-platform/data-platform-create-business-rule (seção 'A large number of business rules on a single table impacts performance')

**Licao para a Tracbel:** COPIAR a IDEIA (validação declarativa que roda nos dois lados), DESCARTAR a implementação. A ideia poderosa: **uma regra escrita uma vez, executada no React (feedback instantâneo) e no .NET (garantia real)**. Em .NET 8 + React o caminho barato é: definir a regra como dado (JSON: campo, operador, valor, ação, mensagem), gerar validação server-side com FluentValidation e servir o MESMO JSON para o front interpretar. Nunca duplicar a regra em duas linguagens — isso é a origem do drift 'a tela deixou passar e o servidor recusou'. DESCARTAR a geração de XAML->plugin síncrono (era a única saída da Microsoft e virou o teto de 150). Mas ADOTAR um teto explícito e monitorado: se a Microsoft, com engenharia dedicada, degrada em 150 regras por tabela, a Tracbel deve alarmar bem antes disso. E documentar que regras de UI (mostrar/ocultar/habilitar) são SEMPRE só cosméticas — nunca podem ser a única barreira de segurança.

### 18. Business Process Flows: limites numéricos duros e um modelo de dados próprio

Limites oficiais e exatos: 'A process can span a maximum of **five unique tables**'; 'Use a maximum of **30 stages per process and 30 steps per stage**'; 'Each branch can be no more than **10 levels deep**'; 'Multiple active processes can run concurrently on the same record'; descrição do processo até **2.000 caracteres**. Regras estruturais: condições de branch combinam AND ou OR mas NUNCA os dois na mesma regra; relacionamento entre stages de tabelas diferentes deve ser 1:N; ao mergear branches, todos os branches irmãos devem convergir para um único stage (ou terminar), nunca ambos. Cada BPF tem tabela própria e privilégios próprios via 'Enable Security Roles' — 'By default, only the System Administrator and System Customizer security roles can view a new business process flow', e dá para dar full access a um perfil e read-only a outro. Um campo booleano marcado como Required num step só deixa avançar se o valor for **Yes** (a doc recomenda usar choice em vez de boolean quando ambos os valores são aceitáveis). Action Steps (executar ação/workflow sob demanda a partir do BPF) não aceitam parâmetros dos tipos Table, EntityCollection, OptionSet, nem ações globais. Os atributos legados `StageId`, `TraversedPath` e a action `SetProcess` estão DEPRECIADOS. BPF não funciona com virtual tables (erro 0x80040216).

**Evidencia:** https://learn.microsoft.com/en-us/power-automate/create-business-process-flow (seção 'Design business process flows with branches'); https://learn.microsoft.com/en-us/power-platform/important-changes-coming (StageId/TraversedPath/SetProcess deprecated); https://learn.microsoft.com/en-us/power-apps/maker/data-platform/create-edit-virtual-entities

**Licao para a Tracbel:** COPIAR o conceito com escopo MUITO menor — e este é o item de maior retorno para 'fluxos interativos' e 'usabilidade para usuário final'. O que vale ouro: a barra de estágios no topo do formulário guiando o vendedor pelo funil (Qualificar -> Proposta -> Negociação -> Fechamento), com campos obrigatórios por estágio e **segurança por perfil no próprio fluxo**. Isso mapeia direto no processo de venda de máquinas da Tracbel. Modelo mínimo: `crm_fluxo(Id, Nome, Entidade, Ativo)`, `crm_fluxo_estagio(FluxoId, Ordem, Nome, Categoria)`, `crm_fluxo_passo(EstagioId, Ordem, Campo, Obrigatorio)`, `crm_fluxo_instancia(RegistroId, FluxoId, EstagioAtualId, IniciadoEm)`. DESCARTAR de saída: branching com 10 níveis, processos cruzando 5 tabelas, e múltiplos fluxos concorrentes no mesmo registro — são exatamente as features que tornam BPF impossível de manter e depurar. Regra: 1 fluxo ativo por registro, linear, sem branch no v1. Se um dia precisar de branch, 1 nível. Copiar SIM o limite de 30 estágios como sanity check (na prática nenhum fluxo de venda saudável passa de 7).

### 19. Real-time (classic) workflows: a própria Microsoft diz para não usar mais

A doc oficial de real-time workflows abre a seção de criação com um bloco **Important**: 'There are better ways to create modern automations. **Consider using Power Automate flows to automate your processes.**' São dois tipos: background workflows (assíncronos, 'run when the system has resource availability') e real-time workflows (síncronos, rodam imediatamente). Real-time workflows são a via declarativa que participa da transação: 'Custom actions are always synchronous, but they don't participate in a database transaction unless you set **Enable rollback**' e 'any error thrown by your workflow extension causes the entire transaction to roll back. This rollback is an expensive operation'. O mecanismo é tão entrelaçado com o pipeline que o comportamento de Update duplicado (ver achado seguinte) afeta workflows do mesmo jeito que plug-ins. Dialogs (Process Dialogs) foram DEPRECIADOS com remoção em **1 de dezembro de 2020**, substituídos por BPF ou canvas apps; Task Flows removidos em **1 de outubro de 2021**.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/maker/data-platform/overview-realtime-workflows (bloco Important); https://learn.microsoft.com/en-us/power-platform/important-changes-coming (Process Dialogs, Task Flows)

**Licao para a Tracbel:** DESCARTAR o mecanismo, ABSORVER a lição estratégica — que é a mais importante de todo o tópico. O Dataverse acumulou SEIS mecanismos concorrentes para 'aplicar lógica de negócio': business rules, real-time workflows, background workflows, BPF, Power Automate cloud flows, plug-ins (mais low-code plug-ins em preview). O resultado é que ninguém sabe onde uma regra mora, o comportamento depende de qual mecanismo ganhou, e a Microsoft passou anos depreciando os próprios mecanismos (dialogs, task flows, custom actions -> custom API, workflows -> Power Automate). Um time de 2-3 pessoas NÃO pode se dar a esse luxo. **Decisão de arquitetura para a Tracbel: UM mecanismo de automação — o pipeline de handlers em C# — mais UM mecanismo declarativo estreito (validação por dado, estilo business rule).** Ponto final. Se alguém propuser 'e se a gente também tivesse um motor de regras / BPMN / scripts?', a resposta documentada é este achado. O Vórtice já sofre desse mal (regra que só existe na tela, resultado 3438 que muda fase/status por efeito colateral, ação 897 com limite vitalício invisível).

### 20. A pegadinha do Update que dispara duas vezes (owner fields e state/status)

Comportamento documentado e contraintuitivo: 'When update requests are processed that include both owner fields plus other standard fields for business owned tables, plug-ins registered for the **Update** message in PreOperation and/or PostOperation stages execute **once for all non-owner fields, and then once for the owner fields**.' O mesmo vale para state/status: 'execute once for all non-state/status fields, and then once for the state/status fields'. Isso é resquício das mensagens depreciadas `AssignRequest`, `SetStateRequest`, `SetParentSystemUserRequest`, `SetParentTeamRequest`, `SetParentBusinessUnitRequest`, `SetBusinessEquipmentRequest`, `SetBusinessSystemUserRequest`, que hoje devem ser feitas com `Update` normal. Workaround oficial: 'In order for plug-in code to receive the full data changes of the update, you must register the plug-in in the PreOperation and then store relevant information in SharedVariables'. Aviso relacionado: ao atualizar `StateCode` sempre setar `StatusCode` explicitamente, senão o sistema aplica o `DefaultStatus` — e a auditoria não captura a mudança de StatusCode se ela não estiver no update.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/special-update-operation-behavior

**Licao para a Tracbel:** EVITAR ativamente — é um caso clássico de 'compatibilidade retroativa vira bug permanente'. Um evento de negócio deve disparar UMA vez com o conjunto COMPLETO de mudanças. Regra de desenho para a Tracbel: o `ChangeSet` entregue ao handler contém TODOS os campos alterados na operação, sem partição por categoria de campo, e o handler roda exatamente uma vez. Nunca criar 'mensagens especializadas' (Atribuir, MudarStatus) que rodem em paralelo à mensagem genérica de Update — se quiser semântica de negócio ('Pedido foi aprovado'), emita um EVENTO DE DOMÍNIO derivado (`PedidoAprovado`) a partir do AfterSave, não uma segunda passada pelo pipeline. Isso mata a categoria inteira de bug. Nota direta para o Vórtice: o comportamento de 'Atividade Cancelada' que grava Fase=Finalizado/Status=CANCELADO por efeito colateral (memória vortice-atividade-cancelada) é o mesmo antipadrão — efeito de negócio escondido dentro de uma mudança de campo.

### 21. Power Fx: linguagem declarativa estilo Excel — e o que ela explicitamente NÃO é

Power Fx é 'a general-purpose, strongly typed, declarative, and functional programming language', expressa em texto amigável numa barra de fórmulas estilo Excel. Princípios de design nominais: **Simple**, **Excel consistency** ('If Excel doesn't have an answer, Power Fx next looks to SQL'), **Declarative** ('The maker describes *what* they want their logic to do, not exactly *how* or *when*'), **Functional** ('Use pure functions that don't have side effects'), **Composition**, **Strongly typed** ('The types of all values are known at compile time'), **Type inference**, **Locale-sensitive decimal separators** (em locale com vírgula decimal, o separador de lista vira `;` e o operador de encadeamento vira `;;` — impacto direto no Brasil), **Not object-oriented** ('Excel isn't object-oriented, and neither is Power Fx... prefer a functional approach' — `Len("Hello")` e não `"Hello".length`), **Extensible**, **Language evolution** (cada documento carrega um carimbo de versão e a Microsoft escreve 'back compat converters' que reescrevem a fórmula automaticamente), **No undefined value** ('all uninitialized variables start with a blank value'). O modelo mental é planilha: 'force = mass * acceleration' se recalcula sozinho, sem handler OnChange. O que ele faz por baixo sem o maker saber: assíncrono automático, delegação para o servidor, projeção automática de colunas, paginação (~100 registros por página), tradução de display name para logical name.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/power-fx/overview

**Licao para a Tracbel:** DESCARTAR como linguagem, COPIAR duas ideias específicas. (1) **'Not object-oriented' é um alerta direto contra o requisito declarado de 'OO forte'**: a Microsoft escolheu deliberadamente NÃO ser OO na camada que o usuário final toca, porque OO exige entender objetos, métodos e estado. A Tracbel deve manter OO forte no núcleo (.NET 8, domínio rico) e oferecer na borda configurável algo simples e sem estado — não expor classes a quem configura. (2) **'Locale-sensitive decimal separators'** é uma armadilha real para o Brasil: se a Tracbel um dia oferecer expressões configuráveis, fixar cultura invariante para PARSING (ponto decimal, vírgula separadora) e formatar em pt-BR só na exibição. Nunca deixar o separador depender do locale do usuário — a Microsoft fez isso e criou fórmulas que não copiam entre máquinas. (3) DESCARTAR a ideia de embutir um motor de expressões no v1: strongly typed + type inference + delegação + incremental compiler é anos de engenharia. Se um dia precisar, avaliar a biblioteca open source `microsoft/power-fx` no NuGet em vez de escrever a sua.

### 22. Low-code plug-ins (Power Fx no servidor): o estado do experimento, e o que já foi abandonado

Low-code plug-ins são 'reusable, real-time workflows... They run server-side and trigger by personalized event handlers', definidos em Power Fx dentro do Dataverse Accelerator app, sem compilar nem registrar assembly. Dois tipos: **Instant** (disparo manual, aceita parâmetros de entrada e saída dos tipos Boolean, String, Float, Decimal, DateTime, Integer; escopo Global ou table) e **Automated** (dispara em Create/Update/Delete, sem parâmetros, escopo table, com estágio Pre-operation ou Post operation). ESTADO ATUAL, e isso é decisivo: 'This is a **preview** feature' e '**Instant low-code plug-ins are deprioritized and aren't being delivered as a feature.** Instant low-code plug-ins are replaced with functions.' Limitações declaradas: só podem chamar first-party actions publicadas pela Microsoft; sintaxe de desambiguação obrigatória `[@Accounts]` em plug-ins automated; `Collect()` às vezes não funciona e exige `Patch()`; plug-ins com conectores só conseguem devolver campos primitivos específicos; não usar o conector Dataverse para falar com Dataverse (usar as funções nativas Filter/LookUp/Patch/Collect/Set). Existe um setting de organização `Allowconnectorsonpowerfxactions` para bloquear conectores globalmente.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/maker/data-platform/low-code-plug-ins (bloco Important e seção Limitations)

**Licao para a Tracbel:** DESCARTAR — e usar como evidência em decisão de arquitetura. A Microsoft, com recursos praticamente ilimitados, tentou colocar uma linguagem low-code no pipeline de eventos do servidor, ficou anos em preview e **despriorizou metade da feature**. Isso é a resposta empírica para 'e se a Tracbel deixasse o usuário-chave escrever fórmulas que rodam no servidor?'. Não faça. O caminho correto para 'extensibilidade sem release' com time de 2-3 pessoas é **configuração de dados** (ligar/desligar/reordenar/parametrizar handlers pré-escritos), não **código em runtime**. Configuração é testável, versionável, auditável e não abre superfície de ataque; expressão arbitrária no servidor é RCE com passos extras. O que vale ABSORVER: a lista de benefícios de lógica server-side que a doc enumera — segurança (o cliente não consegue burlar), performance, consistência entre todos os clientes, manutenção centralizada, escalabilidade. Esses cinco pontos justificam por que a lógica de negócio da Tracbel deve viver no .NET e não no React.

### 23. Web API (OData v4) e Organization Service: a API é uma projeção do mesmo pipeline

Insight arquitetural explícito na doc: 'It's valuable to recognize that the *organization service* is what defines the platform. The Web API provides a RESTful programming experience but **ultimately all data operations go through the underlying organization service**. The organization service defines the supported operations as messages. Each message has a name. **These names are bound to the events used in the event framework** to evaluate what registered extensions should be initiated.' A Web API implementa OData v4 (padrão OASIS), endpoint `[Organization URI]/api/data/v9.2/`. Operações CRUD viram GET/POST/PATCH/DELETE; as demais mensagens viram Functions (GET, sem efeito colateral) ou Actions (POST). Por ser padrão aberto, 'Microsoft doesn't provide assemblies or libraries for a specific developer experience' (exceto o Python SDK). O SDK .NET (`Microsoft.Xrm.Sdk`) usa `IOrganizationService` com `Create/Retrieve/RetrieveMultiple/Update/Delete/Associate/Disassociate/Execute`, onde tudo é fundamentalmente `Execute(OrganizationRequest)` — `InputParameters` do contexto É o `OrganizationRequest.Parameters`, e `OutputParameters` É o `OrganizationResponse.Results`. Classes recomendadas hoje: `Microsoft.PowerPlatform.Dataverse.Client.ServiceClient` (a antiga `OrganizationServiceProxy` está depreciada; autenticação Office365/WS-Trust foi retirada em abril de 2022; OData v2.0 depreciado, remoção adiada sem data).

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/overview (seção 'Web API and the Organization service'); https://learn.microsoft.com/en-us/power-apps/developer/data-platform/understand-the-data-context; https://learn.microsoft.com/en-us/power-platform/important-changes-coming

**Licao para a Tracbel:** COPIAR — este é o segredo estrutural que faz o Dataverse funcionar e é BARATO de replicar. **Uma única porta de entrada para toda mutação de dados**, e a API REST é só um adaptador HTTP sobre ela. Consequência prática: se o CRM da Tracbel expõe endpoint REST, importador CSV, integração TOTVS/JDE e tela React, TODOS passam pelo mesmo `IMessageDispatcher.Execute(request)` e portanto pelo mesmo pipeline — regra de negócio nunca é burlada por 'entrou por outro caminho'. Isso resolve de uma vez os requisitos 'APIs para integração' + 'segurança alta' + 'níveis de permissão'. Implementação em .NET 8: um mediator (MediatR ou 30 linhas próprias) com `IRequest`/`IRequestHandler`, e os controllers/minimal APIs apenas traduzindo HTTP -> comando. NÃO expor `DbContext` nem repositório direto ao controller — essa é a única regra que precisa ser inegociável no code review, porque é ela que sustenta todo o resto. DESCARTAR OData v4 como protocolo público: é pesado, o `$expand`/`$filter` arbitrário vira superfície de DoS e vazamento, e ninguém no time vai dominar. Endpoints REST explícitos + um endpoint de query com contrato fechado.

### 24. Service protection limits: os números que definem quando a integração quebra

Três facetas avaliadas POR USUÁRIO em janela deslizante de 5 minutos (300 segundos), POR WEB SERVER: (1) **Número de requisições: 6.000** na janela de 300s — erro `-2147015902` / `0x80072322`: 'Number of requests exceeded the limit of 6000 over time window of 300 seconds'; (2) **Tempo de execução combinado: 20 minutos (1.200 segundos / 1.200.000 ms)** na janela de 300s — erro `-2147015903` / `0x80072321`; (3) **Requisições concorrentes: 52 ou mais** — erro `-2147015898` / `0x80072326`, e este 'returns an error immediately'. Na Web API o erro é HTTP **429 Too Many Requests** com header `Retry-After` em segundos; no SDK vem um `TimeSpan` em `OrganizationServiceFault.ErrorDetails["Retry-After"]`. Headers de telemetria: `x-ms-ratelimit-burst-remaining-xrm-requests` e `x-ms-ratelimit-time-remaining-xrm-requests` ('Don't depend on these values... They're intended for debugging purposes'). ISENÇÃO CRUCIAL: 'Service protection limits **don't apply to data operations that originate from plug-ins and custom workflow activities**... Dataverse operations invoked on the sandbox service don't use the public API endpoints. However, the extra computation time that these operations contribute is added to the initial request that triggered them.' Orientação anti-intuitiva sobre batching: 'Most scenarios are fastest sending single requests with a high degree of parallelism'; se usar batch, 'start with a small batch size of 10'; `ExecuteMultipleRequest` aceita até 1.000 operações mas 'Larger sized batches increase the chance you encounter execution time limits'. Dataverse Search tem regra própria: 'a throttling limit of one request per second for each user' no endpoint `api/search`.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/api-limits (tabela de limites e seção de erros)

**Licao para a Tracbel:** COPIAR o conceito, calibrar para a realidade. Com ~130 usuários num servidor próprio, a Tracbel não precisa de throttling agressivo no dia 1 — MAS precisa dele antes da primeira integração automatizada (TOTVS/JDE/portal) entrar em produção, porque é exatamente aí que um loop mal escrito derruba o CRM para os 130 vendedores. Implementação barata em .NET 8: `RateLimiter` nativo (`System.Threading.RateLimiting`, já no framework) com particionamento por usuário/aplicação, devolvendo **429 + Retry-After** — usar o mesmo contrato HTTP do Dataverse, que é padrão e todo cliente entende. COPIAR também as três facetas (contagem, tempo acumulado, concorrência): limitar só contagem é ingênuo, porque uma query pesada de relatório consome mais que 100 leituras simples. E COPIAR a isenção: operações originadas dentro do pipeline não contam para o limite do usuário — senão um handler bem-comportado derruba o próprio usuário que disparou a ação. Do lado cliente, a lição é literal: implementar retry com Polly respeitando `Retry-After` (a doc oficial dá o código com `HttpPolicyExtensions.HandleTransientHttpError().OrResult(r => r.StatusCode == TooManyRequests)`).

### 25. FetchXML: limites de paginação e o teto duro de 50.000 em agregação

FetchXML é a linguagem de query XML proprietária do Dataverse, usada tanto em código quanto para definir views de model-driven apps (tabela `savedquery`) e relatórios. Limites exatos: sem o atributo `top`, 'Dataverse returns up to **5.000 standard table rows** and **500 elastic table rows**'; `top` e paginação são mutuamente exclusivos; `top` não pode ser usado com `returntotalrecordcount`. Se usar `distinct`, é obrigatório pelo menos um elemento `order` para paginação consistente, e o resultado não traz as chaves primárias. **Agregação tem teto duro de 50.000 registros**: 'Queries that return aggregate values are limited to **50.000 records**' — erro `-2147164125` / `8004E023` / 'AggregateQueryRecordLimit exceeded. Cannot perform this operation.' A saída oficial é primitiva: 'add appropriate filters... Then run your query multiple times and combine the results'. Existe o atributo `aggregatelimit` para impor um teto menor por query, e nesse caso não há erro — a query agrega sobre no máximo `limit + 1` linhas ARBITRÁRIAS (resultado silenciosamente errado, mas sem exceção). Funções de agregação: avg, count, countcolumn (com `distinct`), max, min, sum; agrupamento por `groupby` com `dategrouping` em day/week/month/quarter/year/fiscal-period/fiscal-year e `usertimezone`.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/fetchxml/overview; https://learn.microsoft.com/en-us/power-apps/developer/data-platform/fetchxml/aggregate-data (seção 'Aggregate query record limit error')

**Licao para a Tracbel:** DESCARTAR FetchXML, COPIAR os limites como política. Inventar uma linguagem de query XML própria em 2026 seria um erro grave — a Tracbel tem SQL Server, EF Core e LINQ. Mas os limites são sabedoria operacional pura: (1) **toda listagem paginada com teto máximo** (sugestão: 5.000 é generoso demais para tela; usar 100 default / 1.000 máximo, com o `top` recusado acima disso) — nunca deixar um endpoint devolver 'todos'; (2) **agregação e relatório NÃO vão pelo caminho transacional**: se o Dataverse, com engenharia dedicada, para em 50.000 registros de agregação, a Tracbel deve mandar relatório pesado para réplica de leitura / view materializada / SQL dedicado desde o dia 1. O caso do relatório TBA_101XX3 do Vórtice (relatório externo com staging IMP_REL_TBA101) mostra que a Tracbel já vive esse problema. (3) COPIAR o `dategrouping` com noção de ano fiscal — a Tracbel é revenda John Deere e trabalha com FY; agrupar por ano fiscal precisa ser primitiva do sistema, não gambiarra por relatório.

### 26. Virtual Tables: dado externo aparecendo como tabela nativa — e a longa lista do que se perde

Virtual table é 'a custom table in Dataverse that has columns containing data from an external data source... you connect directly with an external data source at runtime... without the need for data replication'. Três componentes: um **data provider** (plug-ins registrados no estágio MainOperation), uma linha de **data source** e a **virtual table**. Provedores prontos: OData v4 Data Provider e virtual connector providers (SQL Server, SharePoint, Fabric). A coluna de conexão sensível pode ser marcada com o atributo **Data Source Secret**. A lista de restrições é enorme e define o teto da abstração: tabelas existentes NÃO podem ser convertidas em virtuais; por padrão só têm Name e Id (sem Status, Created On, Modified On); não suportam colunas Currency, Image ou Customer; **sem auditoria**; colunas não podem entrar em rollup nem calculated column; não podem ser tabela de atividade; sem dashboards e charts; sem queues, knowledge management, SLAs, detecção de duplicidade, **change tracking**, mobile offline, column security, Dataverse search, Power Pages; **são organization-owned e não suportam segurança em nível de linha** ('We recommend that you implement your own security model for the external data source'); validações de metadado (ex.: valor mínimo) NÃO são aplicadas; **não suportam business process flows** (erro 0x80040216); não podem ser sincronizadas por Data Export Service ou Azure Synapse Link; o provider OData usa porta de saída 443.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/maker/data-platform/create-edit-virtual-entities (seção 'Considerations when you use virtual tables')

**Licao para a Tracbel:** AVALIAR com muito cuidado — tentador e perigoso, e diretamente relevante para a migração gradual do Vórtice. A tentação: durante a coexistência CRM novo + Vórtice, expor tabelas do banco legado (`IVS_Pes`, `IV_VENDEDOR`, `IVS_Carteira`) como se fossem tabelas do CRM novo, sem migrar dado. A lição da Microsoft é que a abstração VAZA em ~15 lugares diferentes, e os dois que mais doem para a Tracbel são: **sem segurança em nível de linha** (fatal para carteirização por vendedor/CEN, que é o coração do modelo) e **sem auditoria** (fatal para LGPD e para rastrear quem mexeu no cliente). Recomendação: usar leitura virtual APENAS para dados de referência não sensíveis e read-only (catálogo de máquinas, tabela de peças, títulos financeiros para consulta), NUNCA para clientes/pessoas/oportunidades. Para essas, migrar de verdade com sincronização explícita e reconciliação. E COPIAR uma coisa boa: marcar coluna de credencial como 'segredo' no modelo de dados (nunca retornada em query, nunca logada) — é barato e resolve um risco real.

### 27. Change Tracking: sincronização incremental com delta token — e a janela de 7 dias

Change tracking permite 'detecting what data changed since the data was initially extracted or last synchronized'. Habilita-se por tabela (`EntityMetadata.ChangeTrackingEnabled = true`) e **não pode ser desabilitado depois**. Nem toda tabela é elegível (checar `EntityMetadata.CanChangeTrackingBeEnabled`). Dois caminhos: Web API com header `Prefer: odata.track-changes`, que devolve `@odata.deltaLink` com `$deltatoken`, e o SDK com a mensagem `RetrieveEntityChanges` (`RetrieveEntityChangesRequest`, com `PageInfo.Count = 5000`, `PagingCookie`, e `EntityChanges.DataToken` guardado para a próxima chamada). Registros deletados voltam com `"reason": "deleted"`. Restrições numéricas e comportamentais: 'Changes are returned if the last token is within a default value of **seven days**. The value of the Organization table **ExpireChangeTrackingInDays** column controls this duration and can be changed. If unprocessed changes are older than the configured value, the system throws an exception' — ou seja, integração parada por mais de 7 dias exige RESYNC COMPLETO; só é possível rastrear UMA tabela por chamada; a ordem é 'novos/atualizados primeiro (por número de versão), depois deletados'; acima de 5.000 é preciso paginar; 'The calling user must have **organization level read access** to the table' (acesso limitado lança erro de privilégio); e no Web API os query options `$filter`, `$orderby`, `$expand` e `$top` NÃO são suportados junto com `Prefer: odata.track-changes`.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/use-change-tracking-synchronize-data-external-systems

**Licao para a Tracbel:** COPIAR o padrão, com a implementação MUITO mais simples que a Tracbel já tem à mão. O SQL Server nativo oferece Change Tracking e Change Data Capture prontos — não precisa inventar delta token. Alternativa ainda mais simples e portável: coluna `RowVersion` (`rowversion`/`timestamp` do SQL Server, mapeada no EF Core como concurrency token) + uma tabela `crm_delecao(Entidade, RegistroId, DeletadoEm)` para capturar deleções, que é justamente o que qualquer esquema ingênuo esquece. As lições de operação a copiar são as valiosas: (1) **definir e DOCUMENTAR a janela de retenção** e falhar alto e claro quando o token expira, em vez de devolver dado silenciosamente incompleto (7 dias é um bom default); (2) **deleção precisa ser rastreável** — se a Tracbel usar soft delete, isso sai de graça, e é mais uma razão para adotar soft delete no modelo; (3) sincronização exige leitura em nível de organização, o que significa que a integração roda com um principal de sistema e NÃO com o usuário logado.

### 28. Webhooks vs Azure Service Bus: o quadro comparativo oficial e os limites de payload

Comparação literal da doc: 'Azure Service Bus works for high scale processing, and provides a full queuing mechanism if Dataverse is pushing many events. Webhooks can only scale to the point at which your hosted web service can handle the messages. **Webhooks enable synchronous and asynchronous steps. Azure Service Bus only allows for asynchronous steps.** Webhooks send POST requests with JSON payload and can be consumed by any programming language... Both can be invoked from a plug-in or custom workflow activity.' Webhooks: autenticação por **HttpHeader**, **WebhookKey** ou **HttpQueryString** ('This approach is simpler than the SAS authentication model that you might currently use for Azure Service Bus integration'). Headers enviados: `x-ms-dynamics-organization`, `x-ms-dynamics-entity-name`, `x-ms-dynamics-request-name`, `x-ms-correlation-request-id` ('The platform uses this property for infinite loop prevention') e `x-ms-dynamics-msg-size-exceeded`. Corpo = JSON do `RemoteExecutionContext`. **Timeout de 60 segundos**; só respostas `2xx` contam como sucesso; 'The system can't parse any data returned with the body of the response. It only looks at the response StatusCode value'; **retry único e SÓ** para `502`, `503`, `504`. **Payload acima de 256 KB** faz a plataforma REMOVER `ParentContext`, `InputParameters`, `PreEntityImages` e `PostEntityImages` (e sinalizar via header). Azure Service Bus: mesmo corte, mas em **192 KB**, adicionando a propriedade `MessageMaxSizeExceeded` no `BrokeredMessage`; se ainda passar de 192 KB depois do corte, a mensagem NÃO é enviada. Contratos de endpoint: Queue (com persistent queue), One-way (exige listener ativo, senão falha e reenvia em intervalos exponenciais até abortar), Two-way (devolve string), REST, Topic (múltiplos assinantes), Event Hubs. Formato: binário .NET, XML ou JSON. Aviso crítico para webhook síncrono: 'When you register a webhook for a synchronous step, it sends the execution context data to the configured endpoint immediately. **If an error occurs after the request is sent, the data operation rolls back but the request sent to the configured endpoint can't be recalled.**'

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/use-webhooks; https://learn.microsoft.com/en-us/power-apps/developer/data-platform/azure-integration

**Licao para a Tracbel:** COPIAR webhooks (simples, universais, resolvem 'APIs para integração'), DESCARTAR Service Bus no v1. Desenho recomendado: tabela `crm_webhook(Id, Url, TipoAuth, SegredoRef, Ativo)` + steps que apontam para ela, entregando POST JSON com o mesmo envelope do pipeline. COPIAR literalmente: timeout curto e explícito (60s é generoso; 10-30s basta), aceitar só 2xx, ignorar o corpo da resposta, e retry APENAS em erros que indicam problema de rede (502/503/504 + timeout) — nunca em 4xx, que é erro do consumidor e vai falhar de novo para sempre. COPIAR o header de correlação para prevenção de loop. E o aviso do webhook SÍNCRONO é a lição de ouro, porque é o erro que quase todo mundo comete: **notificação externa dentro da transação é irreversível se a transação rolar back** — você avisou o mundo de um pedido que não existe. Por isso, na Tracbel, webhook SEMPRE assíncrono, sempre via outbox pós-commit. Sem exceção. O corte de payload (256 KB / 192 KB) também ensina: definir teto de tamanho de evento e, acima dele, enviar só as chaves e deixar o consumidor buscar o resto (padrão claim-check).

### 29. Solutions e ALM: managed vs unmanaged, camadas, e onde isso destrói projetos

Duas naturezas: **unmanaged** ('are developed'... 'should be considered your source for Microsoft Power Platform assets'; ao deletar, só o contêiner some e as customizações ficam) e **managed** ('are deployed'; não editáveis diretamente; não exportáveis; ao desinstalar, TUDO some). Duas camadas no ambiente: **unmanaged layer** (todas as solutions unmanaged e customizações ad-hoc COMPARTILHAM uma única camada) e **managed layers** (empilhadas, 'the last one installed is above the... previously', com 'Last one wins' ou merge; embaixo de tudo está o system layer). Dentro de uma solution managed há sub-camadas: **Base** -> **Patches** -> **Pending upgrade** -> **Top** (o topo define o runtime). Merge real só acontece em model-driven app, form e site map; **todos os outros componentes usam 'top level wins'**. Ciclo de vida: Create, **Update** ('You can't delete components with an update'), **Upgrade** ('removes unused components... deletes components that existed but are no longer included'), **Patch** ('Using patches **isn't recommended**'). Armadilhas caras e explícitas: 'You **can't import a managed solution into the same environment that contains the originating unmanaged solution**' (exige ambiente separado só para testar); 'When you delete a managed solution, the following data is lost: **data stored in custom tables** that are part of the managed solution and **data stored in custom columns** that are part of the managed solution on other tables'; editar um componente managed cria dependência que impede desinstalar a solution; 'Once you introduce a publisher for a component in a managed solution, you can't change the publisher for the component' — por isso 'it's best to define a single publisher'; prefixo do publisher não pode ser trocado depois de criar os itens; **solution até 95 MB**.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/alm/solution-concepts-alm; https://learn.microsoft.com/en-us/power-platform/alm/solution-layers-alm

**Licao para a Tracbel:** DESCARTAR quase tudo — e entender POR QUE existe, para não reinventar. Todo esse aparato existe porque o Dataverse precisa que dezenas de fornecedores instalem customizações no MESMO ambiente sem se destruírem, mantendo a capacidade de desinstalar limpo. A Tracbel tem UM fornecedor (o próprio time) e UM produto. O equivalente correto e infinitamente mais simples é **Git + migrations do EF Core + pipeline de CI/CD**: a 'camada' é um commit, o 'upgrade' é `dotnet ef database update`, o 'rollback' é reverter um commit. As lições que SOBREVIVEM e valem escrever no repo: (1) **prefixo/namespace único definido no dia 1 e nunca alterado** (`tbl_` ou `tracbel_`) — a Microsoft avisa que depois é irreversível, e isso é verdade em qualquer schema; (2) **configuração é dado versionado, não estado de produção**: os steps do pipeline, fluxos e regras devem ser exportáveis para JSON, entrar no Git e ser aplicados por migration — senão dev, homologação e produção divergem em silêncio (é exatamente o mal que aflige o Vórtice hoje); (3) **'deletar componente apaga o dado dos clientes'** é o alerta que justifica: NUNCA gerar DROP COLUMN/DROP TABLE automaticamente numa migration de produção — revisão manual obrigatória; (4) 'top level wins' ensina que camadas de configuração precisam de precedência DETERMINÍSTICA e visível — se a Tracbel tiver config global + por filial + por usuário, a ordem tem que estar documentada e a UI tem que mostrar de onde veio o valor efetivo.

### 30. Power Platform pipelines: ALM gerenciado — e a lista de coisas que ele ainda não faz

Pipelines trazem CI/CD para dentro do produto: 'Admins easily configure automated deployment pipelines in minutes rather than days or weeks.' Arquitetura: um **host** (ambiente de produção que guarda a configuração e os artefatos), ambientes de **Development** e de **Target**. Garantia importante: 'Solutions are exported as soon as a deployment request is submitted... **the same solution artifact will be deployed**. Similarly, the system doesn't re-export a solution for deployments to subsequent stages... The system also prevents any tampering or modification to the exported solution artifact. This ensures customization can't bypass QA environments or your approval processes.' Licenciamento: 'All other environments used in pipelines must be enabled as **managed environments**' e a partir de fevereiro de 2026 a Microsoft passa a habilitar managed environment automaticamente nos targets. Limitações declaradas na FAQ: NÃO deploya solutions unmanaged; NÃO deploya múltiplas solutions de uma vez; NÃO permite escolher update vs upgrade ('Pipelines default import behavior is **Upgrade** without Overwrite customizations'); NÃO faz deploy cross-tenant; NÃO publica customizações unmanaged antes de exportar; NÃO suporta múltiplos devs em ambientes de desenvolvimento isolados ('The current implementation uses a **single development environment** for a given solution'); Power BI dashboards/datasets não suportados; não dá para customizar o app de pipelines (só extension hooks). Aprovações existem via 'delegated deployments' com service principal.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/alm/pipelines (seção Frequently asked questions)

**Licao para a Tracbel:** DESCARTAR o produto, COPIAR uma garantia específica. A garantia que vale ouro e que a Tracbel deve replicar literalmente: **o artefato é construído UMA vez e promovido imutável entre estágios**, e o sistema impede adulteração — nada é reconstruído entre QA e produção. Isso é build-once-deploy-many, e é exatamente o que GitHub Actions / Azure DevOps entregam de graça: publicar o binário/imagem uma vez, promover a MESMA imagem para dev -> homologação -> produção, com aprovação manual antes de produção. Sem isso, 'passou em homologação' não significa nada. A limitação de 'single development environment' também é reveladora: mesmo a Microsoft não resolveu bem o desenvolvimento paralelo em plataforma low-code. O time de 2-3 pessoas da Tracbel, trabalhando em código com Git e branches, já está estruturalmente MELHOR do que o topo de linha do Power Platform nesse quesito — e isso é um argumento forte a favor da decisão de construir em .NET puro.

### 31. Power Automate cloud flows: os limites que definem se é ferramenta ou armadilha

Limites numéricos oficiais: **500 ações por workflow** ('Flows with a large number of actions might encounter performance issues while you edit them, even if they have fewer than 500. Consider using child flows'); **run duration de 30 dias** (inclui passos pendentes como aprovações, que expiram depois); **retenção do histórico de 30 dias**; intervalo máximo de recorrência de 500 dias; **fluxo com erro contínuo é desligado em 14 dias**; **fluxo sem disparo em 90 dias pode ser desligado** (com aviso 30 dias antes). Concorrência: 'Unlimited for flows with Concurrency Control turned off; **1 to 100 when Concurrency Control is turned on (defaults to 25)**' — e o alerta pesado: 'Turning on Concurrency Control **can't be undone without deleting and re-adding the trigger**'. Apply to each: **5.000 itens (Low) / 100.000 (demais)**, com concorrência interna default de 1, ajustável de 1 a 50. Until: default 60 iterações, máximo 5.000. Split on: 5.000/100.000, mas **cai para 100 quando concorrência está ligada**. Timeouts: requisição síncrona de saída **120 segundos**, requisição de entrada **120 segundos**, assíncrona configurável até 30 dias. Retry default: 'up to 12 retries at exponentially increasing intervals... up to an interval of approximately 1 hour for the last retry' (Medium/High). Limites de retry configuráveis: máximo 90 tentativas, delay máximo 1 dia, mínimo 5 segundos. Requisições: 100.000 por 5 minutos na plataforma; chamadas concorrentes de saída 500 (Low) / 2.500 (demais). Throughput de conteúdo: 120 MB por 5 min (Low) / 1,2 GB (demais).

**Evidencia:** https://learn.microsoft.com/en-us/power-automate/limits-and-config (tabelas de limites, concorrência, timeout e retry)

**Licao para a Tracbel:** DESCARTAR como motor de regra de negócio, CONSIDERAR como cola de integração — e copiar a política de retry. Três limites condenam o uso de cloud flow para regra crítica: (1) **fluxo sem disparo em 90 dias é desligado automaticamente** — uma regra que roda raramente (fechamento anual, exceção de crédito) simplesmente para de existir sem ninguém perceber; (2) **fluxo com erro é desligado em 14 dias**; (3) **500 ações** transforma qualquer lógica não trivial num quebra-cabeça de child flows. Regra de negócio da Tracbel vive em C# testável, não em designer visual. Onde Power Automate faz sentido: notificação (Teams/e-mail), aprovação simples, e cola pontual com SharePoint/Outlook — coisas onde 'parou de rodar' é irritante, não é incidente. O que COPIAR literalmente é a **política de retry**: exponential backoff, ~12 tentativas, teto de intervalo em ~1h, delay mínimo 5s, máximo 1 dia — números validados em escala planetária. Em .NET 8, isso é Polly com `WaitAndRetryAsync` e jitter. COPIAR também a ideia de **concurrency control explícito por consumidor** (default conservador, teto configurável) no processador de outbox, e o timeout de 120s como limite superior absoluto para qualquer chamada síncrona de saída.

### 32. Como replicar o pipeline em .NET 8 puro — receita mínima e concreta

O pipeline inteiro do Dataverse, na parte que importa, cabe em ~5 tipos. (1) **Mensagem**: `record CriarOportunidade(...) : ICommand<Guid>` — toda operação tem nome e é um tipo. (2) **Contexto**: `class PipelineContext<T> { public string Mensagem; public string Entidade; public T Target; public T? Before; public IReadOnlySet<string> CamposAlterados; public Dictionary<string,object> Items; public int Depth; public Guid CorrelationId; public Guid UsuarioId; public Guid UsuarioIniciadorId; public Origem Origem; public List<OutboxItem> Outbox; }`. (3) **Handler**: `interface IStageHandler<T> { Task HandleAsync(PipelineContext<T> ctx, CancellationToken ct); }` — construtor recebe dependências por DI, classe é stateless. (4) **Registro em tabela**: `crm_pipeline_step(Id, Mensagem, Entidade, Estagio, Modo, Ordem, HandlerKey, FiltroCampos, Ativo, ExecutarComo, ConfigJson)` com índice único em (Mensagem, Entidade, Estagio, Ordem), lido no boot e cacheado com invalidação por versão. (5) **Dispatcher**: uma classe que, para cada operação, executa `BeforeValidation` (fora da transação) -> abre transação EF Core -> `BeforeSave` -> `SaveChanges` -> `AfterSave` -> commit -> só então drena o Outbox. Resolução do handler por `IServiceProvider.GetRequiredKeyedService<IStageHandler<T>>(HandlerKey)` (keyed services são nativos no .NET 8). Filtro de campos usa `ChangeTracker` para comparar OriginalValue/CurrentValue. Async = linha no outbox gravada na mesma transação + `BackgroundService` que faz polling. Exceção `BusinessRuleException` -> 422; qualquer outra -> rollback + 500. Cada handler instrumentado com `Stopwatch` e `ILogger` em scope de CorrelationId, com WARNING acima de 2s. Tudo testável: um teste de integração cria o contexto, roda o dispatcher contra um SQLite/Testcontainers e verifica o efeito — sem ferramenta de registro, sem sandbox, sem profiler.

**Evidencia:** Síntese das docs oficiais citadas nos achados anteriores (event-framework, register-plug-in, understand-the-data-context, best-practices/business-logic, analyze-performance) mapeada para recursos nativos do .NET 8 (keyed DI services, System.Threading.RateLimiting, BackgroundService, EF Core ChangeTracker/RowVersion)

**Licao para a Tracbel:** COPIAR — esta é a entrega final. Ordem de implementação sugerida para o time de 2-3 pessoas: **Sprint 1**: dispatcher + 3 estágios + transação + BusinessRuleException + logging com CorrelationId, com handlers registrados só em código (`AddKeyedScoped`). Já resolve 80% do valor. **Sprint 2**: tabela de steps + cache + ligar/desligar/reordenar sem deploy (entrega 'extensibilidade sem release'). **Sprint 3**: outbox + BackgroundService + webhooks (entrega 'APIs para integração' e desacopla o TOTVS/JDE). **Sprint 4**: validação declarativa compartilhada com o React e fluxo de estágios (entrega 'fluxos interativos' e 'usabilidade'). Rate limiting entra antes da primeira integração automatizada em produção, não antes. Todo o resto do Dataverse (sandbox, solutions, FetchXML, Power Fx, BPF com branching, Service Bus) fica de fora — e este documento é a justificativa escrita de por quê.

### 33. O que explicitamente NÃO copiar do Dynamics — lista de veto

Consolidando as evidências dos achados anteriores, sete coisas que a Tracbel deve recusar por escrito: (1) **Sandbox / isolamento por processo** — existe por multi-tenancy com código de terceiros; custo altíssimo (serialização de contexto, entity images como prótese, perda de DI e de debug) e zero benefício num sistema de fornecedor único. (2) **Números mágicos de estágio (10/20/30/40)** — usar enum; `context.Stage.Equals(30)` vazou para o código de toda a comunidade Dynamics. (3) **Múltiplos motores de automação concorrentes** — o Dataverse tem 6 e a Microsoft passou anos depreciando os próprios (dialogs removidos em 01/12/2020, task flows em 01/10/2021, real-time workflows com 'there are better ways', custom actions substituídas por Custom API, instant low-code plug-ins despriorizados). Um mecanismo só. (4) **Update disparando duas vezes** por partição owner-fields / state-status — evento de negócio dispara uma vez com o changeset completo. (5) **`if (Depth > 1) return` como guarda anti-recursão** — a própria Microsoft escreve 'Do not take any dependency on the IExecutionContext.Depth property in your code'; resolver com marcação de origem da operação. (6) **Camadas managed/unmanaged de solutions com merge 'top wins'**, patches (a doc diz 'Using patches isn't recommended') e a regra de que deletar solution managed apaga dados de clientes — substituir por Git + migrations. (7) **Linguagem de expressão própria executando no servidor** — a Microsoft tentou (low-code plug-ins), ficou em preview e despriorizou parte; extensibilidade vem de configuração de handlers pré-escritos, não de código em runtime. Bônus: (8) **FetchXML** — linguagem de query XML proprietária; a Tracbel tem SQL Server + EF Core + LINQ.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/important-changes-coming; https://learn.microsoft.com/en-us/power-apps/maker/data-platform/overview-realtime-workflows; https://learn.microsoft.com/en-us/dotnet/api/microsoft.xrm.sdk.iexecutioncontext.depth; https://learn.microsoft.com/en-us/power-apps/maker/data-platform/low-code-plug-ins; https://learn.microsoft.com/en-us/power-platform/alm/solution-layers-alm

**Licao para a Tracbel:** DESCARTAR os oito itens, e colocar esta lista como seção 'Não-objetivos' no documento de arquitetura e no CLAUDE.md/AGENTS.md do repositório. O valor de um não-objetivo escrito é impedir que, seis meses depois, alguém proponha 'um motor de regras configurável' ou 'plugins carregados dinamicamente' sem saber que a decisão já foi tomada com evidência. Cada item da lista tem uma fonte oficial da Microsoft dizendo, direta ou indiretamente, que aquilo deu problema — é o material de convencimento mais barato que existe.

## Lacunas declaradas

- Valores numéricos dos estágios PreValidation=10 e PreOperation=20: NÃO consegui confirmar em documentação oficial da Microsoft. A doc do event-framework lista os estágios por NOME apenas. Confirmei oficialmente apenas MainOperation=30 (código de exemplo da página de Custom API usa context.Stage.Equals(30)) e PostOperation=40 (payload JSON de webhook publicado pela Microsoft mostra "Stage": 40). Os valores 10 e 20 vêm de fontes de comunidade (Medium, c-sharpcorner, softchief) e são consistentes entre si, mas devem ser tratados como não confirmados na fonte primária.
- Limite de rollup columns (10 por tabela / 100 por organização): apareceu em snippet de busca mas NÃO validei na página oficial de rollup columns. Não usar esse número sem confirmar.
- Limite de business process flows ATIVOS por registro (o número '10' apareceu em snippet de busca): a página oficial create-business-process-flow confirma 'Multiple active processes can run concurrently on the same record' e confirma os limites de 30 stages / 30 steps / 5 tabelas / 10 níveis de branch, mas NÃO confirma um teto de 10 BPFs ativos por registro. Tratar como não confirmado.
- Depth máximo = 8: confirmado na página oficial de IExecutionContext.Depth, mas o mecanismo de configuração citado (PowerShell Set-CrmSetting / WorkflowSettings.MaxDepth, com link para TechNet do CRM 2015) é de deployment on-premises. NÃO consegui confirmar se e como esse valor é configurável em ambientes Dataverse online — a doc parece desatualizada nesse ponto.
- Limite de memória exato do sandbox worker process: a doc reconhece que existe ('Worker process reaches the memory limit', 'threshold CPU, memory, or handles limits') mas NÃO publica o valor numérico em MB. Não encontrei número oficial.
- Limite exato de 50 assemblies por plugin package: apareceu em snippet de busca ('16 MB in size or 50 assemblies') mas a página oficial build-and-package confirma apenas o limite de 16 MB por ASSEMBLY. O teto de 50 assemblies por package não foi confirmado na fonte.
- Status de deprecação dos classic workflows (background e real-time) do Dataverse: a página oficial de real-time workflows contém a orientação 'There are better ways to create modern automations. Consider using Power Automate flows', mas NÃO encontrei anúncio formal de deprecação com data na página important-changes-coming. Dialogs (01/12/2020) e Task Flows (01/10/2021) SIM têm datas oficiais. Não afirmar que classic workflows estão formalmente depreciados.
- Elastic tables: mencionadas de passagem (limite de 500 linhas por página em FetchXML vs 5.000 de standard tables; ausência de transações multi-registro), mas não aprofundei a página oficial. O comportamento transacional citado ('erros em plug-in síncrono não fazem rollback do registro criado') vem de fonte de comunidade, não confirmado.
- Não investiguei em profundidade: Dataverse business events (padrão de evento de negócio publicado via Custom API com AllowedCustomProcessingStepType=AsyncOnly), background operations (preview), Dataverse Functions (que a doc cita como substituto dos instant low-code plug-ins), e Power Platform CLI (pac plugin init, pac modelbuilder, pac pipeline). São adjacentes ao tópico e podem render um segundo levantamento.
