# Plataforma, metadados, UX e ALM no Salesforce — lições para o CRM próprio da Tracbel (.NET 8 + EF Core + SQL Server + React)

> Pesquisa automatizada - workflow `crm-tracbel-pesquisa-profunda`, 30/08/2026.

## Resumo

O Salesforce não é "um CRM com muitas telas": é um runtime dirigido por metadados. Objeto e campo não são DDL — são LINHAS em tabelas de catálogo (MT_Objects / MT_Fields) que apontam para colunas genéricas VARCHAR (Value0..Value500) numa tabela única MT_Data, com índices materializados em tabelas-pivô (MT_Indexes, MT_Unique_Indexes, MT_Relationships, MT_Name_Denorm). Isso é o que permite criar campo sem release — e é também a origem de TODOS os limites duros (500 campos/objeto em Enterprise, 800 em Unlimited). Para a Tracbel, a lição central é: copiar o CATÁLOGO DE METADADOS (o conceito de "campo é dado"), mas NÃO copiar o motor de armazenamento EAV — com SQL Server + EF Core, colunas reais e migrations dão 90% do benefício com 5% da complexidade. Em UX, o Salesforce ganha por poucos primitivos muito bem feitos: Compact Layout (7 campos no topo), Path (5 campos-chave + orientação por etapa), Kanban sobre List View, Related Lists com 10 colunas, e regras de visibilidade condicional (Dynamic Forms) que substituem N page layouts. Em relatórios, o modelo de "Report Type curado pelo admin + builder drag-and-drop para o usuário" é o único jeito de o usuário final montar relatório sozinho sem ver o schema. Em ALM, o Salesforce paga caro pelo multi-tenant (change sets de 10.000 arquivos, gate de 75% de cobertura, 4 níveis de sandbox) — quase tudo isso é overkill para um time de 2-3 devs com banco próprio. Em produtividade de vendas, Einstein exige volumes de dados (200 ganhas + 200 perdidas em 24 meses) e custa US$50/usuário/mês: para 130 usuários é overkill declarado.

## Entidades / objetos mapeados

### `MT_Objects`

**Funcao:** Tabela interna de catálogo que registra cada objeto (tabela virtual) de cada tenant. Uma linha = um objeto.

**Campos-chave:** ObjID, OrgID, ObjName

**Relacoes:** Pai de MT_Fields (ObjID) e referenciado por MT_Data.ObjID

### `MT_Fields`

**Funcao:** Catálogo de campos. Cada linha define um campo e, crucialmente, o FieldNum (slot físico) onde o valor daquele campo é gravado em MT_Data.

**Campos-chave:** FieldID, OrgID, ObjID, FieldName, datatype, IsIndexed, FieldNum

**Relacoes:** Filho de MT_Objects; define o mapeamento lógico→físico para MT_Data

### `MT_Data`

**Funcao:** Tabela ÚNICA de dados de todos os objetos de todos os tenants. Contém colunas genéricas 'flex' Value0..Value500, todas VARCHAR, que hospedam campos lógicos diferentes conforme OrgID+ObjID.

**Campos-chave:** GUID (record id), OrgID, ObjID, Name, Value0..Value500

**Relacoes:** Resolvida via MT_Objects/MT_Fields; particionada por hash de OrgID

### `MT_Indexes`

**Funcao:** Tabela-pivô de índices secundários. Copia sincronamente o valor de campos marcados como indexados para colunas TIPADAS, para que o Oracle possa criar índices nativos.

**Campos-chave:** StringValue, NumValue, DateValue (colunas tipadas)

**Relacoes:** Espelha valores de MT_Data para campos com IsIndexed=true

### `MT_Unique_Indexes / MT_Fallback_Indexes / MT_Name_Denorm / MT_Relationships`

**Funcao:** Pivôs auxiliares: unicidade (Org+valor), busca de fallback quando o search engine cai, lookup rápido de Name por Id, e travessia bidirecional de relacionamentos.

**Campos-chave:** MT_Relationships tem índices compostos (OrgID,parentID,childID) e (OrgID,childID,parentID)

**Relacoes:** Todas derivadas de MT_Data/MT_Fields

### `CustomObject (tipo de metadado)`

**Funcao:** Tipo do Metadata API que representa a definição de um objeto custom (sufixo __c) ou external object.

**Campos-chave:** fullName, label, pluralLabel, nameField, deploymentStatus, sharingModel

**Relacoes:** Contém CustomField, ListView, RecordType, CompactLayout, ValidationRule

### `CustomField (tipo de metadado)`

**Funcao:** Tipo do Metadata API para criar/alterar/apagar definição de campo em objeto standard, custom ou external. É o 'campo como dado'.

**Campos-chave:** fullName, type, length, precision/scale, required, unique, externalId, formula, referenceTo, relationshipName

**Relacoes:** Filho de CustomObject; referenciado por Layout, FlexiPage, ValidationRule, Report

### `CustomMetadataType (__mdt)`

**Funcao:** Tipo de objeto cujos REGISTROS são metadados (deployáveis, empacotáveis, versionáveis em git). É o mecanismo canônico de 'configuração sem release' do Salesforce.

**Campos-chave:** Sufixo __mdt; visibility = Public | Protected | PackageProtected; campos com sufixo __c

**Relacoes:** Consultável por SOQL/Apex/Flow/fórmula; consultas NÃO contam contra governor limits de SOQL; DML não permitido via Partner/Enterprise API

### `RecordType`

**Funcao:** Variante de um objeto que combina: subconjunto de valores de picklist, page layout por perfil, e (em Opportunity/Lead/Case) um Business Process de etapas.

**Campos-chave:** DeveloperName, BusinessProcess, picklistValues, active

**Relacoes:** Matriz Profile × RecordType → Layout; 1 CompactLayout por RecordType; 1 Path por RecordType

### `Layout (Page Layout) vs FlexiPage (Lightning Page)`

**Funcao:** Layout = modelo antigo, rígido, atribuído por Perfil×RecordType. FlexiPage = página do Lightning App Builder, composta por componentes com regras de visibilidade; com Dynamic Forms absorve os campos que estavam no Layout.

**Campos-chave:** Layout: até 20 s-controls, 20 páginas Visualforce, 20 expanded lookups, 100 related lists. FlexiPage: 25 componentes por região.

**Relacoes:** Dynamic Forms move campos do Layout para Field Sections dentro da FlexiPage, unificando o modelo de atribuição

### `CompactLayout`

**Funcao:** Define os campos do Highlights Panel (topo do registro), do hover card de lookup e do resumo na activity timeline.

**Campos-chave:** Até 10 campos; Lightning Experience exibe os 7 primeiros; integrações Outlook/Gmail exibem os 3 primeiros

**Relacoes:** 1 compact layout por RecordType; não é atribuível por perfil/usuário

### `Path / ProcessStep`

**Funcao:** Barra de etapas no topo do registro com campos-chave editáveis e texto de orientação por etapa.

**Campos-chave:** 1 Path por RecordType; até 5 campos-chave por etapa; orientação textual por etapa

**Relacoes:** Compartilha a configuração com o Kanban do mesmo objeto/recordtype/picklist

### `ReportType (standard e Custom Report Type)`

**Funcao:** Contrato curado pelo admin que define QUAIS registros e QUAIS campos ficam disponíveis para o usuário montar relatório. É o que impede o usuário de ver o schema cru.

**Campos-chave:** Até 1.000 campos por report type; até 60 referências de objeto; relação 'with' vs 'with or without'

**Relacoes:** Objeto primário + objetos relacionados; alimenta Report (tabular/summary/matrix/joined)

### `Report / Dashboard`

**Funcao:** Report = consulta montada pelo usuário sobre um ReportType. Dashboard = coleção de widgets alimentados por Reports.

**Campos-chave:** Report: 2.000 linhas exibidas, 20 filtros, 5 fórmulas de resumo, 5 bucket fields, 2 row-level formulas. Dashboard: 25 widgets, 5 filtros, 50 valores por filtro.

**Relacoes:** Report → Dashboard widget; subscriptions por usuário (7-15 conforme edição)

### `Opportunity / OpportunityLineItem / Product2 / Pricebook2 / PricebookEntry`

**Funcao:** Núcleo do modelo de vendas: oportunidade, item da oportunidade, produto, tabela de preços e a associação produto↔tabela de preços com preço.

**Campos-chave:** Opportunity.StageName (usado por Path, Kanban, Forecast Category e Einstein), Opportunity.Amount, Opportunity.Pricebook2Id

**Relacoes:** Opportunity 1:N OpportunityLineItem; OpportunityLineItem → PricebookEntry → (Product2, Pricebook2)

### `PermissionSet / PermissionSetGroup / Muting Permission Set`

**Funcao:** Modelo recomendado de permissão: perfil mínimo ('Minimum Access Salesforce') + permission sets compostos em grupos, com 1 muting permission set por grupo para SUBTRAIR permissões.

**Campos-chave:** 1 muting permission set por permission set group; muting não vence permissão concedida por outro caminho

**Relacoes:** User ← PermissionSetAssignment ← PermissionSet ← PermissionSetGroup

## Achados

### 1. Um campo novo no Salesforce não executa DDL: ele insere uma linha em MT_Fields e aluga um slot VARCHAR em MT_Data

A arquitetura multi-tenant separa kernel compilado, dados do tenant e metadados. O UDD (Universal Data Dictionary) mantém a definição de objetos, campos, relações e atributos. Duas tabelas internas mandam no jogo: MT_Objects (ObjID, OrgID, ObjName) e MT_Fields (FieldID, OrgID, ObjID, FieldName, datatype, IsIndexed, FieldNum). Os DADOS ficam todos numa tabela única MT_Data com colunas genéricas Value0..Value500 ('flex columns' ou 'slots'), TODAS de tipo VARCHAR/string de tamanho variável. O FieldNum de MT_Fields diz qual Value{N} guarda aquele campo. Um mesmo Value7 pode ser 'Amount__c' num objeto e outra coisa em outro objeto, porque toda query filtra por OrgID+ObjID. Tipagem é validada na camada de aplicação e a conversão em runtime usa funções do banco (TO_NUMBER, TO_DATE). Consequência declarada na documentação: 'Salesforce Platform does not create an actual table in a database or compile any code. Instead, Salesforce Platform simply stores metadata that the system's engine can use to generate the virtual application components at runtime.' Trocar o TIPO de um campo dispara migração de dados em background para um novo slot, não um ALTER COLUMN in-place. Tudo é particionado fisicamente por hash de OrgID (tipicamente 128-1024 partições), o que dá partition pruning automático.

**Evidencia:** https://developer.salesforce.com/ja/wiki/multi_tenant_architecture (Force.com Multitenant Architecture, seções UDD / MT_Objects / MT_Fields / MT_Data); https://cirra.ai/articles/salesforce-database-architecture-explained; https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-multitenant-architecture.html (retornou 403 no fetch direto, conteúdo confirmado via snippet de busca)

**Licao para a Tracbel:** ADAPTAR, NÃO COPIAR. Copie o CONCEITO (o catálogo de metadados: uma tabela FieldDefinition que descreve label, tipo, obrigatoriedade, visibilidade, ordem, help text, e que a UI React lê para se desenhar). NÃO copie o motor EAV / flex columns: a Tracbel é single-tenant, tem SQL Server próprio e EF Core com migrations. Colunas reais dão tipagem, índices nativos, constraints, plano de execução decente e SQL legível para o time de 3 pessoas. O padrão pragmático é HÍBRIDO: (a) colunas reais para tudo que é núcleo (Cliente, Oportunidade, Equipamento, Proposta), geradas por migration; (b) uma tabela CampoCustomizado + CampoCustomizadoValor (EAV enxuto, com coluna tipada por tipo: ValorTexto/ValorNumero/ValorData/ValorBool, exatamente como o MT_Indexes faz) só para campos que o negócio quer criar sozinho; (c) um catálogo de metadados que descreve AMBOS de forma uniforme, para que a UI não saiba a diferença. O ganho de 'campo novo sem release' vem do catálogo + UI dirigida por ele, não do EAV.

### 2. O preço do modelo por metadados: limites duros de campos por objeto, e eles NÃO sobem

Enterprise Edition: 500 campos custom por objeto. Unlimited/Performance: 800. Professional: 100. Contam para o teto: campos criados manualmente, campos de fórmula E roll-up summary fields. O limite existe porque MT_Data tem um número FIXO de colunas Value{N}. Quando uma org chega perto do teto, as saídas são: quebrar o objeto em dois, ou mover histórico para Big Objects. Outros tetos correlatos: até 1.000 valores num picklist single-select para poder torná-lo 'restricted' (500 num multi-select); Custom Metadata Types têm no máximo 100 campos por tipo/registro e 10 MB por org.

**Evidencia:** https://help.salesforce.com/s/articleView?language=en_US&id=platform.custom_field_allocations.htm (página SPA não renderizou no fetch; números confirmados por snippet de busca e por fontes secundárias forcetalks/fieldrat); https://help.salesforce.com/s/articleView?language=en_US&id=platform.picklist_limitations.htm; https://cirra.ai/articles/salesforce-database-architecture-explained (explica o porquê físico do teto)

**Licao para a Tracbel:** DESCARTAR o teto artificial, mas COPIAR a disciplina. Com SQL Server você não tem limite de 500 colunas relevante na prática (SQL Server permite 1.024 colunas por tabela, ou 30.000 com sparse columns), mas a lição real é de GOVERNANÇA: sem freio, o CRM legado vira um objeto com 400 campos que ninguém entende — exatamente o que o Vórtice virou. Adote uma regra explícita no projeto: campo novo exige dono, motivo e data de revisão; campos sem preenchimento há N meses entram numa fila de depreciação. Implemente isso como METADADO (FieldDefinition.UltimoUsoEm, .Dono, .Status), não como processo de e-mail.

### 3. Metadata API: metadados são arquivos versionáveis, deployáveis e diffáveis — o coração do ALM

O Metadata API existe para MOVER metadados entre orgs, não dados de negócio (para dados usa-se REST/SOAP/Bulk). Dois modos: (a) chamadas CRUD por tipo de metadado; (b) file-based deploy()/retrieve() com um .zip. Limites exatos: até 10.000 arquivos por deploy ou retrieve; .zip comprimido máximo de 39 MB; pasta descomprimida máximo de 600 MB (629.145.600 bytes); mensagem SOAP pós-encoding máximo de 50 MB. Change sets (in e outbound) também aceitam até 10.000 arquivos. Retrieve com o parâmetro rootTypesWithDependencies: máximo 25 requisições por dia, e cada requisição pode pedir dependências de até 100 componentes. Os tipos CustomObject e CustomField do Metadata API são literalmente como você cria uma tabela e uma coluna no Salesforce — declarativamente, em XML, versionado em git.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_intro.htm; https://developer.salesforce.com/docs/atlas.en-us.salesforce_app_limits_cheatsheet.meta/salesforce_app_limits_cheatsheet/salesforce_app_limits_platform_metadata.htm; https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/customobject.htm; https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/customfield.htm

**Licao para a Tracbel:** COPIAR o princípio, com peso muito menor. A ideia forte é: TODA configuração do CRM (definição de campo, layout de tela, regra de validação, etapas do funil, mapeamento de integração) mora em ARQUIVOS versionados no git, e existe um comando que aplica esses arquivos num ambiente. Na stack .NET isso é trivial: guarde a configuração como JSON/YAML no repositório, com um 'ConfigSeeder' idempotente executado no startup ou por CLI (`dotnet run --project Tools.ConfigDeploy -- --env staging`). Você ganha diff, code review e rollback de CONFIGURAÇÃO — que é exatamente o que falta no Vórtice hoje, onde ninguém sabe quem mudou o quê nem quando. Não construa um Metadata API SOAP: construa um seeder de configuração versionada.

### 4. Custom Metadata Types (__mdt): o mecanismo canônico de 'extensibilidade sem release'

Custom Metadata Types são objetos cujos REGISTROS são tratados como metadados: sufixo __mdt, campos com sufixo __c, deployáveis e empacotáveis como qualquer outro metadado. É o que a Salesforce chama de 'app configuration engine'. Diferenças-chave para custom objects: (1) não consomem armazenamento de dados; (2) registros vêm junto no pacote/deploy, então a configuração viaja com o código; (3) consultas SOQL contra __mdt NÃO contam contra os governor limits de SOQL — você pode ler configuração à vontade dentro de código; (4) três níveis de visibilidade: Public (todas as orgs assinantes), Protected (só a org de desenvolvimento) e PackageProtected (só o código Apex do pacote — o lugar certo para API keys). Apex pode criar/ler/atualizar registros de custom metadata, mas DML NÃO é permitido via Partner/Enterprise API. Limites: 100 campos por tipo/registro; 10 MB por org e 10 MB por pacote gerenciado certificado; API 31.0+. Contraste importante: o Lightning Data Service NÃO suporta custom metadata types (só custom objects e standard objects suportados pelo UI API).

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_custommetadatatypes.htm; https://developer.salesforce.com/blogs/engineering/2015/04/custom-metadata-types-ga; https://help.salesforce.com/s/articleView?id=platform.custommetadatatypes_limits.htm; https://developer.salesforce.com/docs/platform/lwc/guide/data-ui-api.html (confirma que LDS não suporta __mdt)

**Licao para a Tracbel:** COPIAR, e este é o achado mais acionável de todos para o requisito 'extensibilidade sem release'. Crie no CRM da Tracbel uma distinção EXPLÍCITA entre três categorias: (1) DADO transacional (Cliente, Oportunidade, Proposta) → tabelas normais; (2) CONFIGURAÇÃO versionada (regras de roteamento de aprovação por CEN, faixas de desconto por linha de produto, mapeamento de campanha RD Station → identificador de conversão, tipos de processo e suas fases) → tabelas 'Config*' cujo conteúdo mora em JSON no git e é aplicado por seeder; (3) PREFERÊNCIA do usuário → tabela normal, sem git. A categoria (2) é a que resolve as dores reais registradas na memória do Vórtice: 'campo só preenche se o identificador da conversão estiver mapeado na tela Integração RD', 'aprovação vai para o líder do CEN no momento da geração', 'ação 897 tem limite vitalício de 1 por pessoa'. Hoje essas regras estão enterradas numa tela de admin sem histórico. Como configuração versionada, elas viram diff no PR.

### 5. Dynamic Forms substitui Page Layouts: visibilidade condicional em vez de N layouts × M record types

O modelo antigo: um Page Layout rígido, atribuído pela matriz Perfil × Record Type — se 5 perfis precisam ver conjuntos ligeiramente diferentes de campos, você cria 5 layouts. Dynamic Forms quebra o componente 'Record Detail' em componentes individuais de CAMPO e de SEÇÃO (Field Section), posicionáveis em qualquer lugar da página Lightning, inclusive em abas e acordeões, e configurados no Lightning App Builder — sem tocar no editor de page layout. Ganho declarado: 'reduz o número de page layouts e record types que você precisa'; e você passa a ter um MODELO ÚNICO de atribuição (só a Lightning Page) em vez do modelo duplo (Lightning Page + Page Layout). Pegadinha crítica e documentada: regras de visibilidade em CAMPOS são avaliadas dinamicamente (o campo aparece/some enquanto o usuário edita); regras de visibilidade em SEÇÕES NÃO são dinâmicas — só são avaliadas depois que o registro é salvo. Diferença de UX: Field Sections usam ordem de tabulação cima-baixo-esquerda-direita; o Record Detail clássico usa esquerda-direita-cima-baixo. Limites: até 100 campos por COLUNA num Field Section; seções contam contra o limite de componentes da página. Suporte: custom objects, Account (inclusive Person Account), Contact, Opportunity, Case, Lead e a maioria dos standard objects habilitados para LWC — NÃO funciona em objetos sem LWC como Campaign, Task e Product, que continuam lendo do Page Layout. Filtros de visibilidade podem usar campos do registro ou 'advanced fields' (objeto relacionado, ou objeto global como User), com limite de 5 saltos de campo (Record.Account.Owner.Manager.Manager.Manager.LastName tem 6 saltos e não é suportado).

**Evidencia:** https://help.salesforce.com/apex/HTViewHelpDoc?id=sf.dynamic_forms_overview.htm; https://help.salesforce.com/s/articleView?id=sf.dynamic_forms_considerations.htm; https://help.salesforce.com/s/articleView?id=platform.dynamic_forms_limitations.htm; https://help.salesforce.com/s/articleView?id=platform.lightning_page_components_visibility.htm (limite de 5 saltos)

**Licao para a Tracbel:** COPIAR o modelo Dynamic Forms desde o dia 1, e NUNCA construir o modelo antigo. Concretamente: no CRM da Tracbel, a tela de um registro é uma FormDefinition (JSON versionado) composta de seções e campos, e CADA campo e CADA seção carrega uma expressão de visibilidade e uma de somente-leitura, avaliadas contra o registro + o usuário. Isso mata de uma vez a explosão combinatória de 'um layout por perfil' que já assombra o Vórtice. Duas decisões que o Salesforce errou e você deve acertar: (a) avalie visibilidade de SEÇÃO dinamicamente também (não só após o save) — é o mesmo avaliador, não há motivo técnico para a assimetria; (b) o limite de 5 saltos é arbitrário e confuso — no seu caso, resolva a expressão contra um DTO já hidratado com os relacionamentos necessários, declarados no metadado da tela.

### 6. Compact Layout / Highlights Panel: o achado de usabilidade com melhor razão esforço/benefício de todo o Salesforce

O Compact Layout define os campos que aparecem no topo do registro (Highlights Panel). Limites exatos: você pode adicionar até 10 campos ao compact layout; o Highlights Panel do Lightning Experience mostra os 7 PRIMEIROS; o app mobile mostra até 10; as integrações Outlook e Gmail mostram os 3 primeiros. O mesmo compact layout também controla os campos do cartão de hover quando você passa o mouse sobre um link de lookup, e o resumo expandido de uma atividade na activity timeline. Cada Record Type pode ter apenas UM compact layout atribuído; compact layouts NÃO são atribuíveis por perfil nem por usuário.

**Evidencia:** https://help.salesforce.com/s/articleView?id=platform.compact_layout_notes.htm; https://developer.salesforce.com/docs/atlas.en-us.salesforce1appadmin.meta/salesforce1appadmin/s1_admin_guide_compact_layouts_intro.htm

**Licao para a Tracbel:** COPIAR — é a mudança de UX mais barata e de maior impacto percebido. Todo registro do CRM da Tracbel deve ter um 'cabeçalho de destaque' com no MÁXIMO 5-7 campos, definido em metadado por tipo de registro, e esse mesmo conjunto deve alimentar: (1) o topo da tela do registro; (2) o tooltip/preview quando se passa o mouse num link para aquele registro; (3) o card do Kanban; (4) a linha da list view. Um único metadado 'CamposDeDestaque' servindo quatro superfícies é exatamente a economia que o Salesforce fez. Para uma revenda John Deere isso seria, na Oportunidade: Cliente, Modelo/Família do equipamento, Valor, Etapa, Previsão de fechamento, CEN/Vendedor. Reduza para 5 na tela e reserve 3 para superfícies estreitas.

### 7. Path + Kanban compartilham a MESMA configuração: um metadado, duas telas

Path é a barra de etapas no topo do registro. Configuração: cada objeto pode ter UM path por Record Type (não há limite de paths por org); em cada etapa você seleciona até 5 CAMPOS-CHAVE (editáveis inline, sem sair da barra) e escreve um texto de 'Guidance for Success'. O ponto arquitetural: quando você configura key fields e guidance num Path, as KANBAN VIEWS configuradas para o MESMO objeto, record type e picklist mostram automaticamente a mesma informação no painel de detalhes. Ou seja, uma configuração alimenta duas experiências. Restrições documentadas do Path: os campos Record Type e Owner não podem ser editados no painel de Key Fields (o usuário tem que ir na aba Details ou usar a ação Change Record Type); celebrações (confetti) não funcionam para o status 'Converted' de Lead nem para valores cujo API name contenha vírgula; criar um path pode levar alguns minutos quando há muitas combinações objeto × record type × picklist. Restrições do Kanban: a view de Opportunity mostra até 200 registros (Closed Lost são excluídos da contagem); NÃO é possível fazer ações em massa no Kanban; não dá para agrupar por campos de moeda; Opportunity não pode ser agrupada por Forecast Category; a transferência de propriedade e a troca de record type não são suportadas pelo painel de detalhes; cada kanban view é baseada numa LIST VIEW, e as configurações de kanban são aplicadas separadamente para cada list view.

**Evidencia:** https://help.salesforce.com/apex/HTViewHelpDoc?id=path_considerations.htm; https://help.salesforce.com/apex/HTViewHelpDoc?id=kanban_considerations.htm; https://trailhead.salesforce.com/content/learn/modules/leads_opportunities_lightning_experience/visualize-success-with-path-and-kanban

**Licao para a Tracbel:** COPIAR, e é provavelmente o item de maior impacto para 'os usuários mexerem tranquilamente'. O vendedor de máquina agrícola não quer procurar campo: ele quer saber 'em que etapa estou, o que falta para avançar, e quais 3 campos preciso preencher AGORA'. Implemente um metadado EtapaDoFunil { Ordem, Nome, CamposChave[] (máx 5), TextoDeOrientacao, CriteriosDeSaida[] } e renderize-o em DUAS telas com o MESMO metadado: a barra de etapas na tela do registro, e o painel do card no Kanban. O 'Guidance for Success' resolve diretamente uma dor registrada do Vórtice (usuários não sabem por que a ação não foi gerada, ou qual o próximo passo) — texto de orientação por etapa é documentação que aparece no lugar e na hora certa, e é editável sem release. Uma melhoria óbvia sobre o Salesforce: permita ações em massa no Kanban (o Salesforce não permite, e isso é uma limitação sentida).

### 8. List Views são a interface de trabalho real; relatório é o caso raro

O Kanban é literalmente uma projeção de uma LIST VIEW ('each kanban view is based on a list view'). Enhanced Related Lists no Lightning permitem até 10 COLUNAS (contra 4 no modelo antigo), com redimensionamento, ordenação, ações em massa e quebra de texto; e é possível exibir até 30 linhas por related list configurando 'number of records to display' no painel de propriedades. **Licao para a Tracbel:** COPIAR de forma agressiva. Isso é LIST VIEW salva, compartilhada com um grupo, com filtro, ordenação, edição inline e ação em massa — NÃO é relatório. ### 9. Lightning App Builder: composição por componentes com limite de 25 por região, e o modelo de exposição de componente por XML

Páginas Lightning têm limites SOFT e HARD: o App Builder reporta limites de design-time (máximo de componentes por região) e outros são de runtime (tempo cumulativo de carregamento, consumo cumulativo de CPU Apex, tamanho de resposta dos controllers). O limite prático é de 25 componentes por REGIÃO — com Header e Left Sidebar selecionados, o teto vira 75 na página. Contagem sutil: cada aba de um componente Tabs e cada seção de um Accordion contam contra o limite total (um Tabs com 3 abas conta como 4 componentes). Do lado do desenvolvedor, um LWC vira 'peça de Lego' para o admin via o arquivo componentName.js-meta.xml: <isExposed>true</isExposed> torna o componente utilizável no App Builder; <targets> declara onde ele pode ser usado (lightning__RecordPage, lightning__AppPage, lightning__HomePage e outros); <targetConfigs>/<targetConfig> declara configuração por alvo; <property name="..." type="String|Integer|Boolean"/> declara propriedades que o ADMIN preenche na UI (o tipo tem que bater entre o .js e o XML); <objects>/<object> restringe o componente a objetos específicos em record pages; um arquivo componentName.svg dá ícone customizado no painel de componentes. Além disso, Dynamic Interactions permite que um evento disparado por um LWC (um CustomEvent JS comum) reconfigure OUTROS componentes da página sem código: o dev declara o evento no js-meta.xml sob o targetConfig de lightning__AppPage com uma tag <event> contendo um <schema> JSON descrevendo as propriedades do evento; o admin então vê uma aba 'Interactions' no App Builder e liga a saída do evento às propriedades do componente-alvo. Só LWC pode ser origem; qualquer componente (Aura ou LWC) pode ser alvo.

**Evidencia:** https://developer.salesforce.com/docs/platform/lwc/guide/use-config-for-app-builder.html; https://developer.salesforce.com/docs/platform/lwc/guide/use-config-for-app-builder-dynamic-interactions.html; https://help.salesforce.com/s/articleView?id=sf.lightning_app_builder_limitations.htm (limite de 25/região confirmado via snippet e fontes secundárias)

**Licao para a Tracbel:** COPIAR o contrato XML/JSON de exposição de componente; DESCARTAR Dynamic Interactions no MVP. O padrão a copiar é: todo componente React do CRM da Tracbel se REGISTRA num catálogo com { nome, ondePodeSerUsado[], objetosSuportados[], propriedadesConfiguraveis[{nome, tipo, default, label}] }, e a tela é um JSON de composição que referencia esses componentes com valores de propriedade. Isso é o que faz 'qualquer dev do time saber estender': o dev escreve um componente React + um manifesto, e ele APARECE no montador de telas sem tocar em nenhuma tela existente. É o requisito 'OO forte + extensibilidade' resolvido por composição declarativa em vez de herança. Já Dynamic Interactions (wiring evento→propriedade via UI) é sofisticação de plataforma multi-tenant: para 130 usuários e 3 devs, o custo de construir e depurar isso não se paga — o dev escreve o wiring em 5 linhas de React.

### 10. Lightning Data Service: a camada que faz cache, sincroniza componentes e aplica CRUD/FLS/sharing sozinha

LDS é construído sobre a UI API ('a public Salesforce API que a Salesforce usa para construir o Lightning Experience'). Registros carregados via LDS são cacheados no cliente e COMPARTILHADOS entre componentes: se dois componentes mostram o mesmo registro, ambos leem a mesma cópia; se um componente muta o registro, TODOS os componentes que usam um @wire relevante recebem o novo valor automaticamente. Entradas de cache são invalidadas quando um componente muta o registro, ou quando o tempo de vida do cache expira e um wire adapter dispara uma leitura. Metadados de objeto e de layout são cacheados separadamente, num durable store com timeouts diferentes — consequência prática: mudanças de layout feitas pelo admin só aparecem depois do timeout do cache, a menos que o usuário faça logout/login. O acesso se dá por wire adapters do módulo lightning/uiRecordApi (getRecord, getRecords, getObjectInfo) e por funções imperativas (createRecord, updateRecord, deleteRecord). Sintaxe: @wire(getRecord, { recordId: '$recordId', fields: [...] }) — o '$' marca a variável como reativa, então quando ela muda o wire service reprovisiona os dados e o componente re-renderiza. O resultado chega como { data, error }. Acima dos wire adapters existem os componentes-base lightning-record-form, lightning-record-edit-form e lightning-record-view-form, que montam um formulário inteiro a partir do layout — a recomendação explícita da doc é considerar esses ANTES de escrever wire adapters. Segurança: 'UI API responses respect CRUD access, field-level security settings, and sharing settings' — sem escrever uma linha de código de segurança. Limitações: LDS suporta todos os custom objects e os standard objects suportados pela UI API; NÃO suporta Custom Metadata Types; não consome chamadas de API mas está sujeito a limites gerais; dados vindos de Apex NÃO são gerenciados ('changes to a record are reflected in all the technologies built on it. Contrastingly, data from Apex is not managed; you must refresh the data'). Diretriz de performance da doc: 'always use the wire adapter that returns the least amount of data that your use case requires'.

**Evidencia:** https://developer.salesforce.com/docs/platform/lwc/guide/data-ui-api.html; https://developer.salesforce.com/docs/platform/lwc/guide/data-wire-service.html; https://developer.salesforce.com/docs/platform/lwc/guide/reference-lightning-ui-api-record.html; https://developer.salesforce.com/blogs/2019/09/caching-and-synchronizing-component-data-with-lightning-data-service

**Licao para a Tracbel:** COPIAR o padrão inteiro — é o mais transferível para React. Traduza para: TanStack Query (ou RTK Query) com uma query key canônica por registro (['registro', objeto, id]), um hook useRegistro(objeto, id, campos) que é o seu getRecord, e mutações que invalidam a mesma key — assim dois componentes na mesma tela nunca divergem, que é uma classe inteira de bug que some de graça. Dois pontos NÃO negociáveis a copiar do Salesforce: (1) a API que serve o registro deve APLICAR permissão de objeto e de campo no SERVIDOR e devolver só o que o usuário pode ver — o front nunca decide segurança, e campo sem permissão nem chega ao browser; (2) forneça componentes de alto nível equivalentes a lightning-record-form: um <FormularioDeRegistro objeto="Oportunidade" id={id} modo="edit"/> que se monta a partir do metadado de tela resolve 80% das telas CRUD sem código. Copie também o alerta: o cache de METADADO precisa de invalidação explícita (um número de versão de configuração no payload, invalidando o cache quando muda) — senão você reproduz o bug do Salesforce em que o admin muda o layout e ninguém vê até relogar.

### 11. UI API: o endpoint que devolve DADO + METADADO juntos, para que o cliente nunca hardcode campo

A User Interface API é a mesma API que a Salesforce usa para construir o Lightning Experience e os apps mobile. O recurso GET /ui-api/record-ui/{recordIds} devolve, numa única resposta: informação de LAYOUT para os tipos de layout pedidos, os DADOS dos registros, e os METADADOS de objeto dos tipos envolvidos e de objetos aninhados (pedir uma Account devolve também o objectInfo de User, porque OwnerId aponta para User). Parâmetros: layoutTypes = 'Compact' (só campos-chave) ou 'Full' (padrão); modes = 'Create' | 'Edit' | 'View' (padrão), que determina quais campos aparecem conforme a intenção; optionalFields no formato 'ObjectApiName.FieldName' (sem limite documentado de quantidade, mas o usuário precisa ter acesso); formFactor = 'Large' (desktop, padrão) | 'Medium' (tablet) | 'Small' (celular); childRelationships no formato 'ObjectApiName.ChildRelationshipName'; pageSize para paginar filhos; updateMru para registrar no 'usados recentemente'. O benefício declarado: 'you get data and metadata in a single response that matches metadata changes made to the org by Salesforce admins, and you don't have to worry about layouts, picklists, field-level security, or sharing'.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.uiapi.meta/uiapi/ui_api_resources_record_ui.htm; https://developer.salesforce.com/docs/atlas.en-us.uiapi.meta/uiapi/ui_api_get_started.htm; https://developer.salesforce.com/blogs/2018/01/introduction-salesforce-ui-api

**Licao para a Tracbel:** COPIAR — este é o desenho de API que faz o requisito 'APIs para integração' e 'extensibilidade sem release' convergirem. Construa no .NET 8 um endpoint GET /api/ui/registro/{objeto}/{id}?modo=view|edit|create&formato=compacto|completo que devolve { metadadoDoObjeto, definicaoDaTela, valores, permissoes, opcoesDePicklist }. Efeito prático: quando o negócio adiciona um campo pelo admin, o React NÃO precisa de deploy — ele já renderiza o campo novo porque a definicaoDaTela mudou. E o mesmo endpoint serve o app mobile e integrações de terceiros. O parâmetro 'modes' (View/Edit/Create) é um detalhe de desenho que vale copiar literalmente: os campos visíveis na criação são um conjunto DIFERENTE dos da edição, e resolver isso no metadado evita ifs espalhados pelo front. Cuidado a evitar: NÃO devolva a árvore inteira de objetos relacionados por padrão (a UI API devolve objectInfos aninhados e as respostas ficam gordas) — devolva sob demanda via um parâmetro explícito.

### 12. Report Types: o contrato curado que permite ao usuário final montar relatório sozinho sem enxergar o schema

Um Report Type define o conjunto de REGISTROS e de CAMPOS disponíveis para um relatório, baseado nos relacionamentos entre um objeto primário e seus relacionados. Existem report types standard e Custom Report Types, criados pelo admin para expor objetos e campos adicionais. Limites: até 1.000 campos por custom report type; máximo de 60 referências de objeto. Custom report types podem ser do tipo 'with' (só registros que têm o filho) ou 'with or without'. O usuário final então usa o Lightning Report Builder, que é drag-and-drop: o painel Fields lista os campos do report type organizados por pasta, e agrupar é arrastar um campo para uma drop zone. Formatos: tabular (lista simples), summary (agrupa linhas, subtotais, gráficos), matrix (agrupa por linha E coluna) e joined. Agrupamentos: summary e joined suportam até 3 níveis; matrix suporta 2 agrupamentos de linha e 2 de coluna. Fórmulas que o próprio usuário escreve: row-level formulas (calculam em CADA linha, criadas pelo painel OUTLINE, não pelo painel Fields) — 2 por relatório, cada uma referenciando até 5 campos únicos, e NÃO podem referenciar bucket fields, summary formulas nem outras row-level formulas, nem funcionam em Classic, joined reports, cross filters, 'with or without' report types, reporting snapshots ou Apex API; e custom summary formulas — 5 por relatório. Bucket fields (segmentação ad hoc, sem criar campo no objeto): 5 por relatório, 20 buckets por campo, 20 valores por bucket — e você NÃO pode filtrar pelo campo que foi bucketizado num dashboard.

**Evidencia:** https://help.salesforce.com/s/articleView?id=rd_reports_dashboards_limits.htm; https://help.salesforce.com/s/articleView?id=analytics.reports_formulas_row_level_limits.htm; https://help.salesforce.com/s/articleView?id=sf.reports_bucketing_adding.htm; https://trailhead.salesforce.com/content/learn/modules/lex_implementation_reports_dashboards/lex_implementation_reports_dashboards_report_formats

**Licao para a Tracbel:** COPIAR o conceito de Report Type — é A resposta para 'como o usuário monta relatório sozinho'. O erro clássico (e o que o Vórtice sofre, conforme a memória sobre o relatório TBA_101XX3 com filtro de carteira defeituoso) é dar ao usuário um construtor de query genérico sobre o schema cru. A solução do Salesforce é um intermediário curado: o time de 3 devs define, digamos, 6 a 10 'Fontes de Relatório' (Oportunidades, Oportunidades com Itens, Clientes com Equipamentos, Atividades por Vendedor, Propostas com Aprovações, Faturamento por Carteira), cada uma com joins e campos já resolvidos, nomes em português de negócio e permissões aplicadas. Em .NET isso vira uma view/IQueryable nomeada + um manifesto de campos. Só DEPOIS você constrói o builder drag-and-drop em cima disso. Copie especificamente: bucket fields (o usuário cria faixas — 'Valor: até 200k / 200k-800k / acima de 800k' — sem pedir campo novo ao TI) e row-level formulas, ambos limitados e seguros. DESCARTE no MVP: joined reports, matrix com 2×2 agrupamentos e cross filters.

### 15. Change Sets: exatamente o antipadrão de deploy que a Tracbel não deve reproduzir

Limites e restrições documentadas: até 10.000 arquivos de metadados por change set (in ou outbound); NÃO é possível usar change set para DELETAR ou RENOMEAR componentes (para deletar, você tem que usar a interface web na org de destino); depois de fazer upload de um change set você NÃO pode alterar seu conteúdo — se descobrir uma dependência faltando, tem que CLONAR o change set, adicionar os componentes e subir de novo; a org de origem fica TRAVADA durante a validação de um outbound change set e a org de destino fica travada durante o deploy de um inbound (durante o lock você ainda lê e escreve DADOS, mas não pode fazer nenhuma mudança de setup que altere metadados); se um componente referencia outro que não existe nem no destino nem no change set, o deploy FALHA; e componentes não suportados por change sets precisam ser migrados MANUALMENTE, repetindo os passos à mão na org de destino.

**Evidencia:** https://help.salesforce.com/s/articleView?id=platform.changesets_best_practices.htm; https://help.salesforce.com/s/articleView?id=sf.changesets_implementation_notes.htm; https://developer.salesforce.com/docs/atlas.en-us.salesforce_app_limits_cheatsheet.meta/salesforce_app_limits_cheatsheet/salesforce_app_limits_platform_metadata.htm

**Licao para a Tracbel:** DESCARTAR integralmente — mas conheça o antipadrão para não reinventá-lo. 'Não pode deletar', 'não pode editar depois de subir', 'trava a org', 'sem diff', 'sem histórico', 'itens não suportados vão manualmente' é a descrição exata de um processo de deploy que não é código. A Tracbel tem git, .NET e EF Core: deploy é `dotnet ef database update` + publish do artefato, com PR revisado e rollback por tag. O único cuidado real é que a CONFIGURAÇÃO (definições de campo, telas, regras) também precisa passar pelo mesmo pipeline — se o admin puder mudar configuração direto na produção pela tela, você recria o problema do change set ao contrário: produção diverge de homologação e ninguém sabe por quê. Regra a escrever no CLAUDE.md do projeto: configuração estrutural (campo, tela, regra de fluxo) vem do git; configuração operacional (limites, listas de valores, mapeamentos) pode ser editada em produção MAS com trilha de auditoria e export para o git.

### 16. SFDX, scratch orgs e unlocked packages: modularização como artefato imutável e versionado

Scratch org é um deploy 'source-driven e descartável' de código e metadados, cuja forma é definida por um arquivo de definição (o blueprint) compartilhável entre os membros do time, para que todos tenham a mesma org base. Edições suportadas: Developer, Enterprise, Group e Professional. Alocações: scratch orgs ATIVAS simultâneas — 3 em Developer Edition/trial, 40 em Enterprise, 100 em Unlimited, 100 em Performance; alocação DIÁRIA — 6, 80, 200 e 200 respectivamente. Armazenamento por scratch org: 500 MB de dados e 50 MB de arquivos. Unlocked packages: fornecem 'artefatos imutáveis, versionáveis' que tornam deploys repetíveis, scriptáveis e rastreáveis — o MESMO artefato que passou nos testes de CI e no UAT é o que se instala em produção; dão versionamento completo, então você sabe qual instância de produção roda qual versão e pode fazer upgrade de qualquer ambiente para a versão certa; e mantêm as customizações organizadas, porque aparecem como pacotes instalados com seu conteúdo listado como metadados associados — você vê que metadado pertence a que pacote. Variante 'org-dependent unlocked package': permite criar pacotes que DEPENDEM de metadados não empacotados existentes na org de destino. Em 2GP (second-generation packaging), 'version control being the source of truth, there are no packaging or patch orgs' e todas as operações de empacotamento são feitas pela Salesforce CLI.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.sfdx_dev.meta/sfdx_dev/sfdx_dev_scratch_orgs.htm; https://developer.salesforce.com/docs/atlas.en-us.sfdx_dev.meta/sfdx_dev/sfdx_dev_scratch_orgs_editions_and_allocations.htm; https://developer.salesforce.com/docs/atlas.en-us.sfdx_dev.meta/sfdx_dev/sfdx_dev_unlocked_pkg_intro.htm; https://developer.salesforce.com/docs/atlas.en-us.sfdx_dev.meta/sfdx_dev/sfdx_dev_unlocked_pkg_org_dependent.htm; https://developer.salesforce.com/docs/atlas.en-us.sfdx_dev.meta/sfdx_dev/sfdx_dev_dev2gp.htm

**Licao para a Tracbel:** COPIAR duas ideias, DESCARTAR a maquinaria. IDEIA 1 (copiar): ambiente de dev descartável e reproduzível a partir de arquivo versionado. Em .NET isso é um docker-compose.yml + migrations + seeder de massa: `docker compose up && dotnet ef database update && dotnet run --project Tools.Seed` deve dar a um dev novo um CRM funcional em minutos. Isso é o requisito 'código que qualquer dev do time saiba estender' — que começa em 'qualquer dev consegue RODAR em 10 minutos'. IDEIA 2 (copiar): o artefato que passou no CI é o MESMO que vai para produção — nunca rebuildar entre homologação e produção. DESCARTAR: unlocked packages, ancestry de versão, org-dependent packages. Modularização por pacote existe porque a Salesforce não tem monorepo nem solution .NET. Para 2-3 devs, um monorepo com projetos .NET separados por domínio (Tracbel.Crm.Vendas, Tracbel.Crm.Clientes, Tracbel.Crm.Integracoes) e fronteiras impostas por regra de arquitetura (ArchUnitNET ou NetArchTest no CI) dá a mesma separação de responsabilidades sem gerência de versão de pacote.

### 17. O gate de 75% de cobertura e os níveis de teste do deploy: o que copiar e o que evitar

Para fazer deploy de Apex em produção é preciso ter no mínimo 75% do Apex coberto por testes unitários, medido sobre a org INTEIRA; além disso, TODO trigger precisa ter pelo menos UMA linha de cobertura. Ao fazer deploy em produção, por padrão cada teste unitário do namespace da org é executado. Cálculo: chamadas a System.debug NÃO contam para a cobertura, e classes/métodos de teste também não contam. A recomendação oficial é buscar 100% quando possível, mas com a ressalva explícita de que 'o foco não deve estar no percentual coberto e sim em cobrir casos de uso importantes'. No deploy() do Metadata API, o DeployOptions controla tudo: checkOnly=true faz um deploy de VALIDAÇÃO sem salvar componentes; rollbackOnError 'must be set to true if you're deploying to a production org'; ignoreWarnings decide se warnings viram erro; runTests lista classes específicas; e testLevel aceita NoTestRun (só ambientes de desenvolvimento), RunSpecifiedTests (cada classe e trigger do pacote precisa individualmente de 75%), RunLocalTests (todos os testes da org exceto os de pacotes gerenciados/unlocked — é o padrão para deploy em produção com Apex), RunRelevantTests (beta: a Salesforce identifica automaticamente os testes relevantes analisando o payload do deploy, mantendo o requisito de 75% por classe/trigger) e RunAllTestsInOrg (inclui testes de pacotes gerenciados). Depois de uma validação bem-sucedida, deployRecentValidation() permite Quick Deploy: reaproveita os componentes já validados SEM rodar os testes de novo.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_code_coverage_intro.htm; https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_code_coverage_best_pract.htm; https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_deploy.htm

**Licao para a Tracbel:** COPIAR o Quick Deploy e o RunRelevantTests; DESCARTAR o gate percentual global. O gate de 75% da Salesforce é um controle de plataforma multi-tenant (impedir que um tenant suba lixo que derrube o pod), e produz o efeito perverso conhecido: times escrevem testes sem assert só para bater o número. ### 21. Collaborative Forecasting: categorias, tipos de previsão, cotas, ajustes e rollup cumulativo vs simples

### 23. Modelo de permissão: perfil mínimo + permission sets compostos, com muting para SUBTRAIR

A orientação oficial: 'Whenever possible, use the Minimum Access Salesforce profile (or a clone of it), and then use permission sets and permission set groups to grant users only the permissions they require.' ### 24. Apex Enterprise Patterns (fflib): a resposta do ecossistema Salesforce ao requisito 'OO forte'

O padrão de referência do ecossistema, apresentado originalmente no Dreamforce 2012 e mantido como biblioteca open source (apex-enterprise-patterns/fflib-apex-common), organiza o código em quatro camadas com responsabilidades separadas: SERVICE LAYER (forma o 'núcleo durável' da aplicação, expõe operações de negócio orientadas a caso de uso, é o ponto de entrada de qualquer canal — trigger, tela, API), DOMAIN LAYER (fflib_SObjectDomain — encapsula comportamento e validação de um objeto; provê funcionalidade de trigger-handler cujos métodos garantem que os callbacks sejam chamados nos momentos certos), SELECTOR LAYER (encapsula a lógica de CONSULTA a objetos standard e custom e alimenta as camadas Domain e Service — nenhuma query solta no meio da lógica) e UNIT OF WORK (fflib_SObjectUnitOfWork, com registerNew para inserir e registerDirty para atualizar, acumulando as mudanças e cometendo tudo em bloco). Os benefícios declarados: gerenciar melhor recursos governados (como DML), encorajar melhor separação de responsabilidades na lógica, e impor boas práticas de codificação. A Salesforce publica módulos de Trailhead oficiais sobre Separation of Concerns, Service Layer, Domain Layer e Selector Layer.

**Evidencia:** https://github.com/apex-enterprise-patterns/fflib-apex-common; https://developer.salesforce.com/page/Apex_Enterprise_Patterns_-_Service_Layer; https://trailhead.salesforce.com/content/learn/modules/apex_patterns_dsl; https://trailhead.salesforce.com/content/learn/modules/apex_patterns_sl/apex_patterns_sl_apply_uow_principles

**Licao para a Tracbel:** COPIAR as camadas, DESCARTAR a biblioteca. É notável que o ecossistema Salesforce, numa linguagem sem generics decentes e sem DI nativo, tenha convergido para Service + Domain + Selector + Unit of Work — que é literalmente Application Service + Domain Model + Repository + DbContext do .NET. Em EF Core você ganha o Unit of Work DE GRAÇA (o DbContext É um unit of work com change tracking) e o Selector é um Repository/IQueryable. A lição a levar é a REGRA, não o código: (1) nenhuma query fora da camada de acesso a dados — isso é o que impede o time de 3 pessoas de espalhar SQL por controllers; (2) a lógica de negócio vive no Service e no Domain, e o gatilho (endpoint HTTP, job, evento de integração, tela) é só um adaptador fino — assim a MESMA regra de 'gerar ação após faturamento' roda igual vinda da API, do batch noturno ou da tela, que é exatamente o tipo de divergência que produz o bug de '68% de falha na ação 900'; (3) o Domain concentra validação por entidade, não regras espalhadas em N validadores. Escreva isso como três regras no CLAUDE.md do repositório e imponha no CI com NetArchTest — assim 'qualquer dev do time sabe estender' vira uma propriedade verificada, não uma esperança.

**Licao para a Tracbel:** COPIAR os PADRÕES, descartar as cotas. As cotas do Salesforce existem por multi-tenancy; a Tracbel controla o próprio servidor. Mas os três padrões de composição valem: (1) OPERAÇÕES EM LOTE de primeira classe — para a integração com TOTVS/JDE, exponha POST /api/clientes/lote aceitando N registros com resultado individual por item (o modelo do sObject Collections), em vez de forçar o integrador a fazer N chamadas; (2) TRANSAÇÃO COMPOSTA — um endpoint que aceita várias operações encadeadas, onde a saída de uma alimenta a entrada da próxima (criar Cliente + criar Oportunidade + criar Item, tudo ou nada), que é o composite/graph; (3) LIMITE EXPLÍCITO E OBSERVÁVEL — mesmo sem cobrar, publique um teto por cliente de integração e um endpoint /api/limites que devolve consumo atual. A Salesforce expõe /services/data/vXX.0/limits justamente para o integrador se autorregular; sem isso, um job mal escrito derruba o CRM inteiro às 3h da manhã e ninguém sabe qual sistema foi. Dado o histórico da Tracbel com integrações (RD Station, TALLOS, Doc Manager, TOTVS), instrumentação por cliente de integração desde o dia 1 é obrigatória, não opcional.
