# Modelo de segurança do Microsoft Dynamics 365 / Dataverse — anatomia completa, comparação com Salesforce e recomendação de modelo de permissão para o CRM próprio da Tracbel (.NET 8 + EF Core + SQL Server + React, ~130 usuários)

> Pesquisa automatizada - workflow `crm-tracbel-pesquisa-profunda`, 30/08/2026.

## Resumo

O Dataverse resolve autorização em DUAS fases: (1) "privilege check" — o usuário tem o verbo (Create/Read/Write/Delete/Append/AppendTo/Assign/Share) para aquela tabela? — e (2) "access check" — para QUAIS linhas, via a matriz privilégio x profundidade (None / User(Basic) / Business Unit(Local) / Parent:Child BU(Deep) / Organization(Global)). Essa matriz é o coração do modelo e é barata: resolve-se com OwnerId + OwningBusinessUnitId gravados na própria linha, sem join. Todo o resto são camadas de exceção com custo crescente: Owner Teams (barato), Access Teams e sharing linha-a-linha (caro — tudo vai para a tabela PrincipalObjectAccess/POA, que a Microsoft nem permite limpar por DELETE direto), Hierarchy Security (Manager/Position, recomendação oficial de no máximo 50 usuários efetivos sob um gestor) e Column Security (FieldSecurityProfile + FieldPermission, com o comportamento perigoso de devolver NULL silencioso na API). O modelo é 100% ADITIVO: não existe "deny" — "se você deu Organization Read em contato, não dá pra esconder um registro depois". O Salesforce é mais rico onde o Dataverse é pobre (sharing rules declarativas, restriction rules com deny real, territory management) e o Dataverse é mais simples e mais barato onde o Salesforce é pesado (a matriz privilégio x depth substitui OWD + role hierarchy + sharing rules sem materializar linhas). Para a Tracbel (130 usuários, multiempresa, carteiras por linha de negócio, hierarquia de vendas) a recomendação é: copiar a matriz privilégio x depth + Owner Teams + OwningUnitId "modernizado"; cortar sharing linha-a-linha para usuário individual, access teams auto-criados, position hierarchy e os privilégios Append/AppendTo; e construir cedo o endpoint "por que este usuário vê este registro".

## Entidades / objetos mapeados

### `BusinessUnit`

**Funcao:** Nó da árvore organizacional que define fronteira de segurança. Uma raiz imutável por ambiente. Determina a coluna OwningBusinessUnit dos registros criados (no modelo clássico).

**Campos-chave:** businessunitid (PK), parentbusinessunitid (auto-relacionamento, define a árvore), name

**Relacoes:** 1:N com SystemUser, Team, Role e com praticamente toda tabela de negócio via OwningBusinessUnit. Não pode ser deletada se for a raiz.

### `SystemUser`

**Funcao:** Usuário. Carrega a BU de origem, o gestor (para Manager Hierarchy) e o cargo (para Position Hierarchy). Application users são SystemUser sem licença ligados a um app registration do Entra.

**Campos-chave:** systemuserid (PK), businessunitid, parentsystemuserid (campo 'Manager'), positionid, applicationid (para application users)

**Relacoes:** N:N com Role (atribuição direta), N:N com Team (teammembership_association), N:N com FieldSecurityProfile (systemuserprofiles_association)

### `Team`

**Funcao:** Agrupamento de usuários. TeamType define o comportamento: Owner (possui registros + recebe roles), Access (não possui, recebe shares), AAD Security Group e AAD Office Group (como Owner, mas membership derivada do Entra em runtime). Cada BU tem um default team gerenciado pelo sistema.

**Campos-chave:** teamid (PK), teamtype, businessunitid, systemmanaged (true para access teams auto-criados), teamtemplateid, azureactivedirectoryobjectid, membershiptype (Members / Owners / Guests / Members and guests)

**Relacoes:** N:N com SystemUser, N:N com Role, 1:N a partir de TeamTemplate (relação parental — deletar o template deleta os times)

### `TeamTemplate`

**Funcao:** Molde dos access teams auto-criados (system-managed): define a tabela alvo e a máscara de direitos concedida a quem entra no time daquela linha. Máximo 4 por tabela (MaxAutoCreatedAccessTeamsPerEntity), em no máximo 100 tabelas (MaxEntitiesEnabledForAutoCreatedAccessTeams).

**Campos-chave:** teamtemplateid (PK), objecttypecode (tabela alvo), defaultaccessrightsmask (bitmask de AccessRights)

**Relacoes:** 1:N com Team (parental, cascade delete). Requer EntityMetadata.AutoCreateAccessTeams = true na tabela alvo.

### `Role (security role)`

**Funcao:** Conjunto nomeado de pares (privilégio, access level). Atribuível a usuário, owner team e group team. Cumulativa e nunca subtrativa. No modelo clássico é duplicada automaticamente em cada BU filha quando criada na raiz.

**Campos-chave:** roleid (PK), businessunitid, name, ismanaged; opção 'Member's privilege inheritance' (Team privileges only vs Direct User (Basic) access level and Team privileges)

**Relacoes:** N:N com SystemUser e Team; N:N com Privilege via RolePrivileges, onde o depth (Basic/Local/Deep/Global) é armazenado

### `PrincipalObjectAccess (POA)`

**Funcao:** Tabela onde TODO compartilhamento linha-a-linha é materializado. Consultada sempre que o usuário tenta acessar registro que não possui e para o qual não tem privilégio de depth suficiente. DELETE direto não é suportado — só revoke pela via correta.

**Campos-chave:** principalobjectaccessid (PK), objectid, objecttypecode, principalid, principaltypecode, accessrightsmask (int, direitos explícitos), inheritedaccessrightsmask (int, SystemRequired, direitos herdados por cascade), changedon

**Relacoes:** objectid → qualquer registro; principalid → SystemUser, Team ou Organization. EntitySetName: principalobjectaccessset. OwnershipType: None.

### `FieldSecurityProfile / FieldPermission`

**Funcao:** Segurança de coluna. O profile agrupa permissões e é atribuído a usuários e times; cada FieldPermission define o acesso a UMA coluna. Escopo é organization-wide e ortogonal ao acesso à linha. System Administrator sempre bypassa.

**Campos-chave:** FieldPermission: fieldpermissionid, fieldsecurityprofileid, entityname, attributelogicalname, CanCreate, CanRead, CanUpdate, CanReadUnmasked (choice field_security_permission_type)

**Relacoes:** FieldSecurityProfile N:N SystemUser (systemuserprofiles_association) e N:N Team (teamprofiles_association); 1:N FieldPermission (lk_fieldpermission_fieldsecurityprofileid)

### `PrincipalObjectAttributeAccess (POAA)`

**Funcao:** Compartilhamento de CAMPO protegido em UMA linha específica ('field sharing'). Manipulada por create/update/delete direto na tabela, não por mensagem dedicada.

**Campos-chave:** principalobjectattributeaccessid, attributeid (usa o AttributeMetadata.MetadataId, NÃO o logical name), objectid, principalid, readaccess, updateaccess

**Relacoes:** attributeid → metadata da coluna; objectid → registro; principalid → user ou team

### `MaskingRule / AttributeMaskingRule`

**Funcao:** Regras de mascaramento de colunas protegidas: em vez de retornar vazio, devolve valor parcialmente ofuscado. AttributeMaskingRule liga a regra à coluna. Combina com CanReadUnmasked (All Records / One record / Not Allowed) para permitir leitura desmascarada controlada.

**Campos-chave:** MaskingRule: name, displayname, maskedcharacter, testdata, maskedtestdata, richtestdata

**Relacoes:** AttributeMaskingRule liga MaskingRule a uma coluna segura específica

### `Position`

**Funcao:** Nó da hierarquia de CARGOS usada pela Position Hierarchy Security — independente do organograma real e atravessa business units. Um usuário só pode estar em UMA posição por hierarquia.

**Campos-chave:** positionid, name, parentpositionid, description

**Relacoes:** 1:N com SystemUser (campo Position no formulário do usuário). Exige o privilégio 'Assign position for a user' para atribuir.

### `Audit`

**Funcao:** Log de auditoria do Dataverse. Configurável em 3 níveis (environment / tabela / coluna). Armazenado em log storage, não no database storage — daí o atraso na exibição. Retenção default 'Forever'; custom até 24.855 dias, carimbada por linha no momento da criação.

**Campos-chave:** registros de create/update/delete, mudanças de share, associação N:N, mudanças de security role, deleção de logs. Valores grandes truncados em 5 KB / ~5.000 caracteres.

**Relacoes:** ~31 tabelas não podem ser auditadas (CanModifyAuditSettings=false): ActivityPointer, Annotation, Workflow, Service, Subject, Template, etc. Acesso analítico via Web API/SDK ou Azure Synapse Link — não há export pela UI.

### `Organization (settings relevantes de segurança)`

**Funcao:** Configurações globais que mudam o comportamento do modelo de segurança inteiro.

**Campos-chave:** ShareToPreviousOwnerOnAssign ('Share reassigned records with original owner'); EnableOwnershipAcrossBusinessUnits; RecomputeOwnershipAcrossBusinessUnits; AlwaysMoveRecordToOwnerBusinessUnit; ManagersMustBeInSameOrParentBusinessUnitAsReports (default true); AuthorizationEnableHSMForDisabledUsers; MaxAutoCreatedAccessTeamsPerEntity (4); MaxEntitiesEnabledForAutoCreatedAccessTeams (100); IsAccessCheckerAllUsersEnabled; IsAccessCheckerNonAdminAllUsersEnabled; StoreLabelNameforPicklistAudits

**Relacoes:** Editáveis via OrganizationSettingsEditor / OrgDBOrgSettings tool

## Achados

### 1. O coração do modelo: duas checagens separadas (privilege check → access check), e o depth NÃO participa da primeira

O Dataverse faz DUAS barreiras distintas para qualquer ação (Create, Read, Write, Delete, Append, Append To, Assign, Share). Primeiro o PRIVILEGE CHECK: o usuário tem o privilégio daquele verbo naquela tabela, direto pela role ou herdado de um time? A doc é explícita: "When creating or editing a security role, a privilege is granted to that role with a given access level. The access level isn't taken into account in the privilege check, this is done in the access check when the privilege check is passed." Só depois vem o ACCESS CHECK, que decide QUAIS linhas, avaliando 4 origens em paralelo: Ownership, Role access (o depth), Shared access (POA) e Hierarchy access. Na fase 1 a resposta é 'access denied — você não tem o privilégio'; na fase 2 a resposta é 'a linha não aparece'. Duas mensagens de erro diferentes, dois lugares diferentes para depurar.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/how-record-access-determined

**Licao para a Tracbel:** COPIAR, e é a decisão de arquitetura mais importante do projeto. Fase 1 = checagem em memória, O(1), a partir de um permission set cacheado (roleId → entidade → verbo → depth); serve para pintar/apagar botões no React e para o guard do endpoint. Fase 2 = um EF Core Global Query Filter que traduz o depth em predicado SQL. Separar as duas evita o erro clássico de CRM caseiro de tentar decidir tudo com um único IF gigante no service, e dá duas mensagens de erro distintas para o suporte ('você não pode editar pedidos' vs 'este pedido não é da sua carteira').

### 2. A matriz privilégio x access level: 8 verbos x 5 profundidades, e o mapeamento UI ↔ SDK que confunde todo mundo

Os 8 privilégios de tabela são Create, Read, Write, Delete, Append, Append To, Assign, Share. Append = anexar o registro atual a outro (ex.: ter Append na anotação para colá-la numa oportunidade); Append To = permitir que outro registro seja anexado a este (ex.: ter Append To na oportunidade para receber a anotação). Em relacionamentos N:N o usuário precisa de Append nas DUAS tabelas. Cada privilégio recebe um access level. Na UI: Organization / Parent:Child Business Unit / Business Unit / User / None. No SDK e na documentação de desenvolvedor os MESMOS cinco níveis se chamam Global / Deep / Local / Basic / None. Regra de subsunção explícita: 'Users with organization access automatically have all other types of access'; Parent:Child implica Business Unit e User; Business Unit implica User. Para tabelas Organization-owned (e para privilégios Miscellaneous e Privacy-related) só existem Organization ou None — vira liga/desliga.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/security-roles-privileges e https://learn.microsoft.com/en-us/power-apps/developer/data-platform/security-concepts

**Licao para a Tracbel:** COPIAR a matriz, SIMPLIFICAR os verbos. Adote 6 verbos (Read, Create, Update, Delete, Assign, Share) e 5 depths (None, Own, Unit, UnitAndChildren, All). DESCARTE Append/AppendTo: eles existem porque o Dataverse tem um motor genérico de relacionamento e precisa autorizar o ato de ligar duas linhas; num CRM .NET com entidades explícitas isso é ruído, e é onde 100% dos admins de Dynamics erram. Guarde a matriz numa tabela `RolePrivilege(RoleId, EntityName, Verb, Depth)` — assim uma entidade nova entra como LINHAS, não como código, que é exatamente o requisito de 'extensibilidade sem release'.

### 3. O modelo é estritamente aditivo — não existe DENY em lugar nenhum

Frase textual da documentação: "A key concept of Dataverse security to understand is all privilege grants are accumulative with the greatest amount of access prevailing. If you gave broad organization level read access to all contact records, you can’t go back and hide a single record." O efetivo do usuário é a UNIÃO de: roles atribuídas diretamente + roles dos times de que participa + registros compartilhados + hierarquia. A doc de desenvolvedor reforça: 'the least restrictive evaluation of all the security roles that apply'. A própria doc admite o efeito colateral cultural: 'one of the most common administrative mistakes is getting frustrated with permissions and just over granting access. Very quickly a well-crafted security model starts looking like Swiss cheese'.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/wp-security-cds

**Licao para a Tracbel:** COPIAR a semântica aditiva (é a única que um time de 2-3 devs consegue depurar de cabeça), mas ADICIONAR uma única exceção controlada que o Dataverse não tem: um flag de confidencialidade na própria linha (ex.: `IsRestrito` + `RestritoParaTeamId` em Oportunidade/Cliente estratégico), avaliado ANTES da união. Um único ponto de deny, explícito, com nome, auditado — não um sistema de regras de negação. O Salesforce levou 20 anos para adicionar isso (Restriction Rules) justamente porque só-aditivo não resolve 'só a diretoria vê esta negociação'.

### 4. Business Units: fronteira de segurança, não organograma — e a coluna OwningBusinessUnit é o que realmente decide

Todo banco Dataverse tem UMA business unit raiz, imutável, e você cria BUs filhas em árvore. Todo usuário pertence a exatamente uma BU. Cada REGISTRO tem a coluna 'Owning Business Unit', que por padrão recebe a BU do usuário no momento da criação e (no modelo clássico) não pode ser alterada. O guia de implementação do Dynamics 365 é enfático contra o mapeamento 1:1 com organograma: "It's a best practice to minimize the number of business units in your implementation. Base them on access control requirements instead of mapping the organizational chart to business units" e, na seção de performance da hierarchy security, "Avoid creating a large number of business units. Instead, create fewer business units and add hierarchy security". A doc também alerta: se você sincroniza dados entre ambientes com a coluna Owning Business Unit no schema, o job falha com violação de FOREIGN KEY quando o destino não tem a mesma BU.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/wp-security-cds e https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/security-strategy-product-ce

**Licao para a Tracbel:** COPIAR o conceito, SIMPLIFICAR a forma. 'Multiempresa' na Tracbel deve virar `OwningUnitId` (FK para uma tabela Unidade) gravado em TODA linha transacional — cliente, oportunidade, pedido, OS. É essa coluna, e não a unidade do usuário, que decide o acesso. Faça a árvore RASA: Holding → Empresa (Agro / Construção / ...) → no máximo Filial. Não modele os ~130 usuários em 30 BUs; modele 5-10 unidades e resolva o resto com times. E aprenda com o alerta de FK: `OwningUnitId` precisa existir e bater entre DEV/HML/PRD, ou toda carga de dados quebra.

### 5. Modernized Business Units / Matrix data access: o mesmo usuário com roles de várias BUs, sem herança

Com o switch 'Record ownership across business units' ligado (setting EnableOwnershipAcrossBusinessUnits), o modelo muda de hierárquico para matricial: você atribui ao MESMO usuário uma security role POR business unit, e a doc afirma que "the user’s business unit is no longer relevant in determining the user’s access to records" — quem manda é o Owning Business Unit da linha. O usuário pode ser dono de registros em qualquer BU desde que tenha uma role (de qualquer BU) com Read na tabela. Para permitir que o usuário ESCOLHA a BU dona do registro, é preciso dar à role o privilégio Append To na tabela Business Unit com nível LOCAL. Settings correlatos: RecomputeOwnershipAcrossBusinessUnits (o sistema trava por até 5 minutos recomputando) e AlwaysMoveRecordToOwnerBusinessUnit=false (para o registro NÃO migrar de BU quando muda de dono). O roteiro de migração recomendado inclui 'removing record ownership through Teams' e 'Modify all input forms to include the Owning business unit column and add automation to set it to the correct owning business unit by default'.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/modernized-business-units-security e https://learn.microsoft.com/en-us/power-platform/admin/wp-security-cds#matrix-data-access-structure-modernized-business-units

**Licao para a Tracbel:** COPIAR — e nascer já assim, sem a versão legada. Ou seja: no CRM Tracbel, `RoleAssignment` deve ser `(UserId, RoleId, UnitId)`, não `(UserId, RoleId)`. Um gerente que responde por Agro e Construção recebe duas linhas. O acesso resolve por `row.OwningUnitId ∈ unidades_onde_o_usuário_tem_essa_role`. E siga o alerta deles: o `OwningUnitId` precisa ser preenchido por DEFAULT automático no formulário (a partir da unidade do vendedor/carteira), com override apenas para perfis privilegiados — senão o usuário erra e o registro some da visão de todo mundo.

### 6. O custo do modelo hierárquico clássico: cascade de Assign move os filhos de BU e pode tirar acesso do dono

O relacionamento 1:N tem CascadeConfiguration com as ações Assign, Delete, Merge, Reparent, Share, Unshare, e os valores Cascade (All), Active, UserOwned, NoCascade, RemoveLink, Restrict. O padrão de Assign é Cascade All: ao reatribuir o pai, os filhos mudam de dono E de business unit. A documentação dá dois exemplos de armadilha: (1) você troca o dono do pai, os filhos passam para o novo dono mas permanecem na BU antiga e o novo dono perde acesso a eles; (2) você troca a BU do pai, ela cascateia para os filhos, e o dono dos filhos perde acesso aos próprios registros — 'the record's owner privilege for the child records isn't validated'.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/configure-entity-relationship-cascading-behavior

**Licao para a Tracbel:** EVITAR o cascade automático de propriedade. No CRM Tracbel, transferir uma carteira deve ser uma OPERAÇÃO DE DOMÍNIO explícita ('Transferir carteira do vendedor A para B'), transacional, auditada, que reescreve OwnerId/OwningUnitId de um conjunto conhecido de linhas e reporta o resultado — não um efeito colateral emergente de um relacionamento. Isso mata na origem a classe de bug 'mudei o gerente e sumiram 400 pedidos', que é literalmente o problema já registrado no legado Vórtice (hierarquia presa no usuário antigo).

### 7. Teams: quatro tipos com custos e semânticas bem diferentes

(1) OWNER TEAM: possui registros e recebe security roles; membros adicionados manualmente; acesso completo aos registros que o time possui. (2) ACCESS TEAM (user-created): NÃO possui registros e NÃO recebe roles; você COMPARTILHA registros com ele (GrantAccess) e os membros ganham direitos de acesso pontuais. (3) ACCESS TEAM auto-criado (system-managed): criado pelo sistema para UMA linha específica, a partir de um TeamTemplate; nasce quando o primeiro usuário é adicionado via AddUserToRecordTeamRequest. (4) MICROSOFT ENTRA GROUP TEAM (Security ou Office): igual ao owner team (possui registros, recebe roles) mas a MEMBRESIA é derivada dinamicamente do Entra ID em runtime. Toda BU tem um default team gerenciado pelo sistema, com todos os usuários daquela BU, que não pode ser editado manualmente. Detalhe crítico do grupo Entra: 'the team member's Microsoft Entra group memberships are cached upon the team member's sign in... won't be reflected until the next time the team member logs in or when the system refreshes the cache (after 8 hours of continuous sign in)'. Só membership types 'Assigned' e 'Dynamic User' são suportados — 'Dynamic Device' não. Conversão Owner→Access é irreversível.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/manage-teams e https://learn.microsoft.com/en-us/power-platform/admin/manage-group-teams

**Licao para a Tracbel:** COPIAR o Owner Team e o Group Team; DESCARTAR os dois tipos de access team. Modele CARTEIRA como um Owner Team: `OwnerId` da linha aponta para user OU team (guarde `OwnerUserId` e `OwnerTeamId` nulos-excludentes, ou um `OwnerId` + `OwnerType`). O check vira `row.OwnerId IN (@userId, @teamIds...)` — um IN sobre uma lista curta, index-friendly, sem tabela de sharing. E copie o group team: mapeie grupo do Entra/AD → team do CRM, para que a entrada/saída de vendedor seja feita no AD pelo TI e não na tela do CRM (resolve diretamente o problema já mapeado no Vórtice de 'criar usuário toca 5-7 tabelas, sem API'). Só implemente o cache de membership com invalidação explícita no logout/refresh — 8 horas de defasagem é inaceitável para 130 usuários que trocam de carteira.

### 8. Member's privilege inheritance: o parâmetro que decide se a role do time vale para os registros do usuário

Toda security role tem a opção 'Member's privilege inheritance' com dois valores: 'Team privileges only' — o usuário só usa aquele privilégio para registros que o TIME possui; e 'Direct User (Basic) access level and Team privileges' (padrão para roles novas) — o usuário recebe o privilégio como se estivesse atribuído diretamente, podendo criar registros com ele mesmo como dono. A doc de acesso explicita: 'If the team has the Member's privilege inheritance set to Team privileges only, then the user will only be able to make use of that privilege for records owned by the team.' E há um alerta repetido em duas páginas: privilégios de criar/atualizar/excluir registros USER-OWNED não podem ser entregues só via role de time sem essa herança — o usuário ainda precisa de role própria.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/security-roles-privileges e https://learn.microsoft.com/en-us/power-platform/admin/how-record-access-determined

**Licao para a Tracbel:** SIMPLIFICAR: não copie o flag. Ele existe para resolver ambiguidade histórica e é a causa nº 1 de ticket 'o usuário está no time certo com a role certa e mesmo assim não consegue criar'. No CRM Tracbel adote UMA regra fixa: o permission set efetivo é a UNIÃO de todas as roles (diretas + de times), e o depth 'Own' significa `OwnerId ∈ {userId} ∪ {teamIds do usuário}`. Uma regra, sem switch, documentável em uma frase.

### 9. Access Team Templates: limites numéricos reais (4 por tabela, 100 tabelas) e o custo escondido

Um TeamTemplate define a tabela e os direitos de acesso (Read, Write, Append, Append To, Assign, Share) concedidos a quem entra no time daquela LINHA. Limites documentados, controlados por environment database settings via OrganizationSettingsEditor: MaxAutoCreatedAccessTeamsPerEntity — 'The default value is four' (máximo de templates por tabela); MaxEntitiesEnabledForAutoCreatedAccessTeams — 'The default value is 100' (máximo de tabelas habilitadas para access teams auto-criados). Habilitar exige AutoCreateAccessTeams=true na metadata da tabela. Regras que doem: mudar os direitos do template só afeta times NOVOS ('the changes are only applied to new system-managed access teams'); apagar o template apaga em cascata todos os times criados por ele; e para entrar no time o usuário precisa ter no mínimo Basic (User) Read na tabela E privilégio compatível com os direitos do template ('if the access team has the Delete access right on an account, the user must have the Delete privilege on the Account entity to join the team').

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/use-access-teams-owner-teams-collaborate-share-information e https://learn.microsoft.com/en-us/power-platform/admin/create-team-template-add-entity-form

**Licao para a Tracbel:** DESCARTAR inteiro. Access team auto-criado = um registro de Team + N linhas de POA por LINHA de negócio compartilhada. Para 130 usuários e um volume de oportunidades/pedidos de revenda, isso gera milhões de linhas de controle de acesso para resolver um problema que um Owner Team por carteira resolve com dezenas. Se aparecer o requisito 'time da oportunidade' (vendedor + especialista de produto + analista de crédito), resolva com uma tabela de domínio `OportunidadeParticipante(OportunidadeId, UserId, Papel)` e inclua-a explicitamente no query filter: `... OR EXISTS (SELECT 1 FROM OportunidadeParticipante p WHERE p.OportunidadeId = o.Id AND p.UserId = @me)`. Mesma funcionalidade, semântica de negócio legível, um índice, zero motor genérico.

### 10. PrincipalObjectAccess (POA): a tabela onde o compartilhamento vira dívida técnica

Todo compartilhamento linha-a-linha vive na tabela PrincipalObjectAccess. Schema real: PrincipalObjectAccessId (PK), ObjectId, ObjectTypeCode, PrincipalId, PrincipalTypeCode, AccessRightsMask (int, direitos explícitos) e InheritedAccessRightsMask (int, direitos herdados via cascade) — ou seja, DOIS bitmasks por linha, e o herdado é SystemRequired. 'Whenever users try to access a record that they don’t own or don't have the appropriate privilege in their security role, the system checks the POA table.' As fontes de crescimento documentadas: (a) setting 'Share reassigned records with original owner' (Organization.ShareToPreviousOwnerOnAssign) — cada reatribuição vira linha de POA; (b) access teams — cada usuário adicionado vira linha; (c) sharing direto usuário-a-usuário; (d) sharing INDIRETO — compartilhar com um time compartilha com todos os membros, e relacionamentos com cascade Share/Reparent propagam para TODOS os filhos ('All these permissions to access the child records are created in the POA table'). O killer: "Direct deletion on this table is not supported since it can break the security model defined for the organization. The correct way to clean up the POA table is by adjusting the security model, and revoking access that was previously given." Existe até um system job dedicado — 'Inherited access rights cleanup' — para limpar POA órfão depois de trocar cascade para Cascade None.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/manage-principalobjectaccess-storage e https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/principalobjectaccess

**Licao para a Tracbel:** CORTAR na origem — esta é a lição mais cara do documento. Se você construir uma tabela `RecordShare` no CRM Tracbel, imponha desde o commit inicial TRÊS travas: (1) compartilhar SOMENTE com Team, nunca com usuário individual (a própria MS recomenda: 'Sharing with a team is a more efficient way of sharing'); (2) NUNCA cascatear compartilhamento para registros filhos — se o usuário precisa ver as OS do cliente compartilhado, faça o query filter da OS olhar o compartilhamento do CLIENTE em runtime (um join), em vez de materializar uma linha por OS; (3) TTL obrigatório (`ExpiresAt` not null) + job de expurgo, para que a tabela seja auto-limpante. E defina desde já a operação inversa (revoke) — a MS gastou uma página inteira e um system job porque não definiu.

### 11. Os direitos de acesso são um bitmask com valores esparsos e não-óbvios

O enum AccessRights (Microsoft.Crm.Sdk.Messages, [Flags]) tem estes valores exatos: None=0 (0x00), ReadAccess=1 (0x01), WriteAccess=2 (0x02), AppendAccess=4 (0x04), AppendToAccess=16 (0x10), CreateAccess=32 (0x20), DeleteAccess=65536 (0x10000), ShareAccess=262144 (0x40000), AssignAccess=524288 (0x80000). Note que 8 (0x08) está pulado e há um salto enorme entre 32 e 65536 — evidência de compatibilidade retroativa acumulada desde o CRM 3.0. É esse int que vai no AccessRightsMask/InheritedAccessRightsMask da POA e no PrincipalAccess.AccessMask das mensagens GrantAccess / ModifyAccess / RevokeAccess.

**Evidencia:** https://learn.microsoft.com/en-us/dotnet/api/microsoft.crm.sdk.messages.accessrights?view=dataverse-sdk-latest

**Licao para a Tracbel:** COPIAR a técnica (bitmask [Flags] em int para direitos por linha é compacto e rápido de avaliar em C# e em SQL com `&`), DESCARTAR os valores. Defina o seu enum limpo e contíguo (Read=1, Update=2, Delete=4, Assign=8, Share=16) e NUNCA reordene depois — o valor persistido no banco vira contrato. Esse é o exemplo perfeito de por que a Microsoft não pode consertar: os buracos no enum são o preço de 20 anos de compatibilidade. Vocês têm a chance de nascer certo uma vez.

### 12. RetrieveAccessOrigin e Check Access: a Microsoft precisou construir uma API só para responder 'por que este usuário vê isto'

Existe a mensagem RetrieveAccessOrigin (ObjectId, LogicalName, PrincipalId), que devolve uma FRASE explicando a origem do acesso. As respostas possíveis são taxativas e revelam o modelo inteiro: 'PrincipalId is object owner', 'is member of team who is object owner', 'has access to (X) through hierarchy security', 'has direct poa access to object', 'is member of team who has poa access to object', 'is owner of a parent entity of object', 'has poa access to object's root entity', e o desolador 'Access origin could not be found. Access does not come from POA table or object ownership.' Na UI existe o botão 'Check Access', e o painel 'Who has access' precisa de DOIS settings de banco ligados via OrganizationSettingsEditor: IsAccessCheckerAllUsersEnabled e IsAccessCheckerNonAdminAllUsersEnabled. Existe também a API RetrieveAccessOrigin para descobrir de onde vem o acesso de um principal a uma tabela.

**Evidencia:** https://learn.microsoft.com/en-us/power-apps/developer/data-platform/security-sharing-assigning e https://learn.microsoft.com/en-us/power-platform/admin/how-record-access-determined

**Licao para a Tracbel:** COPIAR — e construir no SPRINT 1, não no final. Um endpoint `GET /api/security/explain?entity=Oportunidade&id={id}&userId={id}` que devolve a lista de motivos ('é o dono', 'é membro do time Carteira Agro MG que é dono', 'unidade da linha = Agro e o usuário tem role Vendedor@Agro com depth Unit', 'compartilhado até 30/09') e uma tela simples no React. Com 2-3 devs e 130 usuários, esse endpoint paga o próprio custo na primeira semana de suporte, e é o único jeito de um dev novo entender o modelo sem ler o código. É literalmente a ferramenta que a Microsoft teve que criar depois porque o modelo ficou opaco.

### 13. Hierarchy Security: Manager vs Position, o corte read-only entre direto e indireto, e o teto de 50 usuários

Duas variantes, ambas desligadas por padrão. MANAGER HIERARCHY: usa o campo Manager (ParentSystemUserId) do system user; por padrão 'a manager must be within the same business unit as the report, or in the parent business unit'; dá para relaxar com o setting ManagersMustBeInSameOrParentBusinessUnitAsReports=false. POSITION HIERARCHY: uma árvore de cargos (tabela Position) independente do organograma real, atravessa business units, 'a user can be tagged only with one position in a given hierarchy'. A distinção fina que quase ninguém sabe: para o subordinado DIRETO o gestor tem Read, Write, Append, AppendTo; para o subordinado INDIRETO (mais fundo na cadeia) o acesso é SOMENTE LEITURA. O parâmetro Depth limita quantos níveis abaixo o acesso read-only alcança. Pré-requisito absoluto: o gestor precisa ter no mínimo privilégio Read nível User na tabela ('if a manager doesn’t have Read access to the Case table, the manager can't see the cases that their reports have access to'), e ele NÃO herda o depth do subordinado — a doc dá o exemplo em que o subordinado tem BU-level read e o gestor, com user-level, não enxerga tudo que o subordinado enxerga. Recomendação oficial de performance, textual: 'Keep the effective hierarchy security to 50 users or less under a manager or position'. Settings correlatos: AuthorizationEnableHSMForDisabledUsers (incluir/excluir registros de subordinados desativados) e o alerta de que ligar/desligar a modelagem dispara recomputação que pode dar timeout — 'reduce the number of tables under the Hierarchy Table Management list'.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/hierarchy-security

**Licao para a Tracbel:** ADOTAR só a variante Manager, com depth 1 ou 2; DESCARTAR Position hierarchy. Justificativa: a Tracbel já tem hierarquia de vendas real (vendedor → líder do CEN → gerente), e a memória do projeto registra que a aprovação vai para o LÍDER DO CEN no momento da geração. Basta `ManagerId` em Usuario + um CTE recursivo com cap de profundidade. COPIAR também o corte direto=escrita / indireto=leitura (é a semântica correta de gestão) e o teto de 50 — com 130 usuários vocês estão confortavelmente dentro dele, mas registre o limite antes de alguém pendurar 90 vendedores num gerente. E COPIE o pré-requisito: hierarquia AMPLIA, nunca CRIA privilégio — o gestor sem Read na entidade continua sem ver nada.

### 14. Column Security: FieldSecurityProfile + FieldPermission, e o comportamento de NULL silencioso que é uma armadilha de integração

Segurança de coluna é ORGANIZATION-WIDE ('Column-level security configurations are organization-wide and apply to all data access requests') e ORTOGONAL ao acesso à linha ('column-level security has nothing to do with record-level security. A user must already have access to the record'). Modelo de dados: FieldSecurityProfile ligado a usuários (systemuserprofiles_association) e times (teamprofiles_association), com N linhas de FieldPermission contendo CanCreate, CanRead, CanUpdate e CanReadUnmasked. As 4 permissões na UI: Read (Allowed/Not Allowed), Read unmasked (All Records / One record / Not Allowed, default Not Allowed), Update, Create. System Administrator SEMPRE bypassa: 'Data is never hidden from system administrators'. Se a coluna está segura e nenhum profile foi atribuído, só o sysadmin vê — aparece como cadeado e ********. NÃO podem ser protegidas: colunas de virtual tables, LOOKUPS, formula columns, primary name columns, e colunas de sistema (createdon, modifiedon, statecode, statuscode). File e Image podem ser protegidos mas não mascarados. A armadilha para desenvolvedor, textual: "The default API behavior when returning a value for a secured column is to return no data. The calling application can't distinguish between a value that is secured and a value that is null." Duas outras pegadinhas: colunas calculadas que usam uma coluna protegida vazam o dado ("Both the original column and the calculated column should be secured") e colunas compostas como fullname / address1_composite exigem proteger TODAS as colunas-componentes. Mudanças exigem refresh do browser. Há ainda sharing de campo por LINHA via a tabela PrincipalObjectAttributeAccess (POAA).

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/field-level-security e https://learn.microsoft.com/en-us/power-apps/developer/data-platform/column-level-security

**Licao para a Tracbel:** COPIAR a estrutura (Profile → Permissions → atribuído a user OU team) mas com DUAS correções deliberadas. (1) NUNCA devolva NULL silencioso: a API deve OMITIR o campo do JSON quando não autorizado (para o React saber que não existe) ou devolver um sentinel explícito `{"margem": {"restricted": true}}`. NULL silencioso é a receita de um relatório de margem que soma zero e ninguém percebe por três meses. (2) Limite o escopo: proteja 5-10 colunas de fato sensíveis (custo de aquisição, margem, comissão, limite de crédito, score), não dezenas — a própria MS avisa 'should be used as needed and not excessively as it can add overhead'. DESCARTE o sharing de campo por linha (POAA) — complexidade sem retorno. E copie o alerta das colunas derivadas: se `margem` é protegida, `percentualMargem` e qualquer view/DTO que a exponha também precisam ser.

### 15. Presets de permissão e Copy table permissions: a UX que faz um modelo de 200 tabelas ser administrável

O editor de role oferece grupos pré-definidos de permissão aplicáveis a uma tabela inteira: No Access; Full Access (ver e editar todos); Collaborate (ver todos, editar só os próprios); Private (ver e editar só os próprios); Reference (só ver, não editar); Custom (indica que foi alterado do padrão). Existe também 'Copy table permissions' para replicar a configuração de uma tabela para várias, com regras explícitas de falha: se o depth da permissão da origem não existir no destino, a cópia FALHA com erro; se a permissão existe na origem mas não no destino, é ignorada; se existe só no destino, o depth do destino é preservado. A recomendação oficial é criar roles novas COPIANDO templates: 'App Opener' (privilégios mínimos para abrir um app) e 'Basic User' (mínimo + tabelas core de negócio). E a boa prática de BU: 'create security roles at the root business unit level, since these roles are automatically duplicated for all child business units and can be included in solutions'.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/security-roles-privileges e https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/security-strategy-product-ce

**Licao para a Tracbel:** COPIAR os presets — é barato e é 80% da usabilidade do módulo de permissões. Na tela de role em React, ofereça os 6 botões (Sem acesso / Total / Colaborar / Privado / Referência / Custom) por entidade, e a matriz detalhada só quando o admin escolher Custom. E COPIE o 'copy permissions' com as mesmas regras de falha. DESCARTE a duplicação de roles por BU: no modelo modernizado que vocês vão adotar, a role é ÚNICA e a unidade entra na ATRIBUIÇÃO `(UserId, RoleId, UnitId)` — isso elimina o pior problema operacional do Dynamics clássico, que é ter 8 cópias da role 'Vendedor' e não saber qual editar.

### 16. Hierarquia de custo de performance publicada pela própria Microsoft: Organization é o MAIS rápido, Sharing é o mais caro

O guia de implementação do Dynamics 365 publica uma tabela comparando os mecanismos de acesso. Trechos textuais: Organization — 'Bypasses the need for security checking, which improves performance'. Business unit — 'Great for large volumes of data accessed by large groups of users. Allows for optimal access checking. Reduces maintenance overhead'. User ownership — 'Optimized access checks combine memory cache and record data directly'. Team ownership — 'Optimized access checks... Reduces cascading impact as user involvement changes. Isolates users from record business unit structure, enabling user movement with data impact'. Sharing — 'Ideal for modeling exceptions over standard model... but at a cost—checking a lot of rules increases performance, storage, and maintenance overhead. Sharing with teams mitigates cost'. Inheritance (hierarquia) — 'Not intended to replace business unit access at more senior or broad scope levels'. E a classificação em 3 categorias: fundamental controls (ownership, BU, roles, teams) devem resolver 'most of the security requirements'; other controls (field-level, hierarchy, access teams, relationships) para 'exceptions and edge scenarios'; manual sharing 'can't be automated or scaled'. Recomendações diretas sobre sharing: 'Don't automate sharing' e 'Turn off share rights in security roles where possible'.

**Evidencia:** https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/security-strategy-product-ce

**Licao para a Tracbel:** COPIAR essa hierarquia como REGRA DE DESIGN escrita no CLAUDE.md/AGENTS.md do projeto: todo requisito de visibilidade novo deve ser resolvido primeiro por ownership/unidade/time; sharing é a última opção e exige aprovação. E copie literalmente 'Don't automate sharing' — nenhum job, workflow ou trigger do CRM Tracbel deve criar linhas de compartilhamento em lote; é assim que a POA de qualquer implantação de Dynamics vira 50 milhões de linhas.

### 17. Auditoria do Dataverse: 3 níveis de configuração, limites numéricos concretos e o que ela NÃO captura

Configura-se em 3 níveis: environment → tabela → coluna. Captura: create/update/delete; mudanças de PRIVILÉGIO DE COMPARTILHAMENTO de um registro; associação/desassociação N:N; MUDANÇAS EM SECURITY ROLES; deleção de audit logs; e acesso de usuário (Log access). NÃO captura: mudanças de definição de tabela/coluna, autenticação, e — crucialmente — operações de RETRIEVE e EXPORT ('auditing doesn't support retrieve operations or export operations'), que exigem o activity logging do Purview. Retenção: padrão 'Forever'; custom com MÁXIMO DE 24.855 DIAS; e o detalhe que pega todo mundo: 'Each audit log is stamped with the currently active retention period. Changing the retention period here doesn't change the retention period for already existing records.' Valores grandes (email description, annotation) são truncados em 5 KB / ~5.000 caracteres, com '…' no fim. Existem ~31 tabelas não-auditáveis (CanModifyAuditSettings=false), incluindo ActivityPointer, Annotation, Workflow, Service, Subject, Template. A deleção de logs roda como job assíncrono a ~100 milhões de registros/dia (~4 milhões/hora). Exportar audit log não é suportado pela UI — só via Web API/SDK ou Azure Synapse Link. E o guia de implementação alerta: 'Don't enable auditing for all tables and columns... Excessive auditing can affect performance and consume large volumes of log storage.'

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/manage-dataverse-auditing e https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/security-strategy-product-ce

**Licao para a Tracbel:** COPIAR o modelo de 3 níveis com OPT-IN (padrão desligado, liga-se por tabela e por coluna) e a política de retenção CARIMBADA NA LINHA — é a solução elegante para mudar política sem reprocessar histórico. COPIAR também a decisão de auditar mudanças de ROLE e de COMPARTILHAMENTO, não só de dados: é isso que responde 'quem deu acesso ao concorrente'. DESCARTAR: o truncamento em 5 KB (guarde o hash do valor completo se precisar) e a ausência de export (exponha CSV/Parquet desde o dia 1). ARQUITETURA: grave audit em tabela/partição separada (ou fila → tabela append-only particionada por mês no SQL Server), NUNCA no caminho quente da transação, e planeje o expurgo — a MS publicar '100M registros/dia' é o tamanho do problema que eles criaram.

### 18. Purview / activity logging: o que só o log de leitura resolve, e os limites de 3 KB e de mascaramento

O activity logging do Dataverse e dos model-driven apps vai para o Microsoft Purview e cobre justamente o que a auditoria interna não cobre: CRUD completo, 'Multiple record view' (grids, Advanced Find), Export to Excel, chamadas de SDK por apps de terceiros, Report Viewed / Report Viewer Export, e todas as atividades de engenheiros de suporte da Microsoft. Só funciona em ambientes de PRODUÇÃO ('User access or activity logging is sent to Purview for production environments only'). Limitações duras: 'Office has a 3-KB limit for each audit record' — registros grandes são QUEBRADOS em vários, correlacionáveis por CorrelationId; RetrieveMultiple e ExportToExcel 'don't reliably include individual record identifiers in the QueryResults field. Record-level access tracking for these operations isn't currently supported'; ExportToWord é logado como uma operação única sem detalhe. Colunas com column-level security vão para o Purview como asterisco (*), e 'the details of each column's before-and-after values for CRUD activities are not sent to Purview activity logging to prevent data leaks'. Há uma lista explícita de ~25 mensagens de SDK que NÃO são logadas (WhoAmI, RetrieveMetadataChanges, FetchXmlToQueryExpression, etc.). O guia de implementação afirma que a retenção padrão é de 90 dias ou 1 ano conforme o tipo de licença Microsoft 365.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-dataverse-model-driven-apps e https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/security-strategy-product-ce

**Licao para a Tracbel:** ADOTAR O CONCEITO, não a implementação. A lição de ouro é: 'quem LEU/EXPORTOU' é um log diferente de 'quem MUDOU', com volume 100x maior e vida útil menor. No CRM Tracbel, logue explicitamente: export/download (quem, filtro aplicado, nº de linhas), visualização de listas grandes, e acesso a campos protegidos — porque o risco real numa revenda é o vendedor sair com a base de clientes, não alguém corromper um campo. Grave isso em store separado com retenção curta (90 dias) e mande para SIEM se houver. E COPIE a política de não gravar valores de campos protegidos no log (senão o log vira o vazamento). Nota: não confirmei na fonte os números de retenção do Purview Audit Standard/Premium — ver gaps.

### 19. Autenticação e perímetro: Entra ID, application users, Conditional Access para workload identities e IP firewall

Camadas documentadas: (a) ENVIRONMENT SECURITY GROUP — associar um grupo do Entra ao ambiente; sem ser membro, o usuário 'can't access any information in Dynamics 365 even with a valid authentication and security role assigned'; é best practice explícita. (b) APPLICATION USERS — usuário NÃO LICENCIADO ligado a um app registration do Entra (ou a um Application ID de Managed Identity), com business unit e security roles próprias; regra dura: 'In an environment, you can only have one application user for each Microsoft Entra–registered application'; e 'All your application users can run in any environments that are secured with a security group without being a member of the security group'. Só app users INATIVOS podem ser deletados, e é preciso reatribuir os registros que eles possuem antes. Há também um conjunto de system-provided application users da plataforma. (c) CONDITIONAL ACCESS — para service principal é preciso atribuí-lo diretamente à policy como workload identity; alerta específico de que o Microsoft Flow Service (App ID 7df0a125-d3be-4c96-aa54-591f83ff541c) não está incluído no target 'Office 365'. (d) CONTINUOUS ACCESS EVALUATION — o Dataverse encerra sessões proativamente em mudança de risco/rede. (e) IP FIREWALL e IP-based COOKIE BINDING (anti session hijacking) — ambos SÓ em Managed Environments. (f) Guest access bloqueado por padrão em ambientes Dataverse novos. (g) Recomendação de governança: o PPAC sinaliza ambientes com mais de 20 usuários com role System Administrator.

**Evidencia:** https://learn.microsoft.com/en-us/power-platform/admin/manage-application-users, https://learn.microsoft.com/en-us/power-platform/admin/security/identity-access-management e https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/security-strategy-product-ce

**Licao para a Tracbel:** COPIAR quatro coisas, de baixo custo e alto retorno: (1) autenticação 100% no Entra ID (a Tracbel já é Microsoft 365 — OIDC + MFA + Conditional Access herdados de graça, e resolve o problema já conhecido de MFA/senha de app do Vórtice); (2) o conceito de APPLICATION USER — integrações (TOTVS/JDE, RD Station, Tallos, portal) autenticam com client_credentials e recebem uma IDENTIDADE PRÓPRIA no CRM, com roles próprias e auditoria própria, jamais um 'usuário genérico de integração' com senha compartilhada; (3) o gate de grupo do Entra na frente do ambiente (defesa em profundidade: mesmo com role, sem grupo não entra); (4) o alerta dos 20 sysadmins — implemente um alerta no admin do CRM quando o nº de administradores passar de um teto. DESCARTAR: IP firewall próprio (o CRM vai estar atrás do perímetro corporativo/Entra CA — não reimplemente); implemente sim revogação de sessão por evento (logout forçado ao mudar role/desligar usuário), que é o valor real do continuous access evaluation.

### 20. Comparação Salesforce x Dynamics — onde o Dynamics é MELHOR

(1) SEM MATERIALIZAÇÃO PARA O CAMINHO COMUM: no Dataverse, 'usuário vê tudo da sua unidade e das filhas' é resolvido comparando OwningBusinessUnit da linha com a BU do usuário — nada é gravado. No Salesforce, com OWD restritivo, o acesso é PRÉ-COMPUTADO em linhas das object share tables e das group maintenance tables; cada regra de compartilhamento, mudança de role ou de grupo dispara recálculo de share rows. (2) A MATRIZ VERBO x PROFUNDIDADE É MAIS EXPRESSIVA POR UNIDADE DE CONFIGURAÇÃO: um único par (privilege, depth) por tabela substitui OWD + 'Grant Access Using Hierarchies' + sharing rules, e permite assimetria fina (ex.: Read=Organization mas Write=User) que no Salesforce exige combinar OWD com FLS e regras. (3) SEPARAÇÃO LIMPA ENTRE VERBO E ESCOPO — no Salesforce a permissão de objeto (CRUD no profile/permission set) e o escopo de registros (OWD/sharing) vivem em subsistemas diferentes com modelos mentais diferentes; no Dataverse é a MESMA célula da matriz. (4) IDENTIDADE UNIFICADA COM O RESTO DO STACK: group teams derivados dinamicamente do Entra ID, application users, Conditional Access e Purview — não há equivalente nativo de mesma profundidade no Salesforce sem integração. (5) LIMITES MAIS FOLGADOS em compartilhamento estruturado: no Salesforce o teto é 300 sharing rules por objeto (e 50 criteria-based), e 2 restriction rules por objeto (5 em Performance/Unlimited); no Dataverse não há teto equivalente porque o mecanismo é outro.

**Evidencia:** Dataverse: https://learn.microsoft.com/en-us/power-platform/admin/how-record-access-determined ; Salesforce sharing rules limits e role hierarchy (busca em help.salesforce.com / developer.salesforce.com, doc 'Tips and Hints for Sharing Data' e 'Restriction Rule Considerations'); sharing/group tables: https://developer.salesforce.com/docs/atlas.en-us.salesforce_record_access_under_the_hood.meta/salesforce_record_access_under_the_hood/uth_entity.htm e .../uth_groups.htm

**Licao para a Tracbel:** COPIAR DO DYNAMICS, NÃO DO SALESFORCE, o mecanismo central. Para 130 usuários, materializar acesso (modelo Salesforce) é over-engineering puro: gera uma tabela de shares, um motor de recálculo e uma classe inteira de bugs de consistência que um time de 2-3 devs não sustenta. O modelo Dataverse — duas colunas na linha (OwnerId, OwningUnitId) + um permission set em cache + um global query filter — cabe em ~300 linhas de C# e é auditável a olho nu. Copie também a unificação verbo+escopo na mesma célula: um único CRUD de role, não dois subsistemas.

### 21. Comparação Salesforce x Dynamics — onde o Dynamics é PIOR

(1) NÃO EXISTE DENY. O Salesforce tem RESTRICTION RULES (EnforcementType=Restrict), que efetivamente REMOVEM acesso que o usuário teria por outro caminho, e SCOPING RULES (EnforcementType=Scoping), que mudam o conjunto default visível sem restringir acesso. O Dataverse não tem equivalente: 'you can’t go back and hide a single record'. (2) NÃO EXISTE COMPARTILHAMENTO DECLARATIVO POR CRITÉRIO. O Salesforce tem criteria-based sharing rules ('todo Account com Segmento = Enterprise vai para o grupo X'), reavaliadas quando o dado muda. No Dataverse a única forma é código (plug-in chamando GrantAccess), e a doc oficial diz 'Don't automate sharing'. (3) NÃO EXISTE TERRITORY MANAGEMENT NATIVO. O Salesforce tem Enterprise Territory Management com modelos de território (limite default de 1.000 territórios por modelo; até 20.000 em Performance/Unlimited via suporte) e regras de atribuição automática de contas a territórios. No Dataverse, 'carteira/território' tem que ser modelado à mão com BUs + owner teams. (4) SEPARAÇÃO PERFIL/PERMISSÃO INFERIOR. O Salesforce evoluiu para Permission Sets e Permission Set Groups — blocos pequenos e componíveis, com a recomendação oficial de usar permission sets em vez de profiles; o Dataverse tem só 'security role', e a prática de copiar a role para variar um privilégio gera proliferação. (5) COMPARTILHAMENTO PROGRAMÁTICO MAIS POBRE: o Salesforce tem Apex Managed Sharing com RowCause customizável (você marca POR QUE aquele share existe, e ele sobrevive a recálculo); no Dataverse a POA guarda só AccessRightsMask/InheritedAccessRightsMask — não há campo de 'motivo', e é por isso que precisaram inventar a API RetrieveAccessOrigin para inferir a origem depois. (6) FLS: o Dataverse falha em silêncio (retorna vazio, indistinguível de null); o Salesforce trata field permissions como cidadão de primeira classe em profiles/permission sets.

**Evidencia:** Restriction/Scoping rules: https://developer.salesforce.com/docs/atlas.en-us.restriction_rules.meta/restriction_rules/restriction_rules_about.htm e https://help.salesforce.com/s/articleView?id=platform.security_restriction_rule_considerations.htm ; territory limits: help.salesforce.com art. 000386570 ; permission sets: https://help.salesforce.com/s/articleView?id=platform.perm_sets_best_practices.htm ; sharing rows/RowCause: https://developer.salesforce.com/docs/atlas.en-us.salesforce_record_access_under_the_hood.meta/salesforce_record_access_under_the_hood/uth_entity.htm ; NULL silencioso: https://learn.microsoft.com/en-us/power-apps/developer/data-platform/column-level-security

**Licao para a Tracbel:** COPIAR DO SALESFORCE exatamente TRÊS coisas, e só essas três: (1) o RowCause — toda linha da sua tabela de compartilhamento deve ter um campo `Motivo` (enum: ManualUsuario, RegraCarteira, Aprovacao, Substituicao, Integracao). Isso torna o revoke seletivo trivial ('remova todos os shares de motivo=RegraCarteira do cliente X') e elimina a necessidade de uma API de arqueologia como a RetrieveAccessOrigin. (2) UM deny explícito e nomeado (o `IsRestrito` já citado) — não um motor de restriction rules. (3) A ideia de PERMISSION SET GROUP: modele `Role` como composição de `PermissionSets` pequenos e reutilizáveis ('Ver custos', 'Aprovar desconto até 5%', 'Exportar base'), em vez de 15 roles monolíticas que ninguém sabe diferenciar. DESCARTAR do Salesforce: sharing rules declarativas por critério, territory management e qualquer materialização de acesso — custo desproporcional para 130 usuários.

### 22. Comparação Salesforce x Dynamics — onde é só DIFERENTE (e a lição vale para os dois)

AGRUPAMENTO: Salesforce usa Role (hierarquia rígida, best practice de no máximo 10 níveis de ramificação e até 25.000 roles internas) + Public Groups + Queues, com group maintenance tables mantendo membros diretos e indiretos; o Dataverse usa Business Unit (árvore) + Teams (planos, atravessam BUs). AGREGAÇÃO: ambos são 'most permissive wins' — Salesforce: 'Salesforce uses the most permissive grant when determining record access'; Dataverse: 'the least restrictive evaluation of all the security roles that apply'. HIERARQUIA DE GESTÃO: Salesforce embute no role hierarchy (com o toggle 'Grant Access Using Hierarchies' por objeto custom); Dataverse separa em um módulo opcional (Hierarchy Security) com Manager/Position. OWD do Salesforce (Private, Public Read Only, Public Read/Write, Controlled by Parent, com Public Full Access/View Only em objetos específicos) é o análogo aproximado do access level default por tabela do Dataverse. TIMES DE REGISTRO: Salesforce tem Account/Opportunity/Case Teams com 'only one team per record' e cada membro gerando DOIS registros (team + share); Dataverse tem access teams com template. SKEW: o Salesforce documenta ownership data skew (um usuário dono de mais de 10.000 registros de um objeto causa problemas ao movê-lo na hierarquia); o Dataverse não publica número equivalente, mas o efeito é o mesmo em cascade de assign.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.salesforce_record_access_under_the_hood.meta/salesforce_record_access_under_the_hood/uth_groups.htm ; https://help.salesforce.com/s/articleView?id=platform.admin_sharing.htm ; https://help.salesforce.com/s/articleView?id=platform.setup_roles_guidelines.htm ; https://learn.microsoft.com/en-us/power-apps/developer/data-platform/security-concepts

**Licao para a Tracbel:** ADOTAR o híbrido: use ÁRVORE (unidade/empresa) para o eixo ESTRUTURAL — que é estável, raso e reflete a multiempresa — e use TIMES PLANOS para o eixo de CARTEIRA/LINHA DE NEGÓCIO, que é volátil e cruza empresas (um especialista de colheitadeiras atende 3 filiais). Não tente representar carteira como nó de árvore: é exatamente o erro que a Microsoft passou 15 anos consertando com Modernized Business Units. E COPIE o alerta de skew como regra operacional: nenhum 'usuário genérico' (ex.: 'Carteira Sem Dono') deve possuir dezenas de milhares de linhas — use um TIME como dono nesse caso.

### 23. RECOMENDAÇÃO FINAL — o modelo de permissão para o CRM Tracbel: quais camadas adotar e quais cortar

CAMADA 1 — IDENTIDADE (adotar): Entra ID/OIDC + MFA + Conditional Access herdados do M365; grupos do AD mapeados para Times do CRM; application users com client_credentials e roles próprias para cada integração (TOTVS/JDE, RD Station, Tallos, portal). CAMADA 2 — PRIVILÉGIO (adotar, é o núcleo): tabela `RolePrivilege(RoleId, Entidade, Verbo, Depth)` com 6 verbos (Read/Create/Update/Delete/Assign/Share) e 5 depths (None/Own/Unit/UnitAndChildren/All). Entidade nova = INSERT, não deploy. Permission set efetivo = união de todas as roles do usuário, cacheado em memória/Redis com invalidação em mudança de role. CAMADA 3 — ESCOPO DE LINHA (adotar): TODA tabela transacional carrega `OwnerId` + `OwnerType` (User|Team) + `OwningUnitId`. Atribuição de role é `(UserId, RoleId, UnitId)` — modelo modernizado desde o dia 1. O access check vira UM global query filter do EF Core, com índices compostos em (OwningUnitId, OwnerId) e (OwnerId, StatusId). CAMADA 4 — TIMES (adotar): Owner Teams como implementação de CARTEIRA/linha de negócio; membership sincronizada de grupo do AD; um usuário em N times; `OwnerId IN (@me, @teams)`. CAMADA 5 — HIERARQUIA (adotar reduzida): só `ManagerId`, CTE recursivo com depth 2, direto = leitura+escrita, indireto = só leitura, teto de 50 subordinados efetivos por gestor, e sempre exigindo Read nível Own na entidade. CAMADA 6 — COLUNA (adotar mínima): `ColumnProfile` com CanRead/CanUpdate para 5-10 campos (margem, custo, comissão, limite de crédito, score), aplicada na projeção do DTO, OMITINDO o campo em vez de devolver null. CAMADA 7 — COMPARTILHAMENTO (adotar amputada): `RecordShare(EntidadeId, RegistroId, TeamId, Direitos bitmask, Motivo, ExpiresAt, CriadoPor)` — SÓ para times, SEM cascade para filhos, COM motivo e COM TTL obrigatório. CAMADA 8 — AUDITORIA (adotar): opt-in por tabela/coluna, retenção carimbada na linha, log separado de leitura/export, tabela append-only particionada por mês, export nativo em CSV/Parquet. CAMADA 9 — DIAGNÓSTICO (adotar, sprint 1): endpoints `explain-access` e `who-has-access`. CORTAR EXPLICITAMENTE: privilégios Append/AppendTo; access teams auto-criados e templates; sharing para usuário individual; cascade de share/reparent; Position hierarchy; duplicação de roles por unidade; 'Member's privilege inheritance'; sharing de campo por linha (POAA); qualquer automação que crie compartilhamento em lote. Dimensionamento esperado para 130 usuários: 5-10 unidades, 3 níveis de árvore no máximo, 10-25 times de carteira, 8-15 roles compostas de permission sets, e uma tabela RecordShare que deve permanecer na casa dos milhares de linhas — se passar de dezenas de milhares, o modelo foi violado.

**Evidencia:** Síntese de https://learn.microsoft.com/en-us/power-platform/admin/how-record-access-determined, .../wp-security-cds, .../modernized-business-units-security, .../hierarchy-security, .../manage-principalobjectaccess-storage, .../field-level-security, .../manage-dataverse-auditing e https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/security-strategy-product-ce

**Licao para a Tracbel:** O critério de decisão que amarra tudo: ADOTAR o que é resolvido por COLUNA NA PRÓPRIA LINHA (OwnerId, OwningUnitId) — custo O(1), depurável, index-friendly. CORTAR o que exige TABELA DE ACESSO MATERIALIZADA (POA, access teams, sharing cascateado) — custo O(usuários × registros), indepurável, e a própria Microsoft admite não conseguir limpar. Um time de 2-3 devs sustenta o primeiro grupo indefinidamente e afunda no segundo em 18 meses. E o teste de sanidade para qualquer requisito futuro de visibilidade: 'isso vira uma cláusula WHERE ou vira linhas numa tabela?'. Se vira linhas, exija justificativa por escrito antes de implementar.

## Lacunas declaradas

- Não existe (ou não localizei) limite numérico documentado pela Microsoft para o NÚMERO MÁXIMO DE BUSINESS UNITS por ambiente, nem para profundidade máxima da árvore de BUs. A doc só dá orientação qualitativa ('minimize the number of business units', 'avoid creating a large number of business units'). A página de referência da tabela BusinessUnit não publica limite.
- Não localizei limite documentado para: número máximo de security roles por usuário, número máximo de times por usuário, número máximo de colunas que podem ser protegidas por column security, nem número máximo de Column Security Profiles por ambiente. Todos aparecem apenas como 'não use em excesso'.
- A Microsoft NÃO publica thresholds numéricos de performance para a tabela PrincipalObjectAccess (nº de linhas a partir do qual degrada, latência do join, tamanho típico). Toda a orientação em manage-principalobjectaccess-storage é qualitativa. Isso contrasta com o Salesforce, que publica o número de ownership data skew.
- O número de ownership data skew do Salesforce (um usuário dono de mais de 10.000 registros de um objeto) veio de snippet de busca citando documentação Salesforce; NÃO consegui abrir a fonte primária diretamente (architect.salesforce.com devolveu HTTP 403 e o PDF 'Designing Record Access for Enterprise Scale' em resources.docs.salesforce.com falhou com erro de certificado TLS). Tratar como provável mas não verificado em primeira mão.
- Os números de retenção do Microsoft Purview Audit (Standard 180 dias, Premium 1 ano ou mais, add-on de 10 anos) vieram de snippet de busca sobre audit-log-retention-policies, não de leitura direta da página. O que ESTÁ verificado em fonte primária é: (a) a retenção do audit interno do Dataverse — default 'Forever', custom máximo 24.855 dias; (b) a afirmação do guia de implementação do Dynamics 365 de que activity logging é retido por 90 dias ou 1 ano conforme o tipo de licença M365.
- Não verifiquei os limites exatos do Salesforce para role hierarchy em fonte primária aberta — os números (25.000 roles internas, 100.000 roles externas, máximo recomendado de 10 níveis de ramificação, 300 sharing rules e 50 criteria-based por objeto, 1.000 territórios por modelo) vieram de snippets de busca em help.salesforce.com/developer.salesforce.com, cujas páginas retornam shell de SPA para o WebFetch. Confirmar antes de usar em documento formal.
- Não investiguei em profundidade a integração Dataverse ↔ Microsoft Purview Information Protection (sensitivity labels aplicadas a dados do Dataverse) nem DLP policies do Power Platform — ficaram fora do escopo por tempo, e podem ser relevantes se a Tracbel tiver requisito de LGPD com classificação de dados.

Isso é diretamente relevante para a Tracbel, que hoje consulta o banco do Vórtice via SQL read-only para relatórios.
