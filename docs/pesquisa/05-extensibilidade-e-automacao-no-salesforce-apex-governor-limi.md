# Extensibilidade e Automação no Salesforce — Apex, Governor Limits, Flow, Integração e SOQL/SOSL, com desenho do pipeline equivalente em .NET 8 para o CRM próprio da Tracbel

> Pesquisa automatizada - workflow `crm-tracbel-pesquisa-profunda`, 30/08/2026.

## Resumo

O Salesforce resolve "extensibilidade sem release" com três camadas que a Tracbel pode copiar quase literalmente: (1) um PIPELINE DE SAVE determinístico de 20 etapas, com fase before-save (muta o registro em memória, sem segundo DML) e after-save (efeitos colaterais); (2) um FRAMEWORK DE HANDLERS DIRIGIDO POR CONFIGURAÇÃO — a própria Salesforce recomenda o Metadata-Driven Trigger Framework, onde classes atômicas são registradas em registros de metadados (TriggerAction__mdt) que definem ORDEM, ATIVO/INATIVO e BYPASS por permissão, sem deploy; e (3) CUSTOM METADATA TYPES (__mdt), configuração versionável e deployável cuja leitura NÃO consome limite de SOQL. Os governor limits (100 SOQL / 150 DML / 10.000 ms CPU / 6 MB heap síncrono) existem por multitenancy e NÃO devem ser copiados em número por um sistema single-tenant — mas a DISCIPLINA que eles forçam (bulkificação obrigatória, proibição de query em loop, handler que sempre recebe lista) é o que salvou a plataforma e é exatamente o que falta em CRMs legados como o Vórtice. A orientação atual da Salesforce (2026) é: Workflow Rules e Process Builder sem suporte desde 31/12/2025; Flow para baixa densidade de automação (<15 automações por objeto), Flow + Apex invocável para média (15–30), e framework de trigger em Apex para alta (>30). Para um time de 2–3 devs, a recomendação é NÃO construir um Flow Builder visual: construir o pipeline + tabela de registro de handlers + outbox, e deixar "configuração" significar ordenar/ligar/desligar/parametrizar handlers, não desenhar fluxogramas.

## Entidades / objetos mapeados

### `Apex Trigger (trigger X on Objeto (before insert, after update, ...))`

**Funcao:** Ponto de extensão programático amarrado ao ciclo de save de um objeto. Boa prática oficial: UM trigger por objeto, sem lógica dentro dele, apenas despacho.

**Campos-chave:** Trigger.new, Trigger.newMap, Trigger.old, Trigger.oldMap, Trigger.isBefore/isAfter, Trigger.isInsert/isUpdate/isDelete/isUndelete, Trigger.operationType (enum System.TriggerOperation), Trigger.size, Trigger.isExecuting

**Relacoes:** Dispara dentro da Order of Execution (etapas 4 e 8); delega para handler class; handler consulta TriggerAction__mdt para ordem/bypass

### `TriggerAction__mdt (Custom Metadata Type)`

**Funcao:** Registro de configuração que define QUAIS classes Apex rodam, em QUE ORDEM, em qual contexto e sob qual bypass — alterável sem deploy. É o núcleo do Metadata-Driven Trigger Framework recomendado pela Salesforce.

**Campos-chave:** Nome da classe (Apex a executar), Order (ordem de execução), contexto (before insert/after update/...), BypassPermission__c (custom permission que desliga a ação), Active, Description

**Relacoes:** Lido pelo MetadataTriggerHandler, que instancia dinamicamente as classes atômicas (ex.: RecalculateAccountValues, NotifySalesLeads)

### `Custom Metadata Type (Objeto__mdt)`

**Funcao:** Configuração como METADADO (deployável, empacotável, versionável em git), não como dado. Exposto em cache de aplicação.

**Campos-chave:** DeveloperName, MasterLabel, QualifiedApiName, NamespacePrefix, Label, Id, SystemModStamp (API 56.0+)

**Relacoes:** Acessível por getAll() / getInstance(); operações suportadas: describeSObjects(), describeLayout(), query(), retrieve() — SEM DML a partir de Apex

### `Platform Event (Objeto__e)`

**Funcao:** Mensagem de evento no event bus para desacoplar publicador de assinante, dentro e fora do Salesforce.

**Campos-chave:** ReplayId, campos customizados definidos pelo usuário; comportamento de publicação: Publish Immediately (default) ou Publish After Commit

**Relacoes:** Publicado por EventBus.publish (Apex), Flow, REST composite; assinado por trigger after insert, Flow, Pub/Sub API, CometD, event relays

### `Change Event (Change Data Capture)`

**Funcao:** Evento automático de criação/atualização/exclusão/restauração de registro, para sincronizar sistemas externos e offload assíncrono de lógica pesada.

**Campos-chave:** ChangeEventHeader (metadados da mudança), campos do registro alterado; changeType: CREATE, UPDATE, DELETE, UNDELETE

**Relacoes:** NÃO carrega o estado anterior (não há equivalente a Trigger.oldMap); assinado por Pub/Sub API, CometD, trigger Apex, Flow, empApi

### `External Object (Objeto__x) / Salesforce Connect`

**Funcao:** Objeto virtual mapeado para dados que permanecem no sistema externo (sem replicação), consultável por SOQL/SOSL e exibível em relatórios.

**Campos-chave:** External ID (campo padrão do objeto externo), relacionamentos external lookup (filho -> pai externo) e indirect lookup (filho externo -> pai interno via campo único External ID)

**Relacoes:** Adaptadores OData 2.0/4.0/4.01, Cross-Org e Apex Connector Framework customizado; Apex triggers NÃO são suportados em objetos externos

### `Named Credential + External Credential`

**Funcao:** Separa endpoint de autenticação para chamadas de saída, eliminando credencial hardcoded no código.

**Campos-chave:** Named Credential guarda a URL do endpoint e referencia a External Credential; External Credential guarda o mecanismo/protocolo de autenticação

**Relacoes:** Usado em Apex via a sintaxe callout:NomeDaNamedCredential/caminho; dispensa Remote Site Settings

### `Queueable Apex (System.Queueable)`

**Funcao:** Job assíncrono moderno que aceita tipos não-primitivos (sObjects, tipos customizados), retorna Job Id monitorável e permite encadeamento.

**Campos-chave:** execute(QueueableContext); System.enqueueJob(job), (job, delayMinutos 0–10), (job, AsyncOptions); AsyncInfo.getCurrentQueueableStackDepth(), getMaximumQueueableStackDepth()

**Relacoes:** Database.AllowsCallouts habilita callout; System.Finalizer para lógica de falha; 1 job filho por job pai

### `Database.Batchable`

**Funcao:** Processamento em massa com limites de governor RENOVADOS a cada chunk — o mecanismo que quebra o problema de volume.

**Campos-chave:** start() -> Database.QueryLocator ou Iterable; execute(context, scope); finish(); escopo padrão 200, máximo 2.000 com QueryLocator; até 50 milhões de registros

**Relacoes:** Database.Stateful preserva variáveis entre chunks; cada execute() é uma transação discreta

### `@InvocableMethod / @InvocableVariable`

**Funcao:** Contrato que expõe uma classe Apex como ação chamável por Flow, integrações e outros pontos de entrada — o elo do padrão híbrido (Flow orquestra, Apex calcula).

**Campos-chave:** static e public/global, classe externa; no máximo 1 parâmetro de entrada e ele é uma List; retorno é List; atributos label, description, category, callout; só 1 método por classe pode ter a anotação

**Relacoes:** Contrato de bulk: a i-ésima entrada da lista de saída deve corresponder à i-ésima entrada da lista de entrada

### `PlatformEventSubscriberConfig`

**Funcao:** Configura o usuário executor e o batch size do trigger que assina eventos de plataforma, além de subscrições paralelas.

**Campos-chave:** usuário executor (default: Automated Process), batch size (máx. 2.000), partições paralelas

**Relacoes:** Máx. 10 subscrições paralelas por trigger; máx. 5 triggers configurados para subscrição paralela por org

### `Approval Process`

**Funcao:** Motor declarativo de aprovação multi-etapa com critérios de entrada, aprovadores hierárquicos/paralelos e ações automáticas.

**Campos-chave:** Filter/entry criteria, approval steps, aprovador via campo de hierarquia (ex.: Manager), initial submission actions, final approval/rejection actions, recall actions, 'Allow submitters to recall approval requests'

**Relacoes:** Invocável de Apex via Approval.process(); consome o limite de linhas de DML (10.000/transação)

## Achados

### 1. A Order of Execution completa do save: 20 etapas numeradas, e a fase 'before' é a única que não paga um segundo DML

Ordem oficial documentada para insert/update/upsert: (1) carrega o registro original do banco ou inicializa o registro para um upsert; (2) carrega os novos valores da requisição e sobrescreve os antigos, com validação de sistema (regras de layout, campos obrigatórios, formatos, comprimento); (3) executa record-triggered flows configurados para rodar ANTES do save; (4) executa todos os before triggers; (5) roda de novo a maior parte das validações de sistema, incluindo campos obrigatórios e regras de validação customizadas; (6) executa duplicate rules — se a regra identifica duplicata e a ação é 'block', o registro não é salvo e nenhuma etapa seguinte roda; (7) SALVA o registro no banco, mas ainda NÃO COMMITA; (8) executa todos os after triggers; (9) assignment rules; (10) auto-response rules; (11) workflow rules — se houver field update de workflow, o registro é atualizado de novo, as validações de sistema rodam de novo (excluindo regras customizadas, flows, duplicate rules, processes e escalation rules) e os before/after update triggers rodam MAIS UMA VEZ; (12) escalation rules; (13) automações Salesforce Flow (Process Builder e flows disparados por workflow — ordem de execução NÃO garantida entre eles); (14) record-triggered flows configurados para rodar DEPOIS do save; (15) entitlement rules; (16) e (17) recálculo de roll-up summary no registro pai e depois no avô, cada um passando pelo procedimento de save inteiro; (18) avaliação de Criteria Based Sharing; (19) COMMIT de todas as operações DML; (20) depois do commit, executa a lógica pós-commit: e-mails, jobs Apex assíncronos e caminhos assíncronos de flow. Detalhe crítico: em saves recursivos, as etapas 9 a 17 são PULADAS.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_triggers_order_of_execution.htm

**Licao para a Tracbel:** COPIAR o formato, simplificar o conteúdo. O CRM Tracbel deve ter um pipeline de save explícito, nomeado e documentado, com fases fixas: LoadOriginal -> ApplyIncoming -> ValidaçãoDeSistema -> BeforeSave -> ValidaçãoDeNegócio -> Duplicidade -> Persist(sem commit) -> AfterSave -> Roteamento/Atribuição -> Rollups -> COMMIT -> PostCommit. O maior aprendizado é a separação entre 'antes do commit' (pode bloquear e mutar) e 'depois do commit' (efeitos colaterais irreversíveis: e-mail, webhook, integração). O Vórtice não tem isso explicitado, e é por isso que ninguém sabe prever o que acontece ao salvar. DESCARTAR as etapas 9-15 do Salesforce (assignment/auto-response/escalation/entitlement são features de Service Cloud); a Tracbel precisa apenas de um slot genérico de 'roteamento'. O ponto de atenção número 1: NUNCA deixar um handler pós-save disparar um novo save do mesmo registro — isso é a etapa 11 do Salesforce, que reexecuta os triggers e é a fonte histórica de bugs.

### 2. Before-save vs after-save: a regra de ouro de performance é 'mutou o próprio registro? faça antes do commit'

A orientação arquitetural oficial diz: 'Always use a before-save update when your automation only needs to change field values on the record that starts the transaction. This applies to both fast-field updates in Flow (which run before save) and before-context logic in Apex Triggers (before insert, before update). This pattern is performant, regardless of which tool is used, because it avoids a second DML operation and a recursive save cycle. The changes are made to the record in memory before it is committed to the database, and are saved as part of the original transaction. The overhead of a second save, which would otherwise re-execute the entire save order and fire all automation again, is eliminated.' A documentação de ajuda da Salesforce quantifica: um record-triggered flow before-save atualiza um registro 10 vezes mais rápido que um record-change process (Process Builder).

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (Decision Guide oficial, seção de melhores práticas); claim de '10 vezes mais rápido' atribuído a help.salesforce.com/s/articleView?id=platform.flow_concepts_trigger_record.htm (confirmado apenas via snippet de busca, página bloqueada para fetch)

**Licao para a Tracbel:** COPIAR sem adaptação. No .NET com EF Core, isso significa: handlers que só alteram propriedades da própria entidade DEVEM rodar antes do SaveChangesAsync, mutando a entidade rastreada — nunca como um segundo Update depois. Criar duas interfaces distintas e não deixar o dev escolher errado: IBeforeSaveHandler<T> (recebe a entidade mutável, retorna void, PROIBIDO fazer I/O) e IAfterSaveHandler<T> (recebe entidade somente-leitura + a transação, pode gravar em outras entidades). Um code review que veja um AfterSave alterando a própria entidade e chamando SaveChanges de novo deve reprovar automaticamente.

### 3. Um trigger por objeto + handler pattern + o framework dirigido por metadados (a resposta oficial para 'extensibilidade sem release')

A Salesforce documenta a evolução em três estágios. (1) Regra base: 'maintain one Apex trigger per Salesforce Object. This rule is critical because the platform does not guarantee the execution order of multiple triggers on the same object for the same event. This limitation can lead to non-deterministic behavior, race conditions, and difficult-to-debug issues.' (2) Classic Trigger Handler pattern: o trigger único delega para uma classe handler (ex.: OpportunityTriggerHandler). Crítica oficial: 'this pattern often leads to monolithic handler classes... The execution order of all individual processes is hard-coded within a single method, making the class prone to merge conflicts.' (3) Metadata-Driven Trigger Framework, com três vantagens declaradas: PARTITIONING — 'the core business logic is broken down into small, atomic Apex classes (for example, a RecalculateAccountValues class or a NotifySalesLeads class), with each class adhering to the Single Responsibility Principle'; ORDER AND CHOREOGRAPHY — 'The execution order is no longer hard-coded in Apex. Instead, it is declaratively defined by configuration records, typically stored in a custom metadata type (for example, TriggerAction__mdt). This allows administrators to re-order, add, or remove automation actions simply by modifying a metadata record, which does not require a deployment or code change'; BYPASS FUNCTIONALITY — cada ação pode ser desligada globalmente ou por usuário via custom permission. O trigger vira 'only a dynamic dispatcher. It contains no business logic, but instead instantiates a central MetadataTriggerHandler class.'

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (seção 'Using a Metadata Framework for Apex Triggers')

**Licao para a Tracbel:** COPIAR — este é o achado mais importante do relatório e resolve literalmente o requisito 'extensibilidade sem release'. Em .NET 8: uma tabela TriggerAction (Entity, Event, Order, HandlerKey, IsActive, BypassPermission, Description) + resolução por Keyed Services do DI ([FromKeyedServices] nativo do .NET 8) + um Dispatcher genérico que lê a tabela, ordena e invoca. Adicionar/reordenar/desligar automação vira UPDATE em tabela (auditado), não deploy. Cada handler é uma classe pequena com nome de verbo de negócio (RecalcularValorDaCarteira, NotificarLiderDoCEN) e responsabilidade única — é isso que faz 'qualquer dev do time saber estender'. Cachear a tabela em memória com invalidação, para não pagar um SELECT por save.

### 4. Bypass framework por permissão: requisito operacional, não feature opcional

A orientação oficial: 'A well-architected Salesforce organization requires a consistent and reliable mechanism to bypass automation. This is not an optional feature, but a core operational requirement.' Três cenários citados: carga em massa de dados (disparar automação por registro derruba a carga, estoura limites e gera registros/notificações errôneos); usuário de integração sincronizando de um sistema-mestre externo (a automação de mudança feita por humano é indesejada ou redundante); administradores fazendo correções pontuais. O mecanismo recomendado são CUSTOM PERMISSIONS, atribuídas via permission sets, superiores a hardcode de perfil/usuário por flexibilidade (pode ser concedida temporariamente com data de expiração), manutenibilidade (mudança é atribuição de permission set, não deploy) e escalabilidade. Em Apex: o campo BypassPermission__c no TriggerAction__mdt, lido pelo MetadataTriggerHandler, que chama FeatureManagement.checkPermission() e pula aquela ação se retornar true — permitindo bypass global (todas as ações referenciando a mesma permissão) e granular por ação. Em Flow: checagem da variável global $Permission no critério de entrada, 'making it the most performant approach' porque impede a criação da interview.

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (seção de bypass)

**Licao para a Tracbel:** COPIAR integralmente. A Tracbel vai migrar dados do Vórtice para o CRM novo e vai ter integrações TOTVS/JDE gravando — sem bypass, a carga inicial dispara e-mails, tarefas e aprovações fantasmas. Implementar: coluna BypassPermission na tabela TriggerAction + checagem de claim/permissão do usuário atual no Dispatcher. O usuário de integração ganha a permissão 'AutomationBypass.All' e o suporte ganha bypasses granulares temporários. Isso também dá o botão de emergência: automação com bug em produção é desligada por UPDATE, sem deploy e sem janela.

### 5. Controle de recursão: o padrão correto é comparar novo vs antigo, não flag estática

Orientação oficial: 'Uncontrolled recursion is a common pitfall in after-update triggers... While static boolean flags or collections of processed record Ids have historically been used to prevent such recursion, a more precise and robust pattern is to gate the logic by comparing field values between the new and old versions of the record itself. Execute the logic only if a specific field of interest has actually changed.' Em Apex: comparar Trigger.new com Trigger.oldMap. Em Flow: comparar as variáveis globais $Record (valores novos) com $RecordPrior (valores originais antes do save) no critério de entrada. Resultado declarado: 'This approach makes sure that the automation is idempotent and only runs when necessary.' O limite de proteção da plataforma é 'Total stack depth for any Apex invocation that recursively fires triggers due to insert, update, or delete statements: 16'.

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html; limite de stack depth 16 em https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf (tabela Apex Governor Limits, atualizada em 7 de agosto de 2026)

**Licao para a Tracbel:** COPIAR. O ChangeTracker do EF Core já dá isso de graça: entry.OriginalValues vs entry.CurrentValues. O contrato do handler deve entregar um ChangeContext<T> com Current, Original e um helper HasChanged(x => x.Status) — assim o dev escreve `if (ctx.HasChanged(o => o.Status))` em vez de flags estáticas (que em .NET seriam AsyncLocal/estado por request e são fonte de bug em ambiente multi-thread, pior que no Apex). Adicionar também um contador de profundidade de save por request com teto (ex.: 16, copiando o número por ser um bom teto empírico) que ESTOURA com exceção clara — melhor falhar com 'recursão de save excedeu profundidade 16 na entidade Processo' do que rodar em loop até o timeout.

### 6. Governor limits: os números reais por transação (síncrono vs assíncrono)

Tabela oficial (última atualização 7 de agosto de 2026), síncrono / assíncrono: SOQL queries emitidas 100 / 200; registros retornados por SOQL 50.000 / 50.000; registros por Database.getQueryLocator 10.000 / 10.000; SOSL queries 20 / 20; registros por SOSL query 2.000 / 2.000; DML statements 150 / 150; registros processados por DML, Approval.process ou emptyRecycleBin 10.000 / 10.000; stack depth de triggers recursivos 16 / 16; callouts (HTTP/web services) 100 / 100; timeout cumulativo de callouts 120 segundos / 120 segundos; métodos @future por invocação 50 / 0 em contexto batch e future e 50 em contexto queueable; jobs adicionados com System.enqueueJob 50 / 1; chamadas sendEmail 10 / 10; HEAP 6 MB / 12 MB; CPU TIME 10.000 ms / 60.000 ms; tempo máximo de execução por transação 10 minutos / 10 minutos; EventBus.publish para eventos publish-immediately 150 / 150. Limites estáticos: timeout padrão de callout 10 segundos; tamanho máximo de request/response de callout 6 MB síncrono / 12 MB assíncrono (conta no heap); tempo máximo de SOQL antes do cancelamento da transação 120 segundos; batch size de trigger 200 (mas 2.000 para platform events e change data capture). Limites de 24h por org: execuções de Apex assíncrono = 250.000 ou (nº de licenças x 200), o que for maior; máx. 5 batch jobs em fila ou ativos concorrentemente; máx. 100 classes Apex agendadas concorrentemente; transações síncronas concorrentes de longa duração (>5s) = razão de 100 licenças para 1 transação, mínimo 10 e máximo 50.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_gov_limits.htm e o PDF oficial https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf (extraído e verificado literalmente)

**Licao para a Tracbel:** NÃO COPIAR OS NÚMEROS — ADAPTAR A DISCIPLINA. O CRM Tracbel é single-tenant em SQL Server próprio: não existe vizinho para proteger, e impor 100 queries por request seria arbitrário. O que copiar é o INSTRUMENTO: um contador por request (queries executadas, comandos de escrita, tempo de CPU, bytes materializados) exposto num objeto tipo Limits, logado em toda request e com THRESHOLD DE ALERTA (ex.: >30 queries ou >2s de CPU num save gera warning estruturado no log; >100 queries gera erro em ambiente de dev/homologação e alerta em produção). Isso transforma 'query dentro de loop' de bug invisível em falha de build. Com 130 usuários a Tracbel nunca vai encostar nos números do Salesforce — mas vai encostar em 'a tela de processo demora 14 segundos', e sem contador ninguém descobre por quê.

### 7. Por que os governor limits existem — e a parte contraintuitiva do CPU time

Justificativa oficial: 'Because Apex runs in a multitenant environment, the Apex runtime engine strictly enforces limits so that runaway Apex code or processes don't monopolize shared resources.' Quando um limite é excedido, 'the associated governor issues a runtime exception that can't be handled' — ou seja, LimitException NÃO pode ser capturada em try/catch, por design, para impedir que o dev burle a proteção. Uma transação Apex é 'a set of operations that are executed as a single unit. All DML operations in a transaction must complete successfully' e se qualquer operação falha 'the entire transaction is rolled back and no data is committed to the database'. Detalhe crucial sobre CPU time, direto do PDF oficial: 'Application server CPU time spent in DML operations is counted towards the Apex CPU limit. Operations that don't consume application server CPU time aren't counted toward CPU time. For example, the portion of execution time spent in the database for DML, SOQL, and SOSL isn't counted, nor is waiting time for Apex callouts.' Ou seja, o limite de 10.000 ms mede o SEU código, não o banco nem a espera de rede.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_limits_intro.htm; nota de rodapé 5 da tabela Apex Governor Limits no PDF salesforce_app_limits_cheatsheet.pdf

**Licao para a Tracbel:** ADAPTAR. Duas lições. (a) O limite não capturável é uma decisão de design deliberada: um circuit breaker que o desenvolvedor NÃO pode silenciar. No CRM Tracbel, o equivalente é ter um timeout de request e um limite de escrita por transação que lancem uma exceção que a camada de handler é PROIBIDA de engolir (regra de code review + analisador estático: catch genérico em volta do pipeline é proibido). (b) A distinção CPU-da-aplicação vs tempo-de-banco é exatamente o instrumento que falta para diagnosticar lentidão: medir separadamente 'tempo em SQL Server' e 'tempo em código C#' num save. No Vórtice hoje ninguém sabe qual dos dois é o culpado quando uma tela trava.

### 8. Custom Metadata Types: configuração que NÃO consome limite de query — o truque que viabiliza automação dirigida por configuração

Afirmação literal do PDF oficial de limites, na nota de rodapé do limite de SOQL: 'This limit doesn't apply to custom metadata types. In a single Apex transaction, custom metadata records can have unlimited SOQL queries.' Custom metadata types são 'customizable, deployable, packageable, and upgradeable application metadata that are exposed in the application cache, allowing access without repeated queries to the database', e ficam disponíveis para campos de fórmula, validation rules, flows, Apex e SOAP API. Acesso via métodos estáticos: getAll() retorna um map de todos os registros por DeveloperName; getInstance(recordId), getInstance(developerName) e getInstance(qualifiedApiName) retornam um registro. Limitação documentada dos métodos: 'Only the first 255 characters are returned for any field in a custom metadata type record, so longer text fields get truncated. If you want all the field data from a custom metadata type record, use a SOQL query.' Operações suportadas no objeto __mdt: describeSObjects(), describeLayout(), query(), retrieve() — não há DML a partir de Apex; os registros são criados no Setup ou implantados via Metadata API.

**Evidencia:** https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf (nota 1 da tabela de governor limits, linha 137 do texto extraído); https://developer.salesforce.com/docs/atlas.en-us.apexref.meta/apexref/apex_methods_system_custom_metadata_types.htm; https://developer.salesforce.com/docs/atlas.en-us.object_reference.meta/object_reference/sforce_api_objects_custommetadatatype__mdt.htm

**Licao para a Tracbel:** COPIAR o conceito, que é a decisão de arquitetura mais elegante do Salesforce: a plataforma tirou a CONFIGURAÇÃO de dentro do orçamento de recursos, para que ninguém tenha medo de ler configuração. No CRM Tracbel: toda tabela de configuração (registro de handlers, de-para de códigos TOTVS/JDE, parâmetros de negócio, feature flags, mapeamentos de carteira/CEN) vai para um ConfigurationCache carregado na inicialização (IMemoryCache ou singleton com invalidação por versão/timestamp), NUNCA lido do banco por request. E — copiando a parte mais importante — essa configuração mora em MIGRATIONS/arquivos versionados no git e é implantada, não é 'alguém digitou em produção'. Isso resolve o problema clássico do Vórtice de config que existe em produção e ninguém sabe quem pôs nem consegue reproduzir em homologação.

### 9. Namespaces de pacotes gerenciados certificados têm orçamento PRÓPRIO de limites — o modelo de plugin isolado

Texto oficial: 'Certified managed packages — managed packages that have passed the security review for AppExchange — get their own set of limits for most per-transaction limits.' Exemplo dado: 'If you install a certified managed package, all the Apex code in that package gets its own 150 DML statements. These DML statements are in addition to the 150 DML statements your org's native code can execute... Similarly, the certified managed package gets its own 100-SOQL-query limit for synchronous Apex, in addition to the org's native code limit of 100 SOQL queries.' Não há limite de quantos namespaces certificados podem ser invocados numa transação, mas existe um teto cumulativo: 'This cumulative limit is 11 times the per-namespace limit. For example, if the per-namespace limit for SOQL queries is 100, a single transaction can perform up to 1,100 SOQL queries.' E a ressalva crítica: 'Namespaces in non-certified packages don't have their own separate governor limits. The resources that they use continue to count against the same governor limits used by the org's custom code.' O limite cumulativo não vale para limites compartilhados como CPU time.

**Evidencia:** https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf, seção 'Per-Transaction Certified Managed Package Limits'

**Licao para a Tracbel:** ADAPTAR com moderação — e é uma lição de governança, não de código. O princípio: extensão de terceiro que passou por REVISÃO ganha isolamento e orçamento próprio; extensão não revisada divide o orçamento de todo mundo. Na Tracbel isso vira política: código de handler que passou por code review e tem teste entra no pipeline principal; script/customização ad hoc (ex.: alguém do negócio pedindo uma automação urgente) roda em fila assíncrona separada, com seu próprio orçamento e sem poder derrubar o save do usuário. DESCARTAR a implementação literal de namespaces com contadores separados — é complexidade demais para um time de 3 pessoas. O que fica é: nunca deixe extensão não-revisada rodar dentro da transação síncrona do usuário.

### 10. Apex assíncrono: as quatro ferramentas, o que cada uma resolve e por que Queueable substituiu @future

@future: processamento 'single-shot', limitado a tipos primitivos ou coleções de primitivos como parâmetros; não retorna Job Id monitorável; pode enfileirar milhares. Queueable: aceita membros de tipos NÃO-primitivos (sObjects e tipos Apex customizados) acessíveis quando o job executa; retorna Job Id monitorável via query em AsyncApexJob ou pela UI de Apex Jobs; permite ENCADEAMENTO — 'You can add only one job from an executing job, which means that only one child job can exist for each parent job'; em Developer Edition e orgs Trial o stack depth máximo de jobs encadeados é 5 (permitindo encadear 4 vezes); System.enqueueJob tem três sobrecargas: (queueable), (queueable, delay em minutos, faixa 0–10) e (queueable, asyncOptions); 'You can add up to 50 jobs to the queue with System.enqueueJob in a single transaction' mas transações assíncronas permitem apenas 1; Database.AllowsCallouts habilita HTTP callout no job e nos filhos encadeados; System.Finalizer anexa lógica de recuperação de falha. Batchable: para grandes volumes — start() retorna QueryLocator (até 50 milhões de registros, ignorando o limite de SOQL) ou Iterable; escopo padrão de 200 registros, máximo 2.000 com QueryLocator (valores maiores são fatiados automaticamente em lotes de 2.000); CADA execute() É UMA TRANSAÇÃO DISCRETA COM LIMITES RENOVADOS; Database.Stateful preserva variáveis de instância entre chunks. Schedulable: execução em horário específico (máx. 100 classes agendadas concorrentemente); nota importante do PDF: 'Although scheduled Apex is an asynchronous feature, synchronous limits apply to scheduled Apex jobs.'

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_queueing_jobs.htm; https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_batch_interface.htm; https://developer.salesforce.com/blogs/developer-relations/2015/05/queueable-apex-future; PDF salesforce_app_limits_cheatsheet.pdf

**Licao para a Tracbel:** COPIAR o mapa mental, implementar com Hangfire ou Quartz.NET. Traduções diretas: @future/Queueable -> BackgroundJob.Enqueue do Hangfire (que já dá Job Id, retry, dashboard e serialização de objetos complexos — ou seja, o .NET nasce no nível do Queueable, não do @future); Schedulable -> RecurringJob.AddOrUpdate com cron; Batchable -> job que pagina explicitamente com chunk de 200–2000 e ABRE UMA TRANSAÇÃO POR CHUNK. Essa última é a lição que mais importa: o padrão 'cada chunk é uma transação nova' é o que permite processar 50 milhões de registros sem estourar nada, e é exatamente o oposto do que um dev faz por instinto (abrir uma transação gigante). Documentar isso como regra: job em massa NUNCA é uma transação só.

### 11. Enfileirar job assíncrono direto do trigger é anti-padrão declarado; o padrão seguro é a fila via flag + job agendado

O guia oficial trata o assunto com dureza: 'Enqueuing a Queueable Apex job directly from a trigger should be considered a risky pattern, used only when Apex-provided control is needed... and CDC is not a viable option.' Três riscos numerados: (1) o limite diário de execuções assíncronas é compartilhado por toda a org — 'A bulk data load of 20,000 records will cause a trigger to execute in chunks of 200, resulting in 100 separate trigger invocations... If each invocation enqueues an asynchronous job, a significant portion of the daily limit from a single data load may be consumed. This consumption can potentially starve other critical business processes of async resources.'; (2) 'From a trigger fired by a user action in the UI — a synchronous transaction — up to 50 queueable jobs can be enqueued. However, from a trigger fired within the execute method of a Batch Apex class — an asynchronous transaction — only one queueable job can be enqueued. Failing to account for this difference is a common and critical failure point, leading to LimitException errors during large data operations.'; (3) 'Calling Schedulable Apex (System.schedule) or Batch Apex (Database.executeBatch) directly from a trigger context constitutes an anti-pattern.' O padrão recomendado quando o volume é alto e CDC não está disponível: '(1) Perform a simple, low-cost update in the synchronous trigger. For example, set a Status__c field to "pending processing"... (2) Create a scheduled job, either a scheduled flow or scheduled Apex, that runs periodically, such as every 15 minutes or every hour. (3) Have the scheduled job query for all records in the pending state, execute the complex logic in a controlled, high-volume context, and then update the records as processed.'

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (seção de padrões assíncronos e árvore de decisão)

**Licao para a Tracbel:** COPIAR — este é exatamente o padrão OUTBOX, e é o que a Tracbel deve usar como default para tudo que é efeito colateral. Em vez de o handler pós-save chamar Hangfire diretamente (o equivalente do anti-padrão), ele GRAVA UMA LINHA numa tabela OutboxMessage dentro da MESMA transação do save. Um worker (Hangfire recurring, a cada 30s–1min) lê o outbox em lotes, processa e marca. Vantagens que espelham as do texto oficial: o save do usuário nunca falha por causa de e-mail/integração fora do ar; carga em massa de 20.000 registros gera 20.000 linhas de outbox processadas em lotes controlados, não 20.000 jobs; e ganha-se retry, ordenação e auditoria de graça. Este é o antídoto para o problema real e documentado da Tracbel de 'Ação 900 não é gerada após faturamento' — com outbox, a falha fica visível numa tabela em vez de sumir.

### 12. Platform Events: 'Publish Immediately' vs 'Publish After Commit' é a decisão de consistência, e o default é o inseguro

Comportamento oficial. Publish Immediately (declarado como 'the default option'): o evento é publicado FORA da transação de banco; 'The allOrNone header is ignored when publishing through the APIs. Some events can be published even when others fail in the same call'; 'You can't roll back published event messages, and the Apex setSavepoint() and rollback() Database class methods aren't supported'; o assinante pode receber o evento ANTES do dado ser commitado pelo publicador. Publish After Commit: o evento só é publicado depois do commit bem-sucedido; allOrNone vale para o enfileiramento inicial; 'You can roll back published event messages with the Apex setSavepoint() and rollback() Database class methods'; escolhido 'only if the subscriber requires committed transaction data when it receives the event message'. Impacto em limites: com Publish After Commit cada EventBus.publish conta como um DML statement contra o limite de 150; com Publish Immediately conta contra um limite separado de 150 chamadas EventBus.publish (verificável por Limits.getPublishImmediateDML()). Retenção: 'High-volume platform event messages are stored for 72 hours (3 days). Legacy standard-volume platform event messages are stored for 24 hours (1 day).' Ordem: garantida dentro de uma mesma chamada de publish, NÃO garantida entre requests diferentes ('publish requests can be processed by different Salesforce application servers'). Cada mensagem recebe um Replay ID persistido, e os assinantes recebem na ordem do replay ID — mas 'Replay ID values aren't guaranteed to be contiguous for consecutive events' e o cliente 'must not compute new replay IDs based on a stored replay ID'.

**Evidencia:** https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/platform_events.pdf (Platform Events Developer Guide, seções 'Publish Behavior', 'Event Retention in the Event Bus', 'Order of Events')

**Licao para a Tracbel:** COPIAR a distinção e INVERTER O DEFAULT. A Tracbel deve tratar 'Publish After Commit' (outbox transacional) como o padrão obrigatório e 'Publish Immediately' como exceção justificada — porque o modo imediato é a origem clássica do bug 'o sistema externo consultou e não achou o registro que acabou de ser avisado'. Copiar também três detalhes de contrato: (a) o consumidor deve ser IDEMPOTENTE, porque a entrega é at-least-once; (b) guardar um cursor/offset por consumidor (o Replay ID) e nunca calcular offsets, só armazenar o último processado; (c) definir retenção explícita da tabela de eventos (72h é um número razoável para copiar como default de expurgo, com os eventos de negócio duráveis indo para uma tabela de histórico separada).

### 13. Trigger de Platform Event: assíncrono, batch de 2.000, roda como usuário de sistema, com semântica de retry e checkpoint

Para assinar, escreve-se um trigger 'after insert' no objeto de evento — 'Triggers provide an autosubscription mechanism. No need to explicitly create and listen to a channel in Apex.' Características documentadas: 'An Apex trigger processes platform event notifications sequentially in the order they're received. The order of events is based on the event replay ID. An Apex trigger can receive a batch of events at once. The maximum batch size in a platform event trigger is 2,000 event messages.' Crucialmente: 'Unlike triggers on standard or custom objects, triggers on platform events don't execute in the same Apex transaction as the one that published the event. The trigger runs asynchronously in its own process. As a result, there can be a delay between when an event is published and when the trigger processes the event.' O trigger roda sob a entidade Automated Process (ou um usuário configurado via PlatformEventSubscriberConfig), e o OwnerId dos registros criados é o do usuário executor. Tratamento de erro em duas estratégias comparadas oficialmente: setResumeCheckpoint(replayId) — usar quando o trigger já processou eventos com sucesso antes da exceção; a execução CONTINUA, as operações DML já feitas SÃO COMMITADAS, e no reenvio só chegam os eventos posteriores ao checkpoint; sem limite de quantas vezes se pode fazer checkpoint. EventBus.RetryableException — usar quando se espera que uma condição externa mude ou um erro transitório passe; a execução HALTA, as DML anteriores são ROLLBACK, e no reenvio TODO o batch anterior volta; 'You can run a trigger up to 10 times when it's retried (the initial run plus 9 retries). After the trigger is retried 9 times, it moves to the error state and stops processing new events. Events sent after the trigger moves to the error state and before it returns to the running state aren't resent to the trigger. To resume event processing, fix the trigger and save it.' Recomendação oficial: limitar a menos de 9 retries, checando EventBus.TriggerContext.currentContext().retries. Subscrições paralelas: máx. 10 partições por trigger, máx. 5 triggers com subscrição paralela por org.

**Evidencia:** https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/platform_events.pdf, seções 'Subscribe to Platform Event Notifications with Apex Triggers', 'Limit the Number of Retry Attempts', 'Parallel Subscription Limits'

**Licao para a Tracbel:** COPIAR o desenho de consumidor, que é sofisticado e raramente feito direito. Traduzido para .NET/Hangfire: (a) o consumidor recebe um LOTE (IReadOnlyList<Event>), não um evento — mesmo contrato de bulk do save; (b) duas estratégias de falha distintas e explícitas, checkpoint (avança o cursor, commita o que deu certo, segue) vs retry (rollback do lote inteiro e reprocessa), escolhidas pelo tipo do erro — erro de dado é checkpoint, erro de infraestrutura é retry; (c) TETO DE RETRY com DEAD LETTER: depois de N tentativas o consumidor entra em estado de erro, PARA e alerta, em vez de girar para sempre. E o alerta operacional que a doc dá de graça: eventos publicados enquanto o consumidor está em estado de erro NÃO são reenviados — logo o CRM Tracbel precisa de uma fila durável (a tabela de outbox/inbox) e não pode depender de um bus volátil.

### 14. Change Data Capture: o padrão de offload de alto volume, e a limitação que decide se serve ou não

CDC 'enables developers to receive near-real-time changes of Salesforce records, and synchronize corresponding records in an external data store', publicando eventos de criação, atualização, exclusão e restauração (changeType CREATE, UPDATE, DELETE, UNDELETE), com um ChangeEventHeader de metadados mais os campos do registro. Assinatura via Pub/Sub API, CometD, triggers Apex, empApi Lightning e event relays. Como padrão arquitetural para automação pesada: 'the trigger's only responsibility is to save the record synchronously. The platform then publishes a detailed event message that contains the record's changes to a high-volume event bus. A separate, dedicated Apex trigger subscribes to this change event.' Benefício declarado: 'A failure in the asynchronous processing won't cause the user's record save to roll back. The pattern also provides a durable event stream that multiple internal subscribers or external systems can consume, and events can be replayed for up to 72 hours.' A limitação decisiva, textual: 'CDC event messages don't contain the record's prior state — the equivalent of an Apex Trigger.oldMap. The event payload includes the new field values, but not the values they changed from. This makes it challenging to implement logic based on a specific state transition (for example, run only if Status__c changed from "Pending" to "Approved"). You can mitigate this by querying the object's field history in the event subscriber, but this adds complexity... and field history tracking may not be available for the specific field of interest.' Limite: 'By default, CDC can be enabled on a maximum of five Salesforce Objects.'

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.change_data_capture.meta/change_data_capture/cdc_intro.htm; https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (seção CDC)

**Licao para a Tracbel:** COPIAR o padrão, CORRIGIR o defeito. A Tracbel deve emitir eventos de mudança a partir do EF Core (SaveChangesInterceptor lendo o ChangeTracker) — mas, ao contrário do CDC do Salesforce, DEVE INCLUIR O ESTADO ANTERIOR dos campos alterados no payload. Isso é trivial no EF Core (entry.OriginalValues já está em mãos) e elimina de uma vez a maior limitação do modelo original. Sem isso, regras como 'quando o processo sair de Pendente para Aprovado' viram consulta a histórico — que é justamente o tipo de complexidade que quebra CRM. Formato sugerido do evento: { Entity, Id, ChangeType, ChangedFields: [{ Name, Old, New }], OccurredAt, UserId, CorrelationId }. E copiar a ideia de replay de 72h como janela mínima de reprocessamento.

### 15. A matriz de densidade de automação: o critério objetivo da Salesforce para escolher configuração vs código

A Salesforce define 'automation density' como 'the load placed on a specific Salesforce Object. It serves as a heuristic to determine the object's optimal implementation. As automation density grows, the likelihood of breaching transactional limits increases.' Três dimensões: quantidade de automações, volume de dados por transação e 'dependency sprawl' (operações DML derivadas). A matriz oficial, literal: BAIXA — menos de 15 automações, volume 'Standard' (interações de UI ou cargas pequenas de API, 1–200 registros), dependência 'Discrete' (lógica autocontida, 0–1 DML derivado) -> padrão arquitetural RECORD-TRIGGERED FLOW. MÉDIA — 15 a 30 automações, volume 'Moderate' (batch padrão exigindo bulkificação cuidadosa), dependência 'Coupled' (atualizações pai/filho, 2–4 DML derivados, risco de recursão) -> PADRÃO HÍBRIDO (Flow + Apex invocável). ALTA — mais de 30 automações, volume 'High' (cargas Bulk API de 2.000 a 10.000+ registros), dependência 'Complex and Recursive' (grafo profundo, 5+ DML derivados, risco de loops de recursão triangular) -> APEX TRIGGER METADATA FRAMEWORK. Princípio transversal: 'For a given Salesforce Object, use one mechanism as your entry point into automation' (One Tool Per Object).

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (tabela 'The Density Selection Matrix', extraída literalmente)

**Licao para a Tracbel:** ADAPTAR como critério de governança, não como matriz literal. A tradução para a Tracbel: a decisão 'isso vira configuração ou vira código?' precisa de um critério ESCRITO, e a densidade é um bom critério. Regra sugerida para o CRM Tracbel: entidades com poucas automações e sem efeito cruzado (ex.: cadastros auxiliares) podem ter regras declarativas simples em tabela; entidades quentes com muitas regras e cascata (Processo/Oportunidade, Pessoa/Cliente, Pedido) TÊM QUE ser handlers em C# no framework de dispatch. E o 'One Tool Per Object' é o que salva a manutenção: por entidade, existe UM ponto de entrada de automação (o Dispatcher) e ponto final — nada de metade das regras em trigger de banco, metade em service, metade em job. Esse é exatamente o defeito que o time enfrenta hoje no Vórtice, onde regra de negócio aparece em lugares imprevisíveis.

### 16. Flow vs Apex: a matriz oficial de capacidades — onde o declarativo simplesmente não alcança

Comparação oficial ponto a ponto. Flow é RECOMENDADO em: velocidade de entrega e manutenção (UI visual, menos dependência de dev); visibilidade e governança (Flow Trigger Explorer dá visão consolidada de todos os flows de um objeto); salvaguardas de plataforma ('Flow includes built-in protections, such as auto-bulkification and automatic retries'); distribuição de e-mail; processamento AGENDADO ('Flow's scheduled paths provide a unique and powerful scheduling capability (for example, "fire 3 days before close date"). This capability includes automatic cancellation and rescheduling if the record's data changes' — e para isso Apex é declarado 'Not Available'). Apex é RECOMENDADO em: processamento em massa de alta performance (Flow é 'Not recommended' aqui: 'There is an elevated risk of hitting governor limits'); lógica robusta e estruturas de dados ('Flow lacks native Map and Set data structures, making complex data processing cumbersome and computationally inefficient'); CONTROLE TRANSACIONAL, onde Flow é 'Not Available': 'Flow provides no access to Database.savepoint, Database.rollback, or partially successful DML operations'; deduplicação de computação cara (Apex tem cache transacional via variáveis estáticas e Platform Cache via Cache.CacheBuilder; 'state cannot be cached or shared between different flow triggers' em Flow); tratamento customizado de erro (o método addError() do Apex vs o elemento CustomError do Flow, que 'is not available in all flow types—including subflows'). Casos de uso melhor servidos por Apex, segundo a tabela oficial: batch de alta performance, processamento complexo de dados, controle transacional e validação customizada sofisticada.

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (tabela de comparação de capacidades e tabela de casos de uso)

**Licao para a Tracbel:** USAR COMO CHECKLIST DE ESCOPO DA CAMADA DECLARATIVA — e essa é a lição mais protetora do relatório para um time de 2–3 pessoas. A própria Salesforce, com centenas de engenheiros, admite que seu motor declarativo NÃO tem controle transacional, NÃO tem Map/Set, NÃO compartilha cache e é ruim em volume. Portanto: DESCARTAR qualquer ambição de construir um Flow Builder visual no CRM Tracbel. A camada de configuração deve se limitar ao que o Salesforce prova ser seguro no declarativo: ordenar/ligar/desligar handlers, critérios de entrada simples (campo mudou / campo é igual a X), parametrização numérica e textual, mapeamentos de-para, templates de mensagem e agendamento relativo a data de campo ('3 dias antes da data prevista' — copiar essa ideia, é genuinamente útil para follow-up comercial). ### 18. O padrão híbrido e o contrato do @InvocableMethod: como código é consumido pela configuração

O padrão híbrido oficial posiciona 'Record-Triggered Flow as the orchestration layer, while encapsulating high-complexity operations within Invocable Apex'. Divisão de responsabilidade declarada: 'Record-Triggered Flow serves as the orchestrating layer for the business process. It owns the entry criteria and execution context (the what and when)... preventing critical business logic from being obscured within code.' Exemplo concreto dado: cálculo de SLA em Case usando o objeto BusinessHours (não acessível nativamente em Flow), encapsulado numa classe ServiceLevelAgreementCalculator com um único método estático anotado com @InvocableMethod. Benefícios declarados: modularidade (unidades atômicas, bulk-safe, testáveis isoladamente), REUSABILIDADE ('A well-designed code unit (such as an InvocableMethod) is written one time but leveraged across multiple entry points: Record-triggered flows, screen flows, or external integrations') e manutenibilidade. As regras do contrato @InvocableMethod: método static e public ou global em classe externa; no máximo UM parâmetro de entrada e ele DEVE ser uma List (de primitivo, de sObject, de sObject genérico ou de tipo definido pelo usuário com @InvocableVariable); retorno deve ser uma List; 'Only one method in a class can have the InvocableMethod annotation'; atributos label, description, category e callout=true quando faz chamada externa; e o contrato de bulk: 'the i-th Output entry must correspond to the i-th Input entry'. Limitações do padrão híbrido, textuais: 'No before-save support: This is the most critical limitation. Invocable Actions are only available in the after-save context... Therefore, this pattern cannot be used to delegate same-record field updates'; 'No after-undelete support: Record-Triggered Flow currently does not support the after-undelete context'; e overhead de performance na transição do runtime de Flow para o de Apex.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_classes_annotation_InvocableMethod.htm; https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (seção 'Hybrid Pattern: Invocable Apex for Complex Logic in Flow')

**Licao para a Tracbel:** COPIAR O CONTRATO, que é a peça que faltava para 'qualquer dev do time saber estender'. A interface do handler no CRM Tracbel deve forçar bulk pela ASSINATURA, exatamente como o @InvocableMethod: `Task<IReadOnlyList<TOut>> HandleAsync(IReadOnlyList<ChangeContext<T>> items, CancellationToken ct)`. Nunca `Handle(T entity)`. Isso torna FISICAMENTE IMPOSSÍVEL escrever query dentro de loop de forma inocente — o dev recebe a lista e naturalmente escreve um `WHERE Id IN (...)`. É a mesma jogada da Salesforce: o design da API força a prática correta em vez de depender de documentação e disciplina. Copiar também a reusabilidade: o mesmo handler deve ser chamável pelo pipeline de save, por um job agendado e por um endpoint de API — o que exige que ele não dependa de HttpContext nem de estado de request.

### 19. SOQL não é SQL: o que existe, o que não existe, e todos os limites numéricos

SOQL é 'the equivalent of a SELECT SQL statement and searches the org database'; SOSL é 'a programmatic way of performing a text-based search against the search index'. Diferenças estruturais em relação a SQL: não existe SELECT * ('the fieldList in the SELECT statement specifies the list of one or more fields, separated by commas, that you want to retrieve'), e 'Relationship queries are not the same as SQL joins. You must have a relationship between objects to create a join in SOQL' — ou seja, só se navega por relacionamentos pré-declarados no modelo, nunca por JOIN arbitrário entre duas tabelas quaisquer. A navegação tem duas formas: FILHO-PARA-PAI por notação de ponto, ex.: `SELECT Id, Name, Account.Name FROM Contact WHERE Account.Industry = 'media'`; e PAI-PARA-FILHO por subquery entre parênteses usando o nome plural do relacionamento, ex.: `SELECT Name, (SELECT LastName FROM Contacts WHERE CreatedBy.Alias = 'x') FROM Account WHERE Industry = 'media'`. Limites de relacionamento: 'No more than 55 child-to-parent relationships can be specified in a query'; 'no more than five levels can be specified in a child-to-parent relationship' (ex.: Contact.Account.Owner.FirstName são três níveis); 'No more than 20 parent-to-child relationships can be specified in a query'; até 5 níveis de pai-para-filho em API 58.0+ (era 2 níveis até a 57.0); objeto customizado permite até 40 relacionamentos. Limites de statement: comprimento máximo de statement SOQL 100.000 caracteres (default); comprimento máximo de statement SOSL 100.000 caracteres; string SearchQuery do SOSL máx. 10.000 caracteres (acima disso não retorna resultado); OFFSET máximo 2.000 linhas; strings de cláusula WHERE 4.000 caracteres cada; máx. 500 junction IDs por query; SOSL retorna no máximo 2.000 resultados no total (API 28.0+); disponibilidade dos resultados 2 dias; timeout de query 32 minutos no total (2 minutos de execução, 30 de processamento). Em objetos externos: subqueries buscam até 1.000 linhas e 'Each SOQL query can have up to 4 joins across external objects'. Quando usar SOSL em vez de SOQL: quando não se sabe qual objeto/campo tem o dado, para busca de termo específico dentro de um campo, quando 'faster' com operações CONTAINS, e para conteúdo em chinês, japonês, coreano ou tailandês. 'SOSL doesn't support big objects.'

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.soql_sosl.meta/soql_sosl/sforce_api_calls_soql_sosl_intro.htm; .../sforce_api_calls_soql_relationships_query_limits.htm; .../sforce_api_calls_soql_relationships_query_using.htm; .../sforce_api_calls_soql_limits.htm; https://developer.salesforce.com/docs/atlas.en-us.salesforce_app_limits_cheatsheet.meta/salesforce_app_limits_cheatsheet/salesforce_app_limits_platform_soslsoql.htm

**Licao para a Tracbel:** NÃO COPIAR A LINGUAGEM — COPIAR A RESTRIÇÃO. A Tracbel tem SQL Server e EF Core: seria insanidade inventar uma linguagem de consulta própria. Mas há duas lições reais. (a) SOQL só navega relacionamentos DECLARADOS no modelo, e é isso que permite que a plataforma seja segura, que a UI gere consultas sozinha e que exista permissionamento em nível de campo. O equivalente .NET é: o cliente (React) NUNCA manda SQL nem uma expressão livre; manda um filtro tipado sobre um modelo de leitura declarado, e o backend traduz via LINQ/EF. Isso mata SQL injection por construção e permite aplicar segurança por campo. (b) A separação SOQL (estruturada) vs SOSL (índice de texto) é a resposta certa para a busca do CRM: consulta estruturada vai para o SQL Server; busca global por texto ('acha esse cliente/máquina/chassi em qualquer lugar') deve ir para um índice de texto (SQL Server Full-Text Search ou um índice dedicado), NUNCA para LIKE '%termo%' em N tabelas — que é o que costuma travar CRM legado. Copiar também o teto duro de resultado (algo como 2.000 linhas) em toda consulta exposta a usuário, com paginação obrigatória.

### 20. APIs de integração: qual usar para qual volume, com os números de corte

REST API: 'works well to retrieve several thousand records', mas 'its resources are too granular for write operations at scale (one request per write operation)'. Composite API: síncrona, com acesso aos recursos da REST API, suportando múltiplas operações de escrita por request. Recurso `composite`: 'You can have up to 25 subrequests in a single call. Up to 5 of these subrequests can be sObject Collections or query operations'; permite DEPENDÊNCIA entre subrequests via referências `@{referenceId.FieldName}` e `@{referenceId[0].Id}` (case-sensitive: `@{refAccount.id}` é diferente de `@{refAccount.Id}`); com allOrNone=true 'the entire composite request is rolled back' em caso de erro. Recurso `composite/batch`: até 25 subrequests SEQUENCIAIS e INDEPENDENTES, sem passar informação entre eles (até 10 podem ser queries). Independente do número de subrequests, cada composite request conta como UMA chamada de API. Bulk API 2.0 (assíncrona): recomendação oficial de corte — 'Any data operation that includes more than 2,000 records is a good candidate for Bulk API 2.0... Jobs with fewer than 2,000 records should involve "bulkified" synchronous calls in REST (for example, Composite) or SOAP.' Números: até 150.000.000 registros carregados por período de 24h; até 15.000 batches por período móvel de 24h (compartilhado entre Bulk API e Bulk API 2.0); máx. 10.000 registros por batch; máx. 10.000.000 de caracteres por batch; tamanho de arquivo 10 MB por batch no Bulk API e 150 MB por job no Bulk API 2.0 (com upload máximo de 100 MB, considerando ~50% de aumento por codificação base64); máx. 131.072 caracteres por campo, 5.000 campos por registro, 400.000 caracteres por registro; 'Each chunk of 200 records is processed as a separate transaction'; jobs e batches com mais de 7 dias são removidos da fila; 10.000 query jobs por 24h; 1 TB de resultados de query por janela de 24h. Limites gerais de API: requests concorrentes com duração ≥20 segundos limitados a 25 em orgs de produção e sandboxes (5 em Developer/Trial), retornando REQUEST_LIMIT_EXCEEDED; 'There isn't a limit on the number of concurrent requests shorter than 20 seconds'; timeout de chamadas REST e SOAP de 10 minutos; total de chamadas por 24h em Enterprise = 100.000 + (nº de licenças x 1.000) + add-ons; comprimento combinado de URI e headers em cada chamada REST = 16.384 bytes, com recomendação de limitar URI a 2.000 caracteres e headers a ~8.000 bytes para serviços públicos.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.api_rest.meta/api_rest/requests_composite.htm; https://developer.salesforce.com/docs/atlas.en-us.api_rest.meta/api_rest/resources_composite_batch.htm; https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf (seções API Request Limits e Bulk API Limits)

**Licao para a Tracbel:** ADAPTAR três ideias, descartar o resto. (a) O CORTE DE 2.000 REGISTROS é um número empírico excelente para adotar como política: abaixo disso, endpoint síncrono; acima, job assíncrono com job id, status consultável e resultado em arquivo. Escrever isso no contrato de API do CRM Tracbel. (b) O padrão COMPOSITE com referências entre subrequests resolve um problema real da integração TOTVS/JDE: criar cliente + endereço + oportunidade numa ida só, com rollback tudo-ou-nada, sem o integrador precisar guardar o Id intermediário. Vale implementar um endpoint /api/composite com allOrNone e referências — é barato em .NET (uma transação envolvendo N comandos) e economiza muito round-trip. (c) O limite de requests CONCORRENTES DE LONGA DURAÇÃO (≥20s) enquanto requests curtos são ilimitados é um design de proteção elegante: em vez de limitar todo mundo, limita só quem segura recurso. Vale replicar com um SemaphoreSlim para endpoints reconhecidamente pesados (relatórios, exportações), deixando o CRUD normal livre. DESCARTAR SOAP inteiramente — é legado.

### 21. Named Credentials: credencial de integração é configuração da plataforma, nunca código nem appsettings colado

Problema resolvido, textual: 'By separating the endpoint URL and authentication from the callout definition, named credentials make callouts easier to maintain.' Arquitetura em duas camadas: a Named Credential guarda a URL do endpoint e referencia uma External Credential; a External Credential contém o mecanismo e os protocolos de autenticação de fato. Consequência declarada: o código 'doesn't have to' gerenciar autenticação, e se a URL do endpoint muda 'you update only the named credential'. Sintaxe de uso em Apex: `callout:NamedCredentialName/optional_path`, com query string anexável (ex.: `callout:My_Named_Credential/some_path?format=json`). Named Credentials eliminam a necessidade de Remote Site Settings, que 'are otherwise required for callouts to external sites' quando não se usa named credentials. Sem elas, o desenvolvedor teria que 'manually encode credentials, construct authorization headers, and manage complex OAuth flows'. Limite relacionado: Salesforce armazena tokens de acesso e refresh de terceiros com até 10.000 caracteres.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_callouts_named_credentials.htm; limite de token em https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf

**Licao para a Tracbel:** COPIAR, e com urgência particular dado o histórico. A memória do projeto registra dois problemas exatamente desse tipo no Vórtice: parâmetros OutParLinkBase* ainda apontando para o IP antigo depois da migração de data center, e a senha de app do SMTP noreply_agro@ vivendo em configuração espalhada. O desenho correto para o CRM Tracbel: uma abstração `IOutboundEndpoint` resolvida por NOME (`endpoints.Get("TOTVS_Pedidos")`), onde o código NUNCA vê URL nem credencial — só o nome lógico. Endpoint (URL, timeout, retry) numa tabela de configuração versionada; SEGREDO no Azure Key Vault, AWS Secrets Manager ou, no mínimo, .NET User Secrets/variável de ambiente com rotação — nunca em appsettings.json commitado, nunca no banco em texto claro. Ganho concreto: quando o IP/host mudar de novo (e vai mudar), é UMA linha de configuração, não uma caçada por strings no código e em cinco tabelas de parâmetro.

### 22. Segurança: a Salesforce inverteu o default para 'user mode' na API 67.0 — de opt-in para opt-out

Mudanças versionadas oficiais para a API 67.0: (1) 'In API version 67.0 and later, Apex runs in user context by default, meaning that the current user's permissions and field-level security (FLS) are enforced during code execution' — na 66.0 e anteriores o default era system mode, que 'runs with substantially elevated permissions'; (2) 'In API version 67.0 and later, classes without an explicit sharing declaration are run in the current user context' — ou seja, `with sharing` virou o comportamento padrão, e para não aplicar regras de compartilhamento é preciso declarar explicitamente `without sharing`; (3) 'With API version 67.0 and later, you cannot use the WITH SECURITY_ENFORCED clause in SOQL SELECT queries in Apex code' — deve-se usar `WITH USER_MODE`. Os três modificadores de compartilhamento: `with sharing` aplica as regras de compartilhamento do usuário corrente; `without sharing` garante que as regras não sejam aplicadas; `inherited sharing` aplica as regras da classe chamadora. Ponto crítico frequentemente ignorado: 'Sharing declarations don't enforce object-level access or field-level security' — compartilhamento (quais REGISTROS) e permissão de objeto/campo (quais TABELAS e COLUNAS) são mecanismos independentes, e 'Object-level and field-level permissions take precedence over sharing rules'. Ferramentas complementares: `Security.stripInaccessible()` que 'enforce[s] field-level and object-level data protection by stripping fields and relationship fields from query and subquery results that the user can't access'; e as classes Schema.DescribeSObjectResult / DescribeFieldResult para checar permissões antes de operar.

**Evidencia:** https://developer.salesforce.com/docs/atlas.en-us.apexref.meta/apexref/versioned_behavior_changes.htm; https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_classes_keywords_sharing.htm; https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_classes_perms_enforcing.htm

**Licao para a Tracbel:** COPIAR O MODELO DE TRÊS EIXOS E O DEFAULT SEGURO — atende diretamente o requisito de 'níveis diversos de permissão' e 'segurança alta'. Os três eixos independentes que a Tracbel deve implementar separadamente e nunca confundir: (1) OBJETO — este usuário pode ler/criar/editar/excluir a entidade Processo? (permissão/claim, checada no endpoint); (2) CAMPO — este usuário pode ver/editar o campo Margem ou Custo? (lista de campos permitidos por perfil, aplicada na projeção de leitura e na validação de escrita — é o equivalente do stripInaccessible, e é o eixo que praticamente todo CRM caseiro esquece); (3) REGISTRO — este usuário pode ver ESTE processo? (regra de carteira/CEN/hierarquia — a Tracbel já tem essa semântica em IVS_Carteira e IV_VENDEDOR). E copiar a lição da inversão de default: o filtro de segurança deve ser aplicado POR PADRÃO no repositório/DbContext (via Global Query Filters do EF Core + um IUserContext), e a elevação de privilégio deve ser um `AsSystem()` EXPLÍCITO e auditado. Se o dev esquecer de pensar em segurança, o comportamento resultante tem que ser o seguro, não o inseguro. Essa única decisão vale mais que qualquer revisão de código posterior.

### 23. Automação declarativa: Flow (os tipos), Validation Rules, Approval Process, Formula Field e Roll-Up Summary

Tipos de Flow: SCREEN FLOW — o único que interage com o usuário, disparado por clique em botão/link ou invocado de uma página Lightning, site Experience Cloud ou componente web/Aura; exige interação humana. RECORD-TRIGGERED FLOW — autolaunched, roda quando um registro é criado, atualizado ou excluído; subdivide-se em before-save (fast field updates, agindo sobre o próprio registro antes do save) e after-save (actions and related records). SCHEDULE-TRIGGERED FLOW — roda em background em horário e frequência especificados (diária, semanal, uma vez) sobre um lote de registros; descrito como 'a low-code version of a scheduled batch Apex'. PLATFORM EVENT-TRIGGERED FLOW — autolaunched, roda quando uma mensagem de platform event é recebida; útil para integrar com sistemas externos que enviam notificações. AUTOLAUNCHED FLOW (sem gatilho) — invocado por outros processos. Além disso, o recurso de SCHEDULED PATHS dentro de record-triggered flows permite disparo temporal relativo a dados do registro ('fire 3 days before close date'), com cancelamento e reagendamento automáticos se o dado do registro mudar — capacidade declarada como 'Not Available' em Apex trigger. VALIDATION RULES: rodam na etapa 5 da order of execution (antes do save no banco), podendo bloquear a gravação. APPROVAL PROCESS: composto por filter/entry criteria (registros precisam atender ao critério para serem submetidos), approval steps (com aprovação paralela e opção 'else'), aprovador automático por campo de hierarquia (ex.: Manager), initial submission actions, final approval/rejection actions, recall actions e a opção 'Allow submitters to recall approval requests'; a lista relacionada Approval History é adicionada ao layout, e a lista 'Items To Approve' mostra as solicitações pendentes do usuário; invocável de Apex via Approval.process(), que consome o limite de 10.000 linhas de DML por transação. ROLL-UP SUMMARY: definido no lado master de um relacionamento master-detail, recalculado nas etapas 16 e 17 da order of execution, com cada recálculo de pai e avô passando pelo procedimento de save completo.

**Evidencia:** https://trailhead.salesforce.com/content/learn/modules/record-triggered-flows/get-started-with-triggered-flows; https://admin.salesforce.com/blog/2023/what-is-a-schedule-triggered-flow; https://admin.salesforce.com/blog/2023/what-is-a-platform-event-triggered-flow; https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_triggers_order_of_execution.htm; https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_useful_approval_processes.pdf

**Licao para a Tracbel:** SELECIONAR: copiar dois, adaptar um, descartar dois. COPIAR (1) SCHEDULED PATHS — disparo relativo a data de campo com cancelamento automático quando o dado muda é genuinamente valioso para follow-up comercial ('3 dias antes da data prevista de fechamento, criar tarefa para o vendedor'), e resolve por desenho o problema conhecido da Tracbel de tarefa/ação que não é gerada ou fica órfã quando o processo muda. Implementar como tabela ScheduledAction (EntityId, DueAt, HandlerKey, Status) reavaliada a cada save da entidade. COPIAR (2) APPROVAL PROCESS como MÁQUINA DE ESTADO CONFIGURÁVEL — entry criteria, steps ordenados, aprovador resolvido por regra (líder do CEN), ações de submissão/aprovação/rejeição e RECALL. A memória do projeto registra que a aprovação no Vórtice vai para o líder do CEN 'no momento da geração' e que a agenda antiga não se reatribui — o modelo do Salesforce trata isso explicitamente com ProcessInstance versionado por step, e vale copiar essa estrutura (uma tabela de instância de aprovação com histórico por etapa, em vez de um campo de status no registro). ADAPTAR Validation Rules: uma tabela de regras simples (campo, operador, valor, mensagem) cobre 80% dos casos sem release; o resto é IValidationRule<T> em C#. DESCARTAR Roll-Up Summary como feature genérica configurável — o recálculo em cascata de pai e avô passando pelo save completo é justamente a origem de lentidão e recursão; na Tracbel, agregados devem ser colunas materializadas atualizadas por handler explícito ou views indexadas do SQL Server. DESCARTAR construir Screen Flow — a UI é React e ponto final.

### 24. Mega-flow é anti-padrão; e o que realmente move o ponteiro de performance

Posição oficial: 'It is an anti-pattern to consolidate all of an object's automation into a single, massive mega-flow.' Mas com uma nuance importante e contraintuitiva: 'Consolidating into one flow versus splitting logic into multiple, well-conditioned flows does not have a major impact on performance. The most significant performance gains come from: Using before-save flows for same-record field updates. Writing precise entry conditions to ensure flows are excluded from running on changes that do not impact their specific use case.' O Flow Trigger Explorer permite atribuir um valor de ordem a cada flow de um objeto, 'guaranteeing a sequential execution order'. Sobre coexistência de Flow e Apex trigger no mesmo objeto (situação comum em orgs maduras por dívida técnica): 'The fragmented orchestration causes significant governance and maintenance overhead, making development, testing, and incident handling activities disjointed and cumbersome. This leads to increased Time to Resolution (TTR).' Recomendações de refatoração por densidade: baixa — refatorar triggers Apex para record-triggered flows com ordem especificada, unificando num único ponto de entrada; média — quebrar mega-flows num subconjunto de flows com ordem correta, introduzindo Apex trigger só quando absolutamente necessário (ex.: suportar contexto after-undelete); alta — favorecer Apex triggers.

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (seções 'Mega-Flows vs. Multiple Flows' e de coexistência)

**Licao para a Tracbel:** COPIAR as duas conclusões, que são economicamente importantes. (a) Modularidade é sobre MANUTENÇÃO, não performance — quebrar em handlers pequenos vale por testabilidade, merge sem conflito e leitura, não porque fica mais rápido. Não vender modularidade ao time como otimização, senão a primeira medição frustra. (b) O que realmente dá performance é ANTES DO COMMIT + CRITÉRIO DE ENTRADA PRECISO. Traduzindo: cada handler registrado na tabela TriggerAction deve declarar seu critério de entrada (ex.: WatchedFields = 'Status,ValorTotal') e o Dispatcher deve PULAR o handler sem nem instanciá-lo quando nenhum campo observado mudou. Isso é barato de implementar (comparar dois HashSets) e é o único otimizador que importa num pipeline com dezenas de handlers. (c) A frase sobre 'Time to Resolution' é o argumento de negócio para levar à diretoria da Tracbel: automação espalhada em dois mecanismos não custa performance, custa TEMPO DE RESOLUÇÃO DE INCIDENTE — que é exatamente a dor atual com o Vórtice.

### 25. Documentação e DevOps como parte do desenho de automação, não como acessório

O guia oficial trata isso como decisão arquitetural: 'Documentation is as important as the automation itself. It not only ensures maintainability, it is also critical for AI and agent-based tools.' Para Apex: 'Comment your code clearly to explain the why behind your logic, not just the what. If using a metadata-driven framework, ensure your metadata records include and populate a human-readable Description field to explain what each handler class does and when it should run.' Para Flow: convenção de nomes consistente para elementos e variáveis, e uso do campo Description tanto do flow quanto de CADA elemento — 'especially important for invocable actions and subflows, where the description is the primary place to explain the complex logic performed by the action'. Sobre DevOps: 'Always use a source control tool like Git for Salesforce projects. Both Apex classes and Salesforce Flows are metadata that define your business logic, and they must be versioned and managed.' Três benefícios nomeados: AUTOMATED QUALITY CHECKS via Salesforce Code Analyzer no pipeline, que 'can detect problematic patterns in both automation tools before they are promoted, flagging issues like inefficient Get Records elements inside a Flow loop or SOQL queries inside an Apex for loop, which are common causes of performance degradation'; REGRESSION PREVENTION — 'As your automation density grows, a change to one Flow or Apex class can have unintended consequences for other automations on the same object. A robust DevOps testing strategy, where automated Apex tests are run against any proposed change, is the most reliable way to ensure a new Flow version doesn't break existing Apex logic (and vice versa)'; e COLLABORATION AND VISIBILITY — 'when a production process breaks, you can instantly see who changed the automation, when they changed it, and — via commit messages — why they changed it.'

**Evidencia:** https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html (seções Documentation e DevOps)

**Licao para a Tracbel:** COPIAR, com uma consequência de desenho que é fácil de perder. Se a configuração de automação vive numa TABELA (a TriggerAction), ela precisa ser tratada como CÓDIGO: versionada em migrations/arquivos no git, promovida de dev para homologação para produção pelo pipeline, com campo Description obrigatório e não-nulo em cada linha. O anti-padrão a evitar é o que o Vórtice já sofre — configuração que alguém alterou direto em produção, sem rastro de quem, quando e por quê. Duas exigências práticas: (1) campo Description NOT NULL na tabela de handlers, mais colunas de auditoria (quem/quando alterou); (2) um analisador estático no CI (Roslyn analyzer custom ou regra de lint) que reprove `await` dentro de `foreach` sobre entidades e chamadas de DbContext dentro de laço — o equivalente do Salesforce Code Analyzer pegando SOQL em for loop. Com 2–3 devs, esse analisador vale mais que dez páginas de guideline.
